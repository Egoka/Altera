# ADR-0033: Конфликты редактирования и путь к совместной работе

- **Статус**: принято 2026-09-05
- **Этап**: 1 (конфликты и офлайн), 6 (совместная работа)

## Контекст

Промт требует спроектировать поведение редактора при конфликте двух вкладок и при потере
сети, а также путь к совместной работе. Сейчас `updateArticle` перезаписывает тело без
проверки версии [ФАКТ: `server/src/graphql/article/resolver.ts:531-562`]; принцип «один
процесс API и один Nuxt» держится до появления причины.

## Рассмотренные варианты

| Вариант | За | Против |
|---|---|---|
| Last write wins (как сейчас) | Просто | Тихая потеря текста при двух вкладках или двух людях |
| Блокировка документа на время редактирования | Понятно | Зависшие блокировки, редактор не может открыть материал автора |
| **Optimistic lock по ревизии** + локальный черновик для офлайна; Y.js — только на этапе 6 | Потери исключены, без сервера состояния; путь к CRDT открыт | Пользователь видит баннер конфликта и выбирает |
| Y.js с первого дня | Сразу совместная работа | Второй процесс и вторая истина до появления соавторов |

## Решение

1. Сохранение принимает `baseRevisionId` — ревизию, от которой начал клиент. Если у версии
   уже есть более новая ревизия, сервер отвечает `CONFLICT` и не пишет. Клиент показывает
   баннер: «текст изменён в другой вкладке или другим человеком» с действиями «загрузить
   новую версию» и «сохранить мою как ревизию» (создаёт `manual`-ревизию поверх новой без
   замены текста). Второй вариант никогда не теряет ни одну из сторон.
2. Открытие материала в другой вкладке того же пользователя показывает мягкую пометку
   «открыто в другой вкладке» (BroadcastChannel `[ДОПУЩЕНИЕ]`), без блокировки.
3. Потеря сети: редактор продолжает работать; изменения копятся в локальном буфере
   (IndexedDB); при восстановлении отправляются с тем же `baseRevisionId` — конфликт
   обрабатывается по п. 1. Баннер «нет сети, черновик сохраняется локально».
4. Автосохранение — каждые ≤ 10 секунд при изменениях; сервер создаёт или перезаписывает
   `autosave`-ревизию по правилу ADR-0007.
5. Редакционные правки (`editorial`) идут через тот же механизм: автор, открывший старую
   версию, получает конфликт, а не затирает правку редактора.
6. **Совместная работа (этап 6)**: Y.js + `@tiptap/extension-collaboration` + отдельный
   процесс синхронизации (hocuspocus или `y-websocket`); Y.js-документ — рабочее состояние,
   JSON в базе — снимок при каждом автосохранении/публикации; optimistic lock остаётся для
   одиночного режима. Второй процесс — сознательное отклонение от принципа «один API + один
   Nuxt», допускается только на этапе 6 с согласия владельца.
7. Порог для старта этапа 6: измеренный запрос — материалы с двумя и более соавторами или
   регулярные конфликты редактор/автор `[ДОПУЩЕНИЕ]`.

## Следствия

- Мутация сохранения версии получает `baseRevisionId`; `updateArticle` в нынешнем виде
  уходит.
- E2E-тесты этапа 1: две вкладки, офлайн-режим (Playwright `setOffline`).
- До этапа 6 совместная работа заменяется замечаниями к блокам и ревизиями (этап 2).

## Цена отката

Optimistic lock — код без миграций. Переход на Y.js — аддитивный процесс; отказ от него —
удаление процесса, JSON-снимки остаются.
