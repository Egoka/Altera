# ADR-0023: Хранение сессии на клиенте и BFF-прокси

- **Статус**: принято 2026-09-05
- **Этап**: 0

## Контекст

- API — отдельный процесс на своём адресе с CORS на `FRONTEND_URL` и `credentials: true`
  [ФАКТ: `server/src/server.ts:14-18`]; веб — Nuxt с SSR. Где хранить refresh-токен, как
  выполнять SSR-запросы от имени пользователя и как защищаться от CSRF — в коде не решено:
  клиента нет вовсе.
- Yoga включает `useCSRFPrevention` (обязательный нестандартный заголовок)
  [ФАКТ: `server.ts:20`].

## Рассмотренные варианты

| Вариант | За | Против |
|---|---|---|
| Токены в `localStorage`, запросы напрямую в API | Просто | XSS крадёт refresh; SSR не знает пользователя; кросс-доменные cookie не нужны, но и защиты нет |
| Cookie API на своём домене, кросс-доменные запросы из браузера | Без прокси | Cookie третьей стороны, `SameSite=None`, сложные CORS; SSR всё равно нужен доступ к cookie |
| **BFF-прокси в Nuxt**: браузер ходит только на свой origin (`/api/graphql`), Nuxt пересылает в API; refresh в httpOnly-cookie своего домена; access в памяти клиента и в SSR-контексте | Один origin, cookie первой стороны, SSR видит пользователя, XSS не достаёт refresh | Дополнительный hop для каждого запроса |

## Решение

1. Браузер обращается только к Nuxt: `POST /api/graphql` (серверный маршрут Nuxt) пересылает
   запрос в API с заголовками пользователя. Адрес API — только в серверной части
   `runtimeConfig`.
2. Refresh-токен — httpOnly, `Secure`, `SameSite=Lax` cookie домена сайта, выставляется
   маршрутом Nuxt после `verifyMagicLink`; в браузерный JS не попадает.
3. Access-JWT (15 минут) хранится в памяти клиента; при SSR Nuxt обменивает refresh на access
   через API и кладёт его в контекст рендера. Обновление — по 401 от API, с ротацией
   (ADR-0009).
4. CSRF: `SameSite=Lax` + проверка `Origin`/`Sec-Fetch-Site` в маршруте Nuxt для мутаций +
   существующий защитный заголовок Yoga. Форм с классической отправкой нет.
5. Выход — маршрут Nuxt вызывает `logout` API и стирает cookie.
6. Публичные запросы (SSR страниц чтения) идут без сессии и кешируются на уровне страниц.

## Следствия

- Появляется `web/server/api/graphql.post.ts` (сейчас папка `web/server` пуста) и обработчики
  входа/выхода; клиент (ADR-0012) настроен на относительный адрес.
- Тесты этапа 0: e2e входа через ссылку, обновление после истечения access, отказ мутации с
  чужого origin.
- Health-эндпоинт API доступен напрямую для мониторинга, не через прокси.

## Цена отката

Низкая: прокси — один файл; переход на прямые запросы потребует cookie на домене API и
`SameSite=None`.
