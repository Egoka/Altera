## 3. Качество проверок и реализации

Положительные факты:

- Все **19/19** слитых PR имеют успешный конечный required `test` в полученном rollup; **16/16** для группы Multica. В рассмотренной истории release отказывался сливать красные #35/#46/#48, а не обходил CI.
- CI действительно ловит дефекты: codegen drift в T-008, TS2322 в T-011, отсутствие LOG_HASH_SECRET в T-086, нестабильность browser tests.
- В [CI PR #49](https://github.com/Egoka/Altera/actions/runs/34974986127): server **72 passed + 1 todo**, web **75 passed**, Playwright **5 passed + 9 skipped**. Число тестов не равно покрытию требований; девять skipped не считать в числителе успешных проверок.
- Отчёты содержат RED/GREEN, ревизии, ограничения Node, отрицательные проверки, отдельные результаты QA/reviewer. T-011 проверял сохранность 4 пользователей, 2 статей и связей на disposable PostgreSQL. T-086 учитывал forged errors, вложенные cause и приватность логов.

Проблемы:

1. **Устойчивость CI:** 27/36 = **75%** успешных workflow Checks во всём срезе; для PR Multica **21/30 = 70%**. Это доля сохранённых workflow run, не вероятность при первом запуске и не число отдельных job attempts. Для 16 веток Multica первый сохранённый Checks успешен у **11/16 = 68,75%**. GitHub rerun одной workflow execution может заменять видимый attempt, поэтому эти цифры не являются полным attempt-level биллингом CI.
2. Из 9 неуспешных Checks: 6 browser navigation/EPIPE/connection failures, 1 codegen drift, 1 typecheck, 1 missing LOG_HASH_SECRET. Два follow-up PR #47/#48 устраняли последствия теста темы уже после первого merge #45.
3. В workflow Checks есть только `pull_request`; нет `push: app`. Поэтому зеленый PR не даёт отдельного факта повторной проверки финального `app`. Branch protection: `strict=false`, required approvals **0**, `enforce_admins=false`. Независимый агент-review есть в Multica, но GitHub его не требует машинно; reviews массив пуст у **19/19** PR. Это не означает отсутствия агентского review.
4. Server smoke использует `__typename` и тестовый DB URL без сервиса PostgreSQL. Такой smoke подтверждает запуск и ответ GraphQL, но не рабочую БД/миграции. Redis service имеет healthcheck, но это не полноценная проверка доступа приложения к Redis.
5. Реальная среда у части исполнителей **Node 24.3.0**, требование проекта **24.12.0**. Локальные отчёты честно отмечают это, CI устанавливает нужную версию. Подготовка среды до первого теста снизит расход на заведомо неисполняемые проверки.
6. В T-005 `migrate deploy` удалён из build. Надо отдельно подтвердить, где теперь применяется миграция при Render deploy. Факт успешной сборки или merge T-011 не доказывает применения новых миграций Neon. Текущая Render-конфигурация в этом аудите не прочитана, поэтому отсутствие миграционного шага не объявляется установленным фактом.

## 4. Критические дефекты финализации

### F1. Done после failed deploy — подтверждённый дефект

T-086: [ALTE-20](https://multica.ai/altera/issues/ALTE-20), PR #41, merge `53ee9b4`. В 04:04:46 UTC переведена в blocked из-за startup crash `LOG_HASH_SECRET is required`.

T-011: [ALTE-19](https://multica.ai/altera/issues/ALTE-19), PR #43, merge `9f93b30`. В 07:10:15 UTC переведена в blocked после deploy `dep-dakesagae00c73d1ej30: update_failed`; release-child ALTE-29 также blocked.

Запуск очереди **15.09 10:00:32 UTC / 13:00:32 МСК**, autopilot run `01a0a482-d486-71cf-acda-5f6171667aa6`, native task `01a0a482-d48a-7078-bd92-fad74c2b5a9a`, выполнил:

- ALTE-29 → Done в 10:13:56 UTC;
- ALTE-20 → Done в 10:13:57 UTC;
- ALTE-19 → Done в 10:14:01 UTC.

В его 97 сохранённых сообщениях нет Render-запроса и нового доказательства deploy recovery. Основание в итоговом output: PR #43 merged, все стадии complete, T-086 завершена по project context. Timeline подтверждает переходы blocked → done.

**2 из 10 закрытых parent с новым результатом (20%) закрыты без доказательства устранения известного release blocker.** Если учитывать child, это три неверно обоснованных изменения статуса. Это дефект принятия решения, даже если пользователь позже отдельно восстановил сервис.

Вероятный путь искажения: документация T-086 объявлена завершённой до release; updater затем повторяет этот статус в project context; очередь доверяет сводке и снимает реальный blocker. Последовательность событий и ссылка закрывающего run на project context поддерживают такую интерпретацию; все внутренние причины решения модели доказать нельзя.

## 5. Эффективность управления

- Из 248 запусков **137 (55,2%)** выполнял оркестратор. Это не всё «пустая работа»: сюда входят admission, планирование, маршрутизация и закрытие, но такой масштаб требует оптимизации.
- В timeline явно записаны **16 no_action**. Их usage: input 8 005; output 22 201; cache read 4 001 401; cache write 223 580. Это измеренный нижний слой избыточных/проверочных вызовов; не всё можно безопасно убрать.
- Recovery понадобился неоднократно: пять recovery-запусков передавали работу дальше; очередь тоже восстанавливала переходы. Система движется благодаря ремонту переходов, а не исключительно за счёт устойчивой событийной цепочки.
- T-092 заняла **40 runs**, T-011 вместе со стадиями **29**, T-009 **25**. Медиана по 12 исполнявшимся задачам с новым результатом/незавершённой реализацией — **15 runs**. Нельзя сравнивать только число runs без сложности задачи: T-112 создаёт skipped сценарии, T-011 меняет модель данных.
- Между Done T-112 (08:26:38 UTC) и стартом T-092 (09:10:06) прошло **43 мин 28 с**; между Done T-092 (11:13:54) и стартом T-087 (12:04:25) — **50 мин 31 с**. Это интервалы native lifecycle, не доказанное время простоя CPU. Правило немедленного взятия следующей готовой задачи исполняется непоследовательно.
- ALTE-24/T-098 оставалась Todo **8 ч 13 мин**. Выбор по наименьшему T-ID без aging может откладывать SEO/документационные задачи неограниченно.
- Один запуск очереди длился по timestamp создания/завершения **64,4 мин**, два — около 30–33 мин. Этот интервал включает ожидание runtime, поэтому нельзя приписывать всё время работе модели. Нужны отдельные queued/started/completed timestamps в мониторинге, max concurrency автопилота и защита от устаревшего snapshot.
- Live-подсказки очереди — **20 780 символов**, recovery — **18 486**, context updater — **2 342**. В них сохранены старые запреты Done и поздние overrides. Приоритет формально объявлен, поэтому это не буквальная логическая неразрешимость, но цена интерпретации и вероятность пропустить исключение выросли. Нужен единый актуальный контракт вместо наращивания префиксов.

T-087 корректно остановлена после двух одинаковых `render_tools_absent_codex`; исходники сохранены. Однако отсутствие read tools обнаружено лишь на release. Полезно проверять capability конкретного runtime заранее и не блокировать создание reviewable PR там, где для него Render-доступ ещё не нужен; deploy acceptance при этом остаётся обязательной для выпуска.

## 8. Критерии качества для дальнейших запусков

Не сводить всё в один балл: высокий throughput не должен компенсировать ложный Done. Следующие три главные метрики и вспомогательные проверки дают понятную картину.

| Метрика | Определение | Срез | Предлагаемая цель |
|---|---|---|---|
| Подтверждённое завершение | Closed parent прошёл CI/review нужной revision, merge, необходимый release, финализацию в app | Минимальная проверка 4/10; два известных release blocker проигнорированы | 100%; ложный Done = 0 |
| Полезный выход | Первые интегрированные результаты по типам: продукт / инфраструктура / тестовая подготовка; отдельно полностью принятые | 11 первых результатов / 17,216 ч = 0,64/ч; сквозная приёмка отстаёт | Расти только при сохранении требований приёмки |
| Ресурсы на принятый результат | Input/output/cache отдельно по типу задачи и сложности; затем стоимость, когда есть billing mapping | Per-task usage в таблице выше; корректной $ оценки нет | Сначала собрать сопоставимую базу, затем снижать медиану; обещать конкретную экономию пока нельзя |

Вспомогательные измерения:

| Контроль | Измерение сейчас | Правило на будущее |
|---|---|---|
| Постановка | 11/11 parent со ссылкой, SHA, AC, scope, deps, authorization | 100% полей + отдельная проверка покрытия результата AC |
| Устойчивость Checks | Multica: 21/30 successful; первый сохранённый run 11/16 веток | Раздельно first-attempt, rerun и repair; причиной failed теста нельзя объявлять «инфраструктуру» без фактов |
| Согласованность статусов | Task-файл совпадает с Done у 5/10 | 100% native ↔ receipt ↔ task-файл ↔ app |
| Доступность usage | 247/247 завершённых runs | 100% terminal runs; unreported отдельно, не ноль |

## 9. Что менять по приоритету

### P0 — достоверность приёмки

1. **Проверяемый finalizer.** Право поставить Done должно зависеть от данных: required checks нужного SHA, независимый verdict с actor/run, MERGED, deploy applicability, подтверждённый deploy/health при необходимости, финализация в app. Сводка проекта и сообщение «всё выполнено» не могут снимать blocker. Добавить отдельный required status для проверенного receipt; formal GitHub approval можно дополнить позже с корректной независимой identity.
2. **Разделить состояние результата.** `code_accepted`, `merged`, `release_pending`, `accepted` — разные факты. Ожидание внешнего выпуска освобождает writer по правилам параллельности, но не превращает parent в Done. Новый release-incident сохраняется при любом обновлении контекста.
3. **До начала backend-задачи проверить runtime capabilities и новые env keys.** Не значения секретов. У каждого runtime отдельно проверить фактическое наличие read-инструментов Render/Neon. Для T-086 необходимый env key известен ещё в плане; подготовка должна предшествовать autodeploy. Разделить доступ, нужный для PR, и доступ, нужный для принятия выпуска.
4. **Сверить реальный Render и migration path** для T-086/T-011, затем исправить статусы и финализацию по фактам. Не перезапускать deploy вслепую и не объявлять текущий сервис сломанным по историческому логу.

### P1 — меньше циклов и токенов

5. **Один актуальный operating contract.** Сжать live prompts, убрать прежние взаимоисключающие редакции, сохранить все действующие правила в одной версии. Короткая инструкция с version/hash; полный контекст — по ссылке и только по необходимости роли.
6. **Детерминированная маршрутизация событий.** Уникальный ключ task+stage+source_run+head+event; проверить дубль и отсутствие изменения до LLM. События «принял, начал» не должны запускать оркестратора. Использовать `issue runs --active`, `comment list --since`, `--roots-only --summary`, затем `--thread --tail`, а не повторное чтение полной переписки.
7. **Сразу брать следующую готовую задачу**, поддерживать запас до трёх; периодическая очередь — страховка. Добавить aging к приоритету, чтобы T-098 не вытеснялась бесконечно. Проверять run-state и writer lock, а не только наличие `in_progress` в списке задач.
8. **Изолировать финализацию.** Не дописывать множество задач в общую долгоживущую ветку. Статусы лучше генерировать из одного receipt/index; одно узкое изменение с CI по фактическому scope, без повторного полного QA неизменённого кода.
9. **Сделать CI стабильным и дешевле в эксплуатации.** Разобрать EPIPE как отдельный дефект harness, сохранять диагностические артефакты при первом падении; ограничить повторы по устойчивой сигнатуре. Кешировать доказательства по SHA+команде+версии среды; новый runtime без зависимостей не должен расходовать попытку продуктового теста.
10. **Управлять ресурсами по классу работы.** Детерминированный bookkeeping — без дорогой модели, сложное review/миграции — с достаточным анализом. Для простой задачи план до ~300 слов, итог ~100–200 слов; для сложной миграции допускается больше по существу. Это ориентиры, не ограничение полноты проверки. Сырые логи хранить артефактом, передавать только ссылку, вывод, exit и изменение относительно предыдущего события.

### P2 — обслуживание

11. Подключить после verified finalization уборку ветки/worktree и ограниченное хранение runtime-артефактов. Не трогать активные/dirty/unmerged каталоги.

## 10. Короткий итоговый receipt задачи

Машинный источник истины должен быть небольшим; исторические stage reports остаются доказательствами, а не конкурирующими итогами.

```yaml
task: T-...
issue: ALTE-...
result: "Одно предложение: что теперь работает"
revision: {base: "...", head: "...", merge: "...", pr: "..."}
acceptance:
  - {ac: AC-1, check: "...", result: passed, evidence: "CI/job/artifact URL"}
review: {actor: "...", run: "...", head: "...", verdict: accepted}
release: {required: true, status: pending, deploy: null, health_evidence: null}
finalization: {commit: null, integrated: false}
usage: {input: 0, output: 0, cache_read: 0, cache_write: 0, unreported_runs: 0}
remainder: "Конкретный остаток или none"
cleanup: {status: pending, reason: "release/finalization not accepted"}
```

Нули в примере — заполняемые поля, не показатели реальной задачи. Для `required: false` нужна конкретная причина по diff; `pending` не преобразуется в `passed`. Human summary: результат, AC/checks, PR/merge, release, остаток, расход. Обычно этого достаточно вместо очередного полного паспорта.
