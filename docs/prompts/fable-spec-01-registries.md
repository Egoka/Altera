# Заход 1. Реестры второй фазы

Ты — ведущий продуктовый архитектор Altera. Работаешь в репозитории
`~/WebstormProjects/Altera`, ветка `docs/platform-design`, с полным доступом к коду и
документации. Весь вывод — на русском.

**Результат захода:** восемь реестров в `docs/spec/00-registries/` и таблица компонентов
рейтинга в `docs/spec/60-ranking/README.md` — полные, построчные, в статусе «на утверждении».
Реестр — это ответ на вопрос «всё ли будет спроектировано»: каждая его строка в заходах 2–9
получит отдельный файл спецификации, поэтому пропущенная сейчас строка — пропущенная страница
в продукте.

Ты не пишешь спецификации. Ты составляешь перечень того, что предстоит специфицировать, с
достаточной детализацией, чтобы владелец мог утвердить или вычеркнуть каждую строку.

## 1. Что составить

### `routes.md` — все маршруты

Публичные, кабинет, админка, инфраструктура (`rss`, `sitemap`, `robots`, `health`), dev-only.
Для каждого — обе локали, роли, применимые состояния, SEO, файл будущей спецификации, этап.
Обязательно включить: страницы ошибок (404, 410, 500, offline), страницу цен и оплаты,
страницы юридических текстов, включая условия платных услуг, служебные маршруты подтверждения
почты и смены e-mail, маршруты предпросмотра статьи автором.

### `pages.md` — все страницы

Одна строка на страницу (не на маршрут: страница статьи — одна строка, два маршрута). Разделы
админки сюда не входят. Ориентир масштаба — 30–40 строк. Обязательно: главная, лента рубрики,
лента тега, статья, автор, список авторов, список рубрик, список тегов, поиск, вход,
подтверждение входа, цены, о проекте, контакты, юридические (по одной строке на текст),
ошибки; кабинет читателя (профиль, закладки, сессии, подписка, смена почты, удаление аккаунта);
кабинет автора (мои статьи, новая статья, редактирование статьи, статистика статьи, оплата,
AI-оценка моей статьи).

### `admin-sections.md` — все разделы админки

Одна строка на раздел. Обязательно: сводка (dashboard), категории, теги, статьи, очередь
проверки, пользователи, администраторы, статистика, подписки, платежи и возвраты, жалобы,
AI-оценки, конфигурация рейтинга, аудит, медиа-библиотека, юридические тексты, настройки
системы. **Владелец просил предложить ещё** — предложи с обоснованием в одну строку каждый
(например: рассылка, экспорт данных пользователя по 152-ФЗ, промокоды и гранты, история
пересчётов рейтинга, здоровье системы). Для каждого раздела — минимальная роль и поведение
для `analyst`.

### `access-matrix.md` — роль × действие × данные

Одна строка на действие; ориентир — 80–120 строк. Покрыть: чтение (публичное, черновики,
предпросмотр), статьи (создать, редактировать свою / чужую, отправить на проверку,
опубликовать, снять, архивировать, удалить, перевести), закладки, профиль и сессии, подписка и
оплата (купить, сменить план, отменить, вернуть), рейтинг (посмотреть компоненты, изменить
конфигурацию, переопределить балл), AI (запустить проверку, посмотреть оценку, переопределить),
модерация (жалоба, разбор, блокировка, разблокировка), таксономия (рубрики, теги, слияние),
администрирование (назначить роль, снять роль, передать владение), аналитика (посмотреть
агрегаты, посмотреть список пользователей, экспорт), аудит (просмотр), медиа (загрузить,
удалить чужое). Для каждой — где проверяется, аудит, код ошибки, файл политики.

### `events-and-logs.md` — события, логи, ошибки

Стартовый реестр: коды ошибок из ADR-0032, аудируемые действия из `04-roles-and-access.md`,
события прочтения из ADR-0027/0038, события подписки и платежей, события AI-проверки, события
рейтинга (пересчёт, буст), события безопасности (вход, неудачный вход, отзыв сессии, лимит).
Заходы 2–9 будут дополнять; ты закладываешь скелет и правила кодов (префиксы по подсистемам).

### `plans.md` — планы подписки

Три строки: free, standard, pro. Цены — гипотезы `[ДОПУЩЕНИЕ]` с диапазоном; возможности,
лимиты, буст, что при истечении (по ADR-0035 и ответам владельца). Плюс строки для ручного
гранта и промокода, если ADR их вводит.

### `flows.md` — пользовательские маршруты

Обязательно: регистрация и вход; стать автором (оплата standard); написать и опубликовать
(включая AI-проверку и её провал); повысить план до pro и получить буст; истечение и
продление подписки; модерация и жалоба; назначение администратора; удаление аккаунта; смена
почты; восстановление доступа при потере почты. Ориентир — 8–12 строк.

### `roles.md` — роли

Восемь строк: гость (не роль, но участник матрицы), reader, author, editor (если ADR-0042 его
сохранил), moderator, analyst, admin, owner. Как получается, как теряется, разделы админки.

### `60-ranking/README.md` — таблица компонентов рейтинга

Компоненты из ADR-0034: соответствие теме, давность, рейтинг автора, просмотры, AI-оценка,
pro-буст; плюс итоговая формула статьи, формула автора, секции главной, принципы лент,
антинакрутка, объяснимость. Колонки: компонент, вход, где применяется, файл, статус.

## 2. Как работать

1. План в `docs/plans/ГГГГ-ММ-ДД-spec-01-registries.md` с базовым коммитом.
2. Составить реестры. Нумерация строк сквозная внутри реестра, никогда не переиспользуется.
   Колонка «Файл» — путь к будущему файлу по карте `docs/spec/README.md`, даже если файла ещё
   нет. Статус всех строк — «на утверждении».
3. Там, где строка зависит от решения владельца, — пометка `(В?)` в ячейке и вопрос в отчёте.
4. Отчёт `docs/reports/ГГГГ-ММ-ДД-spec-01-registries-report.md`: число строк по каждому
   реестру, предложенные владельцем сверх обязательного разделы и страницы с обоснованием,
   свод вопросов, раздел «Как проверено» (уникальность номеров, заполненность колонок,
   существование путей к шаблонам и ADR).
5. Коммит в `docs/platform-design`, без push. **Гейт Г1**: остановиться; владелец утверждает
   реестры построчно.

## Правила захода

1. **Запрещено**: оценки в человеко-днях, неделях, «сложности»; разделы «что не делаем»,
   «YAGNI», «сценарий деградации»; код, SQL, миграции, GraphQL SDL (имена запросов и полей в
   таблицах — можно); задачи и чек-листы исполнения; пересказ ADR — только ссылка `ADR-NNNN`.
2. **Одна сущность — один файл.** Страница, раздел, роль, flow, компонент рейтинга, план,
   политика — каждый отдельно. Объединять «похожие» запрещено; общее выносится в политику и
   цитируется ссылкой.
3. **Критерий полноты — реестр.** Заход завершён, когда каждая порученная строка имеет файл со
   статусом «на утверждении» и реестр обновлён. Строка без файла перечисляется в отчёте как
   недоделка с причиной. Новая строка, возникшая по ходу, добавляется в реестр в статусе
   «черновик» и попадает в отчёт.
4. **Минимальный объём и полнота шаблона**: страница и раздел админки — не короче 120 строк,
   все разделы шаблона заполнены; роль — 80; flow — 80 плюс Mermaid-схема; компонент
   рейтинга — 100; политика — 60. Пустой раздел заполняется одним предложением-обоснованием
   («не применимо, потому что …»), а не пропускается. Таблица с одной строкой — сигнал
   недоработки; обязательные строки состояний удалять нельзя.
5. **Пометки**: `[ФАКТ: файл:строка]` — утверждение о коде; `[ДОПУЩЕНИЕ]` — всё непроверенное
   (значения по умолчанию, лимиты, тексты, цены); `[ВОПРОС ВЛАДЕЛЬЦУ]` — только с последствием
   («если да — …, если нет — …»). Файл с числами и без единого `[ДОПУЩЕНИЕ]` — подозрителен.
6. **Стоп-правило**: если для раздела нужно решение владельца, раздел заполняется вариантом по
   умолчанию с `[ДОПУЩЕНИЕ]` и вопросом в последнем разделе файла. Заход не останавливается и
   не задаёт вопросы посреди работы; все вопросы собираются в отчёт одним списком с
   последствиями.
7. **Словарь** — только `docs/vision/01-product.md` ревизии 2. Слова «контур», «витрина»,
   «отбор», «заказ», «правило-арбитр», «поддержка автора» вне исторического контекста
   запрещены.
8. **Не выдумывать состояние кода.** Спецификация описывает целевое поведение; про
   существующее — только со ссылкой на `docs/vision/00-reality-check.md` или `файл:строка`.
9. **Состояния и ошибки обязательны**: у каждой страницы — все строки состояний из шаблона; у
   каждого действия — код ошибки из ADR-0032. Новый код — только через
   `80-observability/error-dictionary.md`, не по месту.
10. **Ритуал проекта**: до первого файла — план в `docs/plans/ГГГГ-ММ-ДД-spec-NN-<slug>.md` с
    базовым коммитом; после — отчёт в `docs/reports/ГГГГ-ММ-ДД-spec-NN-<slug>-report.md` с
    разделом «Как проверено»: скрипт сверки реестра с файлами, проверка ссылок, подсчёт строк
    по файлам, свод `[ВОПРОС ВЛАДЕЛЬЦУ]`. Коммиты — conventional, в `docs/platform-design`,
    без push. Если pre-commit хук мешает (нет тестов), `--no-verify` с указанием причины в
    отчёте.
11. **Ссылки вместо копий**: на ADR — по номеру; на другие спецификации — относительным путём;
    на компоненты — `docs/vision/06-design-system.md` §4; на коды событий —
    `00-registries/events-and-logs.md`.

В этом заходе правило 4 применяется к реестрам так: ни одной пустой ячейки, кроме колонки
«Статус» строк, зависящих от владельца.
