Да, Егор. Ты нашёл описание одного из главных механизмов coding-агентов. Но самое интересное начинается не с четырёх шагов, а с вопроса: **как устроить этот цикл так, чтобы агент действительно решал задачу, а не просто долго и убедительно работал?**

Здесь полезно разделить две вещи: **agent loop как устройство программы** и **практику управления этим циклом при разработке**. Первое объясняет, как агент действует. Второе — как получать от него проверяемый результат.

## 1. Что в найденном определении верно, а что стоит уточнить

Суть верная: агент получает задачу, выбирает действие, получает результат и на его основе выбирает следующий шаг. Ключевое отличие от заранее запрограммированного сценария — **последовательность действий не полностью определена разработчиком: модель выбирает её по ходу работы**. Именно так Anthropic проводит границу между фиксированными workflows и агентами. ([Anthropic][1])

Однако есть несколько важных уточнений.

**«Модель сама решает, когда остановиться» — только часть картины.** Она может решить, что пора ответить пользователю. Но исполнение также контролируют ограничения приложения: разрешения на действия, лимиты, ошибки, отмена пользователем. В Agent SDK, например, предусмотрены отдельные ограничения на число инструментальных проходов и расходы. ([Claude Platform][2])

**Perceive → Reason → Act → Observe — удобная учебная схема, а не обязательный стандарт из четырёх отдельных вызовов модели.** В документации Claude Code тот же процесс описан тремя фазами: сбор контекста, действие, проверка результата. Фазы могут смешиваться: чтение файла одновременно является действием и сбором информации. ([Claude][3])

**Одна сессия — не обязательно один цикл.** Внутри разговора может быть много пользовательских запросов, каждый из которых запускает новую последовательность действий. Причём терминология различается: в описании Codex один *turn* может включать много обращений к инструментам, а в Claude Agent SDK слово *turn* используется для более мелкого прохода внутри исполнения. Поэтому число «итераций» нельзя сравнивать между продуктами без уточнения. ([OpenAI][4])

И ещё: агентный цикл не является изобретением вайбкодинга. Один из важных исследовательских предшественников — **ReAct**, работа 2022 года о чередовании рассуждения и действий с получением информации из внешней среды. Это не React-фреймворк. ([arXiv][5])

## 2. Где заканчивается модель и начинается агент

Полезно держать в голове такую формулу:

**Агент = модель + инструменты + состояние + управляющая среда.**

Последнюю часть обычно называют **harness**: это программная обвязка, которая организует выполнение. OpenAI описывает её как систему, управляющую контекстом, инструментами, состоянием разговора, разрешениями и ходом работы. ([OpenAI Developers][6])

### Модель предлагает действие, но не выполняет его непосредственно

Предположим, агент решил прочитать компонент.

Модель формирует примерно такой запрос:

```json
{
  "tool": "read_file",
  "arguments": {
    "path": "src/components/Select.vue"
  }
}
```

Это ещё не чтение файла. Это **структурированное предложение вызвать инструмент**.

Приложение получает запрос, проверяет его и вызывает соответствующую функцию. Затем результат возвращается модели. Такой обмен `tool_use → выполнение → tool_result` прямо описан в документации инструментальных вызовов Claude. ([Claude Platform][7])

Поэтому модель, которая пишет в чате «я запустил тесты», и система, которая действительно вызвала процесс и получила его вывод, — принципиально разные вещи.

### Ядро цикла может быть довольно простым

Ниже учебный псевдокод, не API конкретной библиотеки:

```ts
while (budget.hasCapacity()) {
  const context = buildContext(task, state);

  const reply = await callModel(context, availableTools);
  state.history.push(reply);

  if (reply.toolCalls.length === 0) {
    return {
      status: "turn-ended",
      message: reply.text
    };
  }

  for (const call of reply.toolCalls) {
    const result = await executeUnderPolicy(call);

    state.history.push(
      toolResult(call.id, result)
    );
  }
}

return { status: "budget-exhausted" };
```

Обрати внимание: здесь возвращается **`turn-ended`, а не `task-successfully-completed`**.

Вызов модели закончился. Это ещё не доказывает, что задача выполнена.

А за условным `executeUnderPolicy` скрывается значительная инженерная работа: проверка аргументов, разрешения, исполнение, таймауты, обработка ошибок. В реальном SDK один ответ модели также может запрашивать несколько инструментов, а порядок их исполнения зависит от реализации. ([Claude Platform][2])

Сам по себе этот цикл — не дообучение модели на твоём проекте. В описанной схеме происходят последовательные вызовы модели с обновляемым контекстом; меняются история, наблюдения и файлы, а не обязательно веса нейросети. ([OpenAI][4])

## 3. Почему обратная связь важнее бесконечного «подумай ещё»

Представь два подхода к исправлению ошибки.

**Первый:** модель читает описание и долго рассуждает, как должен работать компонент.

**Второй:** модель читает описание, запускает воспроизведение, получает ошибку, проверяет конкретную гипотезу и исправляет код.

Во втором случае появляется информация, которую невозможно получить просто дополнительным размышлением над первоначальным запросом. Именно взаимодействие с внешними источниками и средой является центральной идеей ReAct. ([arXiv][5])

Для разработки я бы сформулировал это так:

> Рассуждение выбирает проверку. Проверка даёт данные. Данные позволяют пересмотреть рассуждение.

Например, исходная гипотеза: «Событие не срабатывает из-за неправильного обработчика».

После запуска теста выясняется: обработчик вообще не смонтирован, потому что компонент находится в другом состоянии.

Ещё десять минут размышления о первоначальном обработчике могли бы не помочь. Один правильно выбранный эксперимент изменил направление работы.

**Мой критерий полезной итерации:** после неё должно произойти хотя бы одно из трёх — стало меньше неизвестного, появилась нужная часть решения или проверилось важное предположение.

Поэтому много действий — ещё не прогресс. Повторить тест бывает полезно для проверки нестабильности. Но десятый одинаковый запуск без изменений и без новой диагностической цели — уже повод вмешаться.

## 4. Как выглядит хороший цикл на примере FishtVue

Возьмём учебную задачу для твоей библиотеки — **это пример, не утверждение о существующем баге в репозитории**:

> В `Select` клавиатурная навигация позволяет выбрать отключённую опцию. По контракту нашей задачи отключённые опции нужно пропускать, а Enter не должен их выбирать.

### Сначала агент устанавливает факты

Я бы ожидал, что он найдёт реализацию, прочитает существующие тесты, проверит представление отключённой опции и разберётся, как устроены активный пункт, выбранное значение и фокус.

Одновременно он выясняет реальные команды проекта, а не предполагает, что любой репозиторий запускается через `npm test`.

Здесь правильный результат первой части — не код, а достаточно точное понимание контракта:

> «Навигация управляет активным пунктом отдельно от выбранного значения. Исправление должно сохранять это разделение».

### Затем появляется воспроизведение

Для этой задачи я бы задал тестовый сценарий:

```text
Есть три опции:
A — доступна
B — отключена
C — доступна

Активна A.
Пользователь нажимает ArrowDown.
Ожидается: активна C, а не B.
```

Агент добавляет регрессионный тест и убеждается, что он падает на исходной реализации **по нужной причине**.

Это важное различие. Ошибка импорта, отсутствующий mock или незапущенное окружение не являются воспроизведением бага навигации.

### Исправляется минимально необходимая часть

После подтверждения причины агент меняет алгоритм перехода между опциями.

Здесь возникает дополнительный вопрос: что произойдёт, когда отключены все опции? Если алгоритм просто ищет следующую доступную по кругу, он может никогда её не найти.

Хороший следующий шаг — проверить этот граничный случай, а не считать первое зелёное воспроизведение достаточным.

### Проверка расширяется постепенно

Для такого изменения я бы ожидал проверку движения в обе стороны, пустого списка, полностью отключённого списка и невозможности выбора отключённой опции через Enter.

Затем — существующие тесты компонента и связанные проверки проекта.

При этом успешная проверка логики навигации не отвечает автоматически на вопрос, правильно ли ведёт себя реальный браузерный фокус. Поэтому отдельный браузерный сценарий может быть необходимой частью приёмки. Anthropic отдельно описывает случаи, когда агент проходил локальные проверки, но не замечал неработающую сквозную функциональность веб-приложения до проверки через браузер. ([Anthropic][8])

### В конце нужны доказательства

Не:

> «Всё исправил, теперь работает корректно».

А примерно:

> «Добавлен тест, воспроизводивший выбор отключённой опции на исходной реализации. После исправления он проходит. Проверены такие-то граничные случаи. Запущены такие-то команды. Браузерная проверка фокуса не выполнялась».

Последняя фраза не делает отчёт хуже. Она показывает границу доказанного.

## 5. Самое важное различие: остановка и приёмка результата

Я бы разделял завершение на три уровня.

### Уровень модели: «мне больше нечего делать»

Модель выдаёт завершающий ответ. Она может быть права, ошибаться или не иметь доступа к необходимой проверке.

### Уровень выполнения: «этот запуск закончился»

Сработал лимит, возник блокер, потребовалось решение человека или пользователь остановил работу. Это не обязательно неудача: иногда остановиться и сообщить о препятствии — правильное поведение.

### Уровень приёмки: «результат соответствует требованиям»

Проверены оговорённые условия: воспроизведение исправлено, нужные сценарии работают, ограничения соблюдены, изменения просмотрены.

В материалах по оценке агентов Anthropic отдельно различает **текстовый отчёт агента** и **реальное итоговое состояние среды**. Это полезное различие: проверять следует не только то, что агент сообщил, но и то, что действительно произошло. ([Anthropic][9])

Отсюда важный практический принцип:

> **Фраза «готово» — заявление о результате. Проверка — основание его принять.**

Особенно осторожно нужно относиться к ситуации, когда агент одновременно пишет реализацию, пишет тесты и сам решает, достаточно ли этих тестов.

В примере с `Select` он мог бы «исправить» красный тест, изменив ожидаемое значение на неправильное. Формально тест стал зелёным, но исходное требование исчезло.

Поэтому я бы фиксировал критерии приёмки заранее, требовал объяснять изменения существующих проверок и выносил критичные проверки в отдельный контролируемый этап.

И не задавал бы единственным ограничением «работай, пока всё не станет зелёным»: у цикла должны быть разрешённый объём работ, бюджет и условия остановки при отсутствии прогресса.

## 6. Контекст и память: что агент действительно «знает»

**Доступ к репозиторию не равен постоянному присутствию всего репозитория в контексте модели.**

На конкретном шаге решение принимается на основании того, что приложение передало в модель: инструкций, истории, прочитанных фрагментов, результатов инструментов и других включённых данных. В Claude Code контекст также включает загруженные правила и навыки. ([Claude][3])

Отсюда три разных вида состояния.

**Рабочий контекст** — то, что доступно модели сейчас.

**Состояние среды** — реальные файлы, процессы, Git, результаты сборки.

**Сохранённая память** — документы, планы и заметки, которые можно прочитать позднее.

Их нельзя считать взаимозаменяемыми. Запись в плане «тесты прошли» может устареть после следующего изменения файла.

### Почему длинная сессия не обязательно лучше

По мере работы контекст заполняется прочитанными файлами, выводом команд и историей неудачных гипотез. Для продолжения используются сжатие истории, выборочное получение информации и сохранение заметок. Anthropic подчёркивает, что при слишком агрессивном сжатии можно потерять важные детали. ([Anthropic][10])

Поэтому я бы не пытался бесконечно поддерживать одну гигантскую беседу.

Для длительной задачи полезнее оставить понятную передачу состояния:

```text
Цель:
Исправить навигацию Select без изменения публичного API.

Подтверждено:
Регрессионный тест воспроизводит проблему на исходном коде.

Сделано:
Изменён поиск следующей доступной опции.

Осталось:
Проверить браузерный фокус и связанные сценарии.

Важное решение:
Активная опция и выбранное значение остаются разными состояниями.
```

В реальном файле я добавил бы конкретные пути, команды, результаты и привязку к проверенной версии кода.

Это близко к подходу Anthropic для длительных задач: последовательная работа над небольшими частями с сохранением прогресса и артефактов для следующего запуска. ([Anthropic][8])

**Полезная память агента — не пересказ всех разговоров, а актуальное состояние задачи и причины важных решений.**

## 7. Где здесь AGENTS.md, Skills, MCP, Hooks и subagents

Эти сущности не заменяют agent loop. Они подключаются к разным его частям.

| Механизм            | Что даёт циклу                              | Пример для твоей разработки                |
| ------------------- | ------------------------------------------- | ------------------------------------------ |
| **Правила проекта** | Постоянные инструкции и ограничения         | Использовать pnpm, сохранять публичный API |
| **Skill**           | Повторяемую методику и справочные материалы | Порядок тестирования Vue-компонента        |
| **MCP**             | Подключение инструментов и данных           | Доступ к issue, документации или браузеру  |
| **Hook**            | Обработчик события жизненного цикла         | Запустить проверку после изменения         |
| **Subagent**        | Отдельного исполнителя со своим контекстом  | Исследовать зависимости компонента         |

Такое разделение прямо отражено в документации расширений Claude Code. В частности, skill — это знания или процедура, а subagent — отдельный выполняющий работу контекст. Hook запускается на событии, но его обработчиком может быть не только скрипт, поэтому «hook» не всегда означает полностью детерминированное решение. ([Claude][11])

Для Codex правила проекта можно задавать через `AGENTS.md`: приложение собирает инструкции с учётом их расположения и области действия. ([OpenAI Developers][12])

Важный вывод: **написать правило и технически обеспечить его соблюдение — разные задачи**.

«Не публикуй пакет» в инструкции — указание модели. Отсутствие доступа к публикации без отдельного разрешения — ограничение возможностей системы.

## 8. Внутренний цикл, внешний workflow и несколько агентов

Здесь часто смешивают разные уровни автоматизации.

### Внутренний цикл: выполнить текущую задачу

Прочитать файл → изменить → запустить проверку → исправить.

### Цикл достижения цели: проверить, действительно ли готово

Исполнитель закончил → отдельная проверка обнаружила невыполненный критерий → исполнитель получил конкретную обратную связь → продолжил.

### Внешний процесс: выбрать следующую работу

Задача принята → выбирается следующая задача → запускается новый исполнитель.

В актуальном разборе Anthropic отдельно рассматриваются циклы, запускаемые запросом, ориентированные на достижение цели и запускаемые по времени. Это разные способы управлять началом и окончанием работы, а не просто разные названия одного `while`. ([Claude][13])

Для инженерной работы мне нравится сочетание:

> **Предсказуемый внешний процесс, адаптивный агент внутри каждого этапа.**

Например:

```text
Исследование → согласование плана → реализация → проверка → ревью
```

На этапе исследования агент сам выбирает, что читать. На этапе реализации — как локально исправлять ошибки. Но переход к изменению публичного API или публикации требует отдельного решения.

Это сочетает гибкость агента с управляемостью workflow. Само различие между фиксированными и динамически выбираемыми путями исполнения описано в Building effective agents. ([Anthropic][1])

### Как здесь помогает Plan Mode

Твой подход «сначала хорошее ТЗ и план, потом выполнение» хорошо подходит для такого разделения.

В плане я бы требовал не столько перечень будущих файлов, сколько ответы: какой контракт сохраняем, что пока неизвестно, как проверим результат, какие изменения выходят за границы задачи.

Разделение исследования, планирования и реализации также рекомендуется в документации Claude Code. ([Claude][14])

### Когда полезны несколько агентов

Для FishtVue я бы сначала разделял **исследование и проверку**, а не запускал нескольких исполнителей править один компонент.

Один исследует реализацию, второй — существующие тесты и контракт, основной агент объединяет выводы. После исправления отдельный проверяющий пытается найти нарушение требований.

При этом отдельное окно контекста не делает проверяющего непогрешимым. Я бы давал ему исходную задачу и diff, а не только уверенный пересказ исполнителя.

Для параллельных изменений нужны отдельные рабочие области и последующая совместная проверка. Claude Code, например, документирует использование Git worktrees для параллельных сессий. ([Claude][3])

## 9. Как распознавать плохой цикл

Я бы следил прежде всего за четырьмя признаками.

**Действия повторяются, но знание не меняется.** Агент снова читает те же файлы и возвращает предыдущие правки. Здесь полезно потребовать краткий отчёт: что установлено, какие гипотезы отвергнуты и чем следующая проверка отличается от предыдущей.

**Меняется цель вместо реализации.** Появляются пропуски тестов, ослабленные проверки, отключённые правила или моки, скрывающие проверяемое поведение. Иногда такие изменения оправданы, но они должны объясняться исходным контрактом, а не желанием получить зелёный вывод.

**Ошибка среды лечится правками продукта.** Например, тесты не запускаются из-за зависимости, а агент уже меняет бизнес-логику. Я бы требовал сначала классифицировать препятствие: код, тест, окружение или неоднозначное требование.

**Задача разрастается.** Исправление навигации превращается в переработку архитектуры формы. Здесь помогает заранее заданная граница: необходимые изменения выполняются, соседние улучшения фиксируются отдельно.

Для работы без постоянного наблюдения я бы ввёл правило: после нескольких повторов одной ошибки без новой информации — остановка с диагностическим отчётом. Конкретное число, например три, является настройкой процесса, а не универсальным стандартом.

### Безопасность — тоже часть качества цикла

Внешняя страница, issue или прочитанный файл могут содержать инструкции, пытающиеся перенаправить агента. Это класс риска, называемый **prompt injection**. Полученные данные нельзя автоматически считать разрешением на новые действия. ([Claude][15])

Поэтому реальная автономность должна опираться на ограниченные права. В Codex документация отдельно разделяет sandbox — что технически доступно — и approval policy — когда требуется подтверждение. ([OpenAI Developers][16])

Для coding-агента я бы по умолчанию оставлял локальные правки и проверки внутри проекта, а публикацию, работу с production и опасные внешние изменения отделял разрешениями.

**Git-ветка помогает управлять кодом, но не заменяет sandbox.** И отмена файлов не отменяет уже выполненное внешнее действие: например, изменение удалённой базы. Документация Claude Code прямо предупреждает об этой границе checkpoints. ([Claude][3])

## 10. Как оценивать эффективность, а не впечатление от работы

Плохой показатель — «агент работал долго и сделал много шагов».

Я бы оценивал, удалось ли принять результат, сколько потребовалось вмешательств, появились ли регрессии и сколько времени заняло ревью.

Для наблюдения нужен **trace — журнал выполнения**: вызванные инструменты, их результаты, изменения и причина остановки. При оценке агентов важно также повторять задачи: один успешный запуск не показывает устойчивость поведения. Эти принципы описаны в материале Anthropic об evals. ([Anthropic][9])

Для твоего рабочего процесса я бы просил в итоговом отчёте:

> «Что изменено, какие проверки действительно выполнены, на какой версии кода, что осталось непроверенным и почему работа остановлена».

Это полезнее длинного рассказа о том, насколько тщательно агент размышлял.

### Стоимость нужно считать на принятую задачу

Моя рабочая формула:

```text
Стоимость принятой задачи =
расходы всех попыток
+ инфраструктура
+ время проверки и исправлений человеком
```

Из неё следует, что более дешёвый отдельный вызов модели не обязательно означает более дешёвую задачу. Если он приводит к многочисленным неудачным попыткам и сложному ревью, экономия может исчезнуть.

В длинных циклах имеет значение повторное использование контекста. Prompt caching позволяет переиспользовать вычисления для совпадающего префикса запроса. Но это не кэш готового ответа: модель всё равно генерирует новый ответ, и одинаковые запросы не гарантируют одинаковый результат. ([OpenAI Platform][17])

При сравнении настроек я бы использовал несколько типовых задач FishtVue с одинаковыми начальными версиями репозитория и критериями приёмки. Сравнивал бы не только модели, но и весь процесс: инструменты, правила, проверки и степень необходимого участия.

## 11. Что такое harness engineering на практике

Это следующий уровень после «я научился писать промпты».

Ты организуешь репозиторий и окружение так, чтобы агенту было легче получать правильную информацию и труднее незаметно нарушать ограничения.

Например, для FishtVue я бы предложил такую структуру:

```text
AGENTS.md

docs/
  architecture.md
  testing.md
  component-contracts/
  plans/
    active/
    completed/
```

В `AGENTS.md` — краткие правила и указатели. В `testing.md` — реальные команды, допустимые моки, способы проверки компонентов. В планах — решения и текущий прогресс.

Это согласуется с подходом OpenAI: использовать `AGENTS.md` как карту знаний, а не превращать его в огромную энциклопедию; подробные материалы и планы хранить структурированно в репозитории. ([OpenAI][18])

Далее я бы переводил повторяющиеся замечания в проверки.

Если агент регулярно нарушает определённое ограничение импортов, не только дописывать «будь внимательнее», а сделать нарушение обнаруживаемым линтером или тестом.

**Хороший harness превращает часть человеческой внимательности в воспроизводимую обратную связь.**

Поэтому различия между coding-продуктами не сводятся к выбранной модели. Например, Cursor прямо описывает свой агент как сочетание модели, инструкций и инструментов, которые продукт согласует между собой. ([Cursor][19])

## 12. Шаблон задания для управляемого agent loop

Для твоего подхода с предварительным планом я бы использовал такую основу:

```text
Задача:
[Описание требуемого изменения.]

Сначала исследуй задачу без изменения файлов.

Установи:
— текущее поведение и ожидаемый контракт;
— затрагиваемые части проекта;
— существующие способы проверки;
— неизвестные и риски.

Предложи план и критерии приёмки.
Дождись моего подтверждения перед реализацией.

После утверждения плана:

1. Для исправления ошибки сначала получи воспроизведение.
   Убедись, что проверка падает по нужной причине.

2. Вноси минимальные необходимые изменения.
   Сохраняй публичный API и оговорённые ограничения.

3. Запускай релевантные проверки.
   Используй реальные команды из конфигурации проекта.

4. Анализируй результат каждого неудачного подхода.
   Следующая попытка должна учитывать полученные данные.

Не ослабляй существующие проверки ради зелёного результата.
Не подменяй тестируемую логику моками.
Не расширяй задачу соседними улучшениями без согласования.
Не публикуй пакет и не выполняй внешние изменения
без отдельного поручения.

Если несколько попыток повторяют одну ошибку
и не дают новой информации, остановись и опиши блокер.

В финале сообщи:
— что изменено;
— какие критерии приёмки подтверждены;
— какие команды выполнены и с каким результатом;
— что осталось непроверенным;
— какие риски сохраняются.
```

Этот текст задаёт процесс, но технические права и жёсткие лимиты нужно настраивать в среде исполнения, а не только описывать словами. ([OpenAI Developers][16])

### Главное, что стоит вынести

**Agent loop — это делегирование не только написания кода, но и выбора следующих действий.**

А твоя роль при этом смещается: меньше указывать каждое движение, больше определять контракт, границы работы и способы проверки.

Для FishtVue цель я бы формулировал не как «пусть агент самостоятельно работает как можно дольше», а так:

> **Пусть он самостоятельно доводит небольшое изменение до проверяемого состояния, сохраняет ограничения проекта и возвращает доказательства результата.**

Это уже управляемая инженерная практика, а не надежда, что достаточное количество итераций само превратится в качество.
