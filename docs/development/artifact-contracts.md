# Контракты артефактов разработки

- **Статус**: принят как контракт M3 2026-09-13. Примеры ниже — шаблоны, не evidence;
  техническое enforcement полей относится к M4.
- **Совместимость**: сохраняют обязательные поля существующих планов/отчётов и задач.

## 1. Паспорт задачи перед реализацией

```yaml
task: T-NNN либо ссылка на прямое поручение владельца
multica_issue: ALTE-N либо неприменимо
goal: проверяемый результат
contract_sources: пути и разделы журнала/spec/ADR
baseline_commit: полный SHA
baseline_tree: clean либо dirty fingerprint со ссылкой на diff и SHA-256 файлов
scope: разрешённые файлы и поведение
preserved_contract: API, данные, роли, пользовательские сценарии
dependencies: ID и evidence закрытия
authorization: источник уже данного разрешения и границы
acceptance: список AC-N с наблюдаемым результатом
unknowns: факты для исследования отдельно от решений владельца
stages: участники, вход и выход каждой обязательной стадии
```

Паспорт дополняет существующую задачу, не создаёт альтернативное ТЗ. Критерии берутся
из исходного контракта; изменение сохраняется с причиной и согласованием при необходимости.

## 2. Evidence одной проверки

```yaml
task: T-NNN
stage: тестирование
run: native ID или ID локальной сессии
actor: проверяющий
criterion: AC-N
check_id: стабильное имя проверки, одинаковое между попытками
baseline_commit: полный исходный SHA из паспорта
revision_commit: полный SHA проверяемого кода
dirty_fingerprint: clean либо ссылка на diff и SHA-256 затронутых файлов
cwd: каталог запуска
environment: версии Node/pnpm/runner и безопасные сведения об окружении
command: точная выполненная команда
started_at: время с часовым поясом
exit_code: фактический код
executed: фактическое число тестов/сценариев, если применимо
result: passed / failed / blocked / not_run / not_applicable
output: путь к значимому выводу или артефакту
trace_ref: ссылка на native trace или очищенный журнал tool call/result этого run
limits: что эта проверка не доказывает
```

`not_applicable` требует причины от контракта; `not_run` не заменяется `passed`.
Для браузера сохраняются URL, действия, ожидаемый и наблюдаемый результат, версия приложения
и артефакт. Для документации — перечень сверенных источников, ссылок и изменений смысла.
В отчёт не копируются секреты, токены, пользовательские данные или полный шумный лог.

Общий trace связывает вызовы инструментов и их результаты, изменения среды и причину
остановки с run и ревизией. Предпочтительна ссылка на доступную историю runner; если
экспорта нет, сохраняется очищенный журнал существенных действий и явно называется
ограничение полноты. Следующий reviewer должен суметь открыть trace без прежнего чата.

## 3. Неуспех и передача состояния

```text
Цель / T-NNN / ALTE-N / стадия / исполнитель:
Ветка, HEAD, состояние дерева, изменённые файлы и diff:
Подтверждено (ссылки на evidence):
Сделано:
Осталось:
Причины принятых решений / сохраняемые ограничения:
Отвергнутые гипотезы и результаты:
check_id → число последовательных неуспехов:
Причина остановки (код / тест / среда / контракт / конфликт / права / бюджет / отмена):
Наблюдаемое условие возобновления:
Как проверено отсутствие активного дубликата:
Следующий разрешённый шаг:
```

Счёт двух неуспехов хранится в истории стадии, не только в памяти процесса.
Положительная проверка сбрасывает только свой счёт. Нельзя перезапуском стереть блокер.
Handoff нового run проверяется против реальных файлов и процессов до продолжения.

Native outcome отдельного run (`success / failed / blocked / cancelled / unknown`), outcome
стадии (`завершена / возвращена / остановлена / не начиналась`) и acceptance задачи
(`принято / вернуть / не проверено`) записываются раздельно. Значение одного поля нельзя
выводить из другого.

## 4. Независимая приёмка и итог

| Поле          | Требование                                                                 |
| ------------- | -------------------------------------------------------------------------- |
| Вход          | Первичное поручение/задача, критерии, все источники, точный diff, evidence |
| Независимость | Reviewer и его run не создавали проверяемую реализацию                     |
| Ревизия       | SHA; при dirty tree также diff и хэши                                      |
| Критерии      | Каждый AC-N: подтверждён / нарушен / не проверен, ссылка на основание      |
| Ограничения   | Отсутствующая среда, skipped tests, непроверенная интеграция               |
| Вердикт       | принято / вернуть / не проверено; причина и конкретные места               |
| Выпуск        | Дополнительные условия operating-model §7, если стадия указана             |

Финал задачи содержит: что изменено и почему, подтверждённые критерии, команды и результат,
что не проверено, риски, причина окончания run и отдельно статус приёмки. Старые результаты
не удаляются: после изменения кода они помечаются устаревшими для соответствующих критериев.

## 5. Журнал серии и стоимость

Для каждого случая сохраняются исходная ревизия, критерии, runner/модель/настройки/права,
порядок попыток, итог среды, reviewer, вмешательства, возвраты, регрессии, время до приёмки,
время ревью, расходы run, инфраструктуры и человеческой проверки. Неудачные случаи остаются
в знаменателе доли приёмки. Финансовые значения без данных обозначаются «неизвестно».

Стоимость серии / число принятых задач — агрегатная стоимость принятой задачи, когда
есть хотя бы одна принятая. При нуле приёмок показатель не вычисляется. Заранее
зафиксированные одинаковые условия позволяют сравнить процесс до и после переезда.


## 6. Типизированный lifecycle и неизменная история

В исполнимом паспорте stage.kind явно задаёт contract, implementation, verification либо
publication; отсутствие kind сохраняет прежний verification-профиль. До первого start
техплан уже готов и заморожен вместе с паспортом. Один implementation может менять source
только в scope, хранит вход и проверенный выход. Следующие verification закреплены за этим
выходом. Исторический contract не выдаётся за source check более поздней ревизии.

Обычный return с первым записанным дефектом использует объявленный return_to, точные
AC/место/направление исправления, прежние check_id и счёт. Итерация возрастает, эффективные
implementation/test/review становятся недействительными, но события и архивы не удаляются.
Parent сохраняется. Второй неуспех блокирует start/return; смена run не обновляет бюджет.

Канонический парный отчёт — последняя сводка. До перехода координатор сохраняет точные
копии в `docs/reports/evidence/SLUG/stages/STAGE/RUN-report.md` и `RUN-report.gate.json`.
Finish/return записывает их хэши; дальнейшая подмена отклоняется. Перед последним finish
все исторические proof/архивы и финальная пара должны уже находиться в Git.

`bind-artifacts` доказывает узкую ancestry-связь собственной evidence-публикации: только
канонические gate-пути этой задачи и её evidence-каталог, прежний scoped dirty fingerprint,
неизменные контракт и старые хэши. Исходный revision_commit в evidence остаётся фактическим;
поздний commit хранится отдельно в relation. Это не новый запуск тестов и не общий docs-only
эквивалент. Binding после return не восстанавливает superseded source acceptance.

`publication_paths` — точные scoped Markdown metadata-файлы, замороженные перед работой.
Публикация фиксирует отдельную relation: S source acceptance, D metadata output, ancestry,
точные пути, diff SHA-256, старые/новые Git blobs, защищённый dirty fingerprint. Следующая
независимая verification явно принимает этот diff как supported_metadata с сохранением
правил/контракта. Formatter и старое source review такого решения не заменяют. Смешанный
файл разрешает проверить status/link diff, но не менять правила; истинность вердикта требует
независимого reviewer. До обязательного релиза документация говорит release pending; после
успешного релиза хранитель делает docs-finalize и completion-check в той же задаче/parent.

Отдельный recover привязан к текущему stop_event, прежним task/stage/check/run/count,
именованной причине и условию, новым наблюдаемым условиям и независимому подтверждению,
свежему snapshot и отсутствию активного дубликата/Q/конфликта. Счёт сохраняется: фактический
pass сбрасывает только свой check, failed/blocked увеличивает старое число и сразу повторяет
stop. Ожидаемый RED и unknown/not_run не доказывают восстановление; proof одноразовый.
Исправление source без свежей реализации/prerequisites не разрешает retry. Текущий останов
Task 3 не получил такой remediation и остаётся failures=2; этот контракт не разрешает третий
запуск. CLI не проверяет семантическую истинность причины и native liveness, не является
scheduler или самостоятельной приёмкой задачи. Формат/команды — в [gate](agent-loop-gate.md).
