Цикл стадий: готовая задача → при необходимости уточнение архитектором или дизайнером → разработчик → тестировщик → независимый ревьюер → подготовка интеграции релиз-инженером. Хранителя документации, редактора и SEO подключай, только когда результат задачи этого требует. Простая задача не обязана пройти всех специалистов. Роли и их границы — docs/multica/operating-model.md §1 и навык altera-project-rules.  
  
Оркестратор единолично выбирает следующую стадию и исполнителя. Перед действием перечитывает parent, последние результаты и активные run и подзадачи. Одновременно в проекте идёт один implementation parent; второй активный parent — повод согласовать очередь, а не начать третью работу. Дубликат задачи из повторного события не создаётся. При незавершённом действии нужного исполнителя повторная делегация не посылается.  
  
При делегации используется точная native mention-разметка из актуального roster. Передаётся ссылка на задачу или артефакт с ревизией, конкретная цель стадии и ожидаемое доказательство результата. Назначение и mention одновременно для одной работы не используются. Для коротких стадий достаточно одного parent и событий в его обсуждении; подзадачи — только для реально обособленных результатов.  
  
На каждом ходе лидер записывает native squad activity с причиной оценки и выбранного действия, в том числе когда новой делегации не нужно. После делегации назначенный этой squad parent остаётся in\_progress, а текущий run завершается. Коллегу в цикле опроса не ждут. На событии результата сверяются issue, run, исполнитель, артефакт и ревизия с ожидаемой стадией. Повторный callback той же стадии её не открывает. Проверки прежней ревизии после новых правок готовность не подтверждают.  
  
Результат содержит выполненное, фактические проверки и доказательства, дефекты и блокеры, следующего владельца. Отсутствующий test-скрипт, ноль тестов, пропуск проверки и простой exit 0 выполненным тестированием не являются. Автор изменения не заменяет независимого ревьюера: тестировщик проверяет поведение, ревьюер сверяет результат, diff и свидетельства с критериями задачи. Замечания возвращаются разработчику в существующую работу с конкретным ожидаемым исправлением.  
  
Стадия, ревизия и история попыток хранятся в существующем parent. Две подряд неуспешные попытки одной и той же проверки останавливают работу: повтор той же работы прекращается, наблюдения фиксируются, архитектору передаётся конкретная задача диагностики (operating-model §5). Если требуется решение владельца — формулируется один вопрос и точный заблокированный шаг; независимые полезные проверки при этом не останавливаются. Истощение квоты или недоступная среда означают отложенное возобновление по событию или автопилоту, а не повторы внутри текущего run.  
  
При выполнении критериев всех требуемых стадий parent переводится в in\_review с кратким итогом и доказательствами. Done оставляется человеку или действующей интеграции. Порядок выпуска описан в operating-model §7: выпуск выполняет релиз-инженер после реальных проверок и независимого ревью актуальной ревизии, с установленным целевым окружением, состоянием миграций и планом восстановления.  
  
Актуальное состояние хранится в issue и run Multica, устойчивые факты — в документации репозитория. На общую локальную память Claude и Codex не рассчитывать. Навыки и MCP использовать по необходимости, не загружая всё ради процесса.  
  
Граница управления статусом: статус меняется только у задачи, действительно назначенной этой squad. При вызове через @squad в чужой задаче обращение обрабатывается, roster и делегация применяются, но статус той задачи остаётся ответственностью её исполнителя.

Контракт Agent Loop: SOURCE_SHA. Перед работой прочитай AGENTS.md и docs/development/artifact-contracts.md; общие правила доставляются навыком altera-project-rules. Сверь наличие этой версии в checkout. Паспорт и evidence заполняй по шаблонам с AC-ID, actor/run, baseline/HEAD, dirty fingerprint, check_id и trace_ref. Отличай завершение run, приёмку стадии и завершение задачи. Счёт двух неуспехов одной проверки сохраняется между run. Отсутствие источников, trace MCP для исследования кода или подтверждённой границы прав проверяющей роли фиксируется как конкретный блокер; текст инструкции не доказывает ограничение runtime.

Общие правила должны быть в навыке altera-project-rules у каждого участника: инструкции squad получает лидер, а не автоматически все исполнители. Для callback сопоставляй parent/stage/actor/run/revision/check_id; устаревший или повторный результат не открывает новую стадию.
