Проход финализации Altera: довести до Done задачи в `in_review`, чей PR уже слит в `app`.
Порядок и требования контроллера — docs/multica/done-finalization.md на свежем origin/app.

0. Очередь проходов. Первым действием прочитай `multica agent tasks 3fdfb369-fa6c-49d6-921b-95593f174705
   --output json`. Если там есть run этого автопилота в `queued` или `waiting_local_directory`, созданный
   позже текущего, заверши проход одной строкой `no_action: superseded`: ту же работу сделает он, а
   проходы, накопившиеся за время ожидания слота, не повторяют друг друга.
1. Отбор. Карточки проекта в `in_review` с `metadata.task_id`, PR задачи слит в `app`
   (номер — из `docs/reports/tasks/<T-ID>.json` или `multica issue pull-requests`), в карточке нет
   `queued`/`running` run. Список: `multica issue list --project 1ff3917d-4c10-4303-a671-406c1fda9613
   --status in_review --output json` — это объект, карточки в поле `issues`, следующая страница по
   `has_more` и `offset`. Старые первыми, не больше пяти за проход. Открытые PR, конфликты
   и красный CI — работа оркестратора, их не трогай.
2. Для каждой найди итоговый head (`headRefOid` слитого PR) и последний свой комментарий
   `ALTERA_FINALIZE_V1` в карточке. Если с него ничего не изменилось — пропусти задачу молча.
3. Ревью. Нужен завершённый run ревьюера `db94a617` в этой карточке, последняя строка вывода
   которого — `ALTERA_REVIEW_V1 {"sha": "<итоговый head или SHA с тем же патчем>", "verdict": "approved"}`.
   Если его нет и запроса на этот SHA ещё не было, оставь в карточке комментарий:
   `[@Altera — независимый ревьюер](mention://agent/db94a617-807c-4eec-981f-51fd4b3217d4)`,
   номер PR, полный итоговый SHA, просьба проверить слитый код по критериям задачи и последней
   строкой вывода напечатать маркер; уборку и комментарий — до маркера, после него ничего.
   Повтор — один раз и только если прошлый run завершился без маркера. Отказ не перезапускай:
   зафиксируй `review_rejected`, исправление ставит оркестратор. Не больше трёх новых запросов
   ревью за проход.
   Если у карточки есть `metadata.rework_task` (она вернулась по шагу «Возврат»), в запросе перечисли
   задачи-доработки, их слитые PR и то, что они приняты (Done), и попроси проверить итоговый head
   исходного PR вместе с ними: блокирующие находки прошлого ревью, закрытые принятыми доработками,
   одобрению этого SHA не мешают. Маркер — на итоговом head исходного PR.
4. Итог в `app`. Нужны Markdown итога с Task ID и итоговым head и receipt, где `tested_sha` =
   `pr.head_sha` = итоговый head, есть `pr.merge_sha` и `review.*` из run ревьюера, а
   `finalization.sha256` — SHA-256 байтов Markdown. Если этого нет, обнови
   `docs/reports/tasks/<T-ID>.json` и `.md` одним docs-PR на все такие задачи прохода в отдельном
   worktree от свежего `origin/app`, включи автослияние (`gh pr merge <номер> --auto --merge`)
   и не жди. Поля, которых нет в истории карточки и GitHub, не выдумывай — `blocked` с причиной.
5. Проба выкладки. Если для задачи с готовым итогом `controller.py verify` отказывает только
   `deployment` и завершённой пробы моложе 40 минут нет, оставь в карточке первой такой задачи
   один комментарий с упоминанием ревьюера: прогреть `https://altera-m4po.onrender.com/health`
   до ответа 200, затем только чтение Render MCP — `list_deploys` и `get_deploy` для сервиса
   `srv-d1uk6b6mcj7s73ek25h0` (workspace `tea-d0q29c7diees738n0250`); маркер ревью не печатать;
   вернуть deploy ID, commit SHA и статус. Не больше одной пробы за проход.
6. Done. Для задачи с готовым итогом в `app` и завершённой пробой моложе 55 минут (если выкладка
   обязательна): receipt из `origin/app` плюс локально `deployment.probe_actor_id` =
   `db94a617-807c-4eec-981f-51fd4b3217d4` и `deployment.probe_run_id` = run пробы; прогрей
   `/health`; `controller.py verify`, при `ok` — `controller.py done`. Одна свежая проба годится
   всем задачам, чей `merge_sha` входит в задеплоенный коммит.
7. Каждое решение по карточке — один комментарий, последняя строка которого
   `ALTERA_FINALIZE_V1 {"task": "<T-ID>", "stage": "<review|receipt|probe|done|blocked|return>", "sha": "<итоговый head>", "reason": "<код>"}`.
8. Возврат. Карточки проекта в `blocked` с `metadata.rework_task` (одна или несколько T-ID через
   пробел). Если каждая из этих задач принята — её карточка с тем же `metadata.task_id` в `done`,
   а в `.git/autonomy-state/verified/` есть `<T-ID>.json`, — переведи исходную карточку в `in_review`
   (`multica issue status <id> in_review`) и оставь в ней комментарий: какие доработки приняты
   (T-ID, карточка, PR) и что дальше она идёт обычными шагами 3–6; последняя строка — маркер со
   `stage: return`. Если хоть одна доработка не принята, карточку не трогай и ничего не пиши.
   Другие `blocked` (без `rework_task`, с причиной рантайма или владельца) не трогай. Без упоминаний:
   комментарий не должен запускать ничьих run. Не больше пяти возвратов за проход.

Внутри прохода не жди завершения запусков. Нет кандидатов или изменений — заверши одной строкой
`no_action`. В конце — только задачи, переведённые в Done, запрошенные ревью и пробы, docs-PR
и конкретные блокеры.
