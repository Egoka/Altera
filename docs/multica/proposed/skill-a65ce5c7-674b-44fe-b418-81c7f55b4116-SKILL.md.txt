# Правила проекта Altera

Читается перед любой задачей. Здесь только то, что нужно знать **до** чтения репозитория;
остальное — в файлах, на которые указывают ссылки. При расхождении этого текста с репозиторием
прав репозиторий.

## Старшинство источников

1. Рабочий журнал решений владельца `docs/decisions/role-review-working-log-2026-09-08.md`
2. Спецификации `docs/spec/`
3. ADR `docs/decisions/`
4. Vision `docs/vision/` (`00-reality-check.md` сам отстаёт от журнала)

Продуктовые решения принимает только владелец. Не подтверждённое кодом или спецификацией
помечается `[ДОПУЩЕНИЕ]`. Придуманные числа, лимиты, сроки, цены и провайдеры запрещены.
Если задача упирается в незакрытый `Q-NN` или в отложенную владельцем тему — работа не
начинается, задача возвращается с пометкой «требует решения владельца».

## Порядок работ

- Операционная модель `docs/multica/operating-model.md` — стадии, evidence, единственный writer
  продуктового кода, действия владельца. Читается перед планированием любой задачи.
- Бэклог `docs/backlog/README.md`. Задача берётся только в статусе `готова`; статус ставит
  владелец. `кандидат` — это предложение, а не готовность. Прямое письменное поручение владельца отдельно разрешает конкретный план в его scope, без изменения статусов остальных задач.
- Стадии: архитектура → разработка → тестирование → независимое ревью → документация → релиз.
  Стадии, не указанные в задаче, пропускаются. Стадия передаётся дальше только с evidence
  в репозитории: план, отчёт, вывод команд, вердикт.

## Ритуал плана и отчёта

1. Перед работой — план `docs/plans/ГГГГ-ММ-ДД-имя.md`; в шапке обязателен базовый коммит
   (`git rev-parse HEAD`). Работа по неописанному плану не начинается.
2. После завершения — отчёт `docs/reports/ГГГГ-ММ-ДД-имя-report.md` с тем же слагом. План не
   считается выполненным, пока отчёта нет, даже если код закоммичен. Отчёт обязателен и для
   частично выполненного, и для отменённого плана.
3. Раздел «Как проверено» содержит выполненные команды и их фактический вывод. Утверждение
   «работает» без выполненной проверки в отчёт не попадает.
4. Планы не переписываются задним числом: изменилось решение — новый план либо раздел
   «отклонение» в отчёте.

Эти пути перекрывают пути по умолчанию из любых навыков планирования.

## Бюджет попыток

Две подряд неуспешные попытки одной и той же проверки внутри стадии останавливают работу:
итерации прекращаются, стадия возвращается с описанием причины — что именно проверялось, что
менялось между попытками и каким был вывод. Счёт ведётся по конкретной проверке, а не по стадии
в целом; успешная проверка обнуляет счёт для себя. Правило — `docs/multica/operating-model.md`
§5, подтверждено владельцем 2026-09-09. Других числовых ограничений (таймаутов, лимитов на число
задач, общего лимита итераций) не задано, и агент их не вводит.

## Команды проверки

```
pnpm format && pnpm lint && pnpm test
```

`pnpm test` реально исполняет тесты; актуальное число, команды и датированный baseline смотри в `docs/development/testing.md` и отчёте текущего run. Ноль тестов,
отсутствующий test-скрипт, пропущенная проверка и простой `exit 0` не являются выполненным
тестированием. Дымовая проверка сервера — `cd server && pnpm run smoke`; она подтверждает старт
и ответ GraphQL, но **не** связность с Redis.

Обычный `server build` содержит `prisma migrate deploy` и безвредной проверкой не является;
для сборки без миграций — `build:ci`. Production-миграции выполняет релиз-инженер в составе
проверенного выпуска после установления целевой базы, состояния миграций и плана восстановления.

`pnpm format:fix` изменяет файлы и допускается только исполнителю разрешённой правки в её scope; проверяющие используют `pnpm format`.

## Ветки, коммиты, выпуск

- Ветки `server/*`, `web/*`, `docs/*`; pull request открывается в `app`. На `app` напрямую
  не коммить.
- Conventional commits: тип из `commitlint.config.js`, scope в нижнем регистре, заголовок до 100
  символов, без точки — `feat(admin): …`. Pre-commit запускает format, lint и test; хук живой,
  обходить его не нужно.
- Push, слияние в `app` и выкладка отдельного разрешения владельца не требуют (операционная
  модель §7, разрешение от 2026-09-05, подтверждено 2026-09-09). Выпуск ведёт релиз-инженер
  после независимого ревью **актуальной** ревизии, с установленным целевым окружением,
  состоянием миграций и проверяемым планом восстановления.

## Язык и секреты

Документация и комментарии — русские; идентификаторы и сообщения GraphQL-ошибок — английские.
Форматирование задаёт Prettier (без точек с запятой, без trailing comma, ширина 120, отступ
2 пробела) — спорить с ним вручную не нужно.

Секреты — файлы окружения, ключи, строки подключения Neon и Redis — не попадают ни в репозиторий,
ни в вывод, ни в текст задачи.

Контракт Agent Loop (версия SOURCE_SHA; сверяй с рабочим деревом перед исполнением)

Начни с AGENTS.md, docs/development/README.md, docs/development/artifact-contracts.md и docs/development/testing.md. Разделяй продуктовый контракт (журнал → спецификации → ADR → vision), фактическое состояние (код и проверки на ревизии) и правила процесса. Если нужная версия источников отсутствует, зафиксируй блокер синхронизации до действий с продуктовым кодом.

Паспорт стадии содержит исходную задачу/поручение владельца, AC-ID, scope, разрешённые действия, baseline SHA, итоговый HEAD, actor/run, план и парный отчёт. Каждая проверка содержит check_id, команду, cwd, exit code, результат и ограничения, trace_ref; при dirty tree также fingerprint diff и хэши изменённых/неотслеживаемых файлов. После правок прежнее evidence по затронутым критериям устаревает. Отличай завершение run, приёмку стадии и завершение задачи.

Счёт последовательных неуспехов хранится для конкретных задачи/стадии/check_id и переносится между run и исполнителями. Два неуспеха останавливают эту проверку; успех обнуляет только свой счёт. Диагностика после остановки читает уже полученное evidence и формулирует причину; она не является скрытой третьей попыткой. Изменение условий фиксируется до восстановления. Сохраняй отвергнутые гипотезы, ограничения и следующий разрешённый шаг.

Для исходного кода обязателен trace MCP по AGENTS.md; если его нет в эффективном наборе инструментов, сообщи точный блокер подключения и продолжи только независимую работу с документацией/конфигурацией. Не заменяй отсутствие инструмента выдуманным вызовом. Private в Multica — право вызвать агента, а не файловая песочница. Промпт, hook и наличие skill не доказывают реального ограничения прав; без подтверждённого ограничения tester/reviewer не объявляй их read-only. Не удаляй и не обходи gate ради зелёного результата.
