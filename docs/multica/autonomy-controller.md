# Контроллер автономии

Этот контракт применяется только к явно запущенной Multica. Обычный чат не читает очередь,
не приобретает слот и не завершает чужие задачи. Общие AGENTS.md/CLAUDE.md не подключают этот процесс.

## Текущие гарантии

`scripts/autonomy/controller.py` проверяет цепочку CI → независимое review → merge →
необходимый deploy/health → финализация в `app`. JSON задачи сам по себе не является доказательством:
GitHub, история native runs и файлы `app` перечитываются перед действием.

Граница — управляемый путь выполнения. У native агентов остаются прежние локальные CLI-доступы:
запрет прямого `gh pr merge`/`multica issue status done` в инструкции не является серверным ACL.
Пока отдельное разграничение прав не подтверждено, отчёт обязан писать `managed_path_only`.
Без live deployment verifier серверные задачи блокируются, а не закрываются по тексту агента.

## Один итог задачи

Хранить канонический JSON в `docs/reports/tasks/<T-ID>.json` и короткий итог в соседнем Markdown.
Исторические планы/отчёты не удалять; сослаться на них. Минимальный пример:

```json
{
  "schema_version": 1,
  "task_id": "T-123",
  "issue_id": "native-issue-uuid",
  "work_class": "product",
  "source": { "path": "docs/backlog/tasks/T-123.md", "sha": "full-source-sha" },
  "baseline_sha": "full-app-baseline-sha",
  "tested_sha": "full-pr-head-sha",
  "implementer_id": "native-agent-uuid",
  "implementer_run_id": "native-execution-uuid",
  "criteria": [{ "id": "AC-1", "status": "passed", "evidence": "https://github.com/Egoka/Altera/actions/runs/123" }],
  "pr": {
    "number": 123,
    "head_sha": "full-pr-head-sha",
    "base_sha": "full-base-sha",
    "base_ref": "app",
    "merge_sha": "full-merge-sha"
  },
  "review": {
    "actor_id": "reviewer-uuid",
    "run_id": "review-execution-uuid",
    "sha": "full-reviewed-sha",
    "verdict": "approved"
  },
  "deployment": { "required": false, "reason": "Только документация" },
  "finalization": { "path": "docs/reports/tasks/T-123.md", "sha256": "sha256-of-markdown-bytes" },
  "usage": null
}
```

UUID и SHA в примере — placeholders, не готовое evidence. Поля `verified`/`accepted_at` создаёт
контроллер после проверки; агент не назначает их сам. Финальный Markdown включает Task ID,
полный tested SHA, результат критериев и ссылки. Собственный hash/commit внутрь Markdown не записывать.

Ревьюер — другой actor из настроенного allowlist. Его завершённый native run заканчивается
строкой `ALTERA_REVIEW_V1 {"sha": "<полный SHA>", "verdict": "approved"}` только при одобрении.
Отклонённое review не печатает эту строку. Новый CI обязателен после каждого изменения head.
Новое review обязательно после изменения патча ветки; обновление от `app` с тем же патчем его не требует
(см. «Обновление ветки перед merge»).
Разработчик и reviewer фиксируют настоящие execution IDs, не Issue ID.
В первой версии контроллера обе native execution должны относиться к `issue_id`
канонического итога. Запускай review в этой же задаче; run отдельной дочерней карточки
не наследует доверие автоматически. Для старых child-review сохрани ссылку как историю
и выполни актуальный независимый review в канонической задаче.

Вызовы: `python3 scripts/autonomy/controller.py verify|merge|done --config <installed-config> --receipt <json>`.
Готовность к слиянию проверяется `verify --phase merge`; без флага `verify` отвечает про фазу Done.
Это разные вопросы: `deployment` и `finalization` входят только в Done и слияние не запрещают.
Отказ Done по деплою не означает, что PR нельзя сливать: задача сливается и ждёт выкладки уже в `app`.
Не вызывать merge/Done напрямую. При отказе исправить конкретное недостающее evidence.
Потеря доступа фиксируется один раз; ручное Done владельца не требуется.

## Обновление ветки перед merge

Решение владельца от 2026-09-19: ветку не догоняют до актуальной `app` перед merge. Раньше защита
`app` требовала актуальную ветку: пока шёл CI обновлённой ветки, в `app` вливался другой PR, GitHub снова
требовал обновления, и очередь крутилась без конца. Теперь в защите `app` выключено «Require branches to
be up to date» (`strict: false`), обязательной остаётся проверка `test`. Контроллер для `merge` требует
открытый PR, совпадение head с проверенным SHA и подтверждение GitHub, что PR сливается без конфликтов
(`mergeable`). Отставание от `app` само по себе отказа не даёт. Совместимость параллельно слитых PR
проверяет прогон CI на push в `app`; его падение чинится отдельным PR, а не откатом очереди.

Отказ `base` означает, что PR закрыт, конфликтует с `app` или GitHub ещё не посчитал mergeability.
Только при конфликте ветку обновляют от `app` (rebase или merge `app` в ветку) и разрешают его.

`review.sha` в итоге — SHA, который проверил ревьюер; `tested_sha` и `pr.head_sha` — текущий head
с зелёным CI. Они различаются только после обновления ветки. Контроллер сам сравнивает патч ветки
от точки ответвления от `app` для проверенного SHA и для head (`git patch-id --stable`, без собственных
`docs/reports/tasks/<T-ID>.json`, `.md`, прямых файлов `docs/reports/` и `web/app/graphql/generated/`).
Совпадение сохраняет review. Сгенерированные артефакты исключены потому, что обязательная проверка CI
`pnpm codegen --check` на том же head доказывает их вывод из схемы и операций, а сами схема и операции
из патча не исключаются: ревьюер смотрит именно их. Без этого разрешение конфликта в сгенерированном
файле отменяло уже полученное одобрение, и задача уходила на повторное review, пока `app` снова
не уходил вперёд. Другой код, иное разрешение
конфликта или правка `app` в трёх строках контекста изменений ветки дают отказ `review`.

Порядок: `merge` → при отказе только `base` из-за конфликта обновить ветку, дождаться CI нового head,
записать новый `tested_sha`, `pr.head_sha` и `pr.base_sha`, оставив `review` прежним, и повторить `merge`.
Если GitHub ещё считает mergeability, `merge` повторяется в следующем проходе без обновления ветки.
Новое review запрашивать только после отказа `review`.

## Слияние по зелёному CI

Решение владельца 2026-09-20 (журнал §30): PR сливается в `app`, как только зелёные все проверки
GitHub Actions. Слияние выполняет автослияние GitHub, а не контроллер: в защите `app` обязательна
агрегатная проверка `test`, апрувы не требуются, ветка удаляется после слияния. Открыв PR, агент
включает автослияние (`gh pr merge <номер> --auto --merge`) и не ждёт результата — это внешняя
система, а не работа прогона.

Независимое ревью перестало быть условием слияния, но осталось условием Done вместе с деплоем:
их проверяет `controller.py` на фазе `done`. Фаза `merge` остаётся для случаев, когда автослияние
недоступно — например, при выключенной защите ветки. Цена решения записана в журнале: код попадает
в `app` до независимой проверки, и дефект чинится уже в `app` отдельным PR.

У перехода в Done после автослияния пока нет владельца и триггера: 2026-09-20…21 ни одна слитая
задача не дошла до Done. Порядок шагов и предложение отдельного автопилота —
[фаза Done после автослияния](done-finalization.md) (ждёт решения владельца).

## Итог задачи и head PR

Итог задачи (`docs/reports/tasks/<T-ID>.json`, `.md` и повествовательный отчёт `docs/reports/`)
пишется после зелёного CI, поэтому он физически не может назвать SHA коммита, в котором лежит сам.
Отсюда правило порядка: **итог публикуется отдельным PR в `app` после того, как head ветки с кодом
стал окончательным**, и называет именно этот head. Ветка с кодом тогда не двигается после CI,
`tested_sha` совпадает с head, а review запрашивается на нём же.

Контроллер дополнительно терпит обратный порядок, когда итог дописан последним коммитом в ту же
ветку. Head принимается при трёх условиях сразу: он потомок `tested_sha`; отличается от него только
файлами `docs/reports/tasks/<T-ID>.json`, `docs/reports/tasks/<T-ID>.md` и прямыми файлами
`docs/reports/`; CI зелёный именно на живом head. Чужие итоги в `docs/reports/tasks/`, evidence,
суточные отчёты, `docs/plans/`, спецификации и любой код под это исключение не подпадают —
для них нужен новый `tested_sha` и новый CI. Тот же набор файлов не входит в отпечаток патча,
поэтому собственная финализация не отменяет уже полученное одобрение кода.

Независимое review запрашивается на финальном head — том, который пойдёт в merge. Его результат
оркестратор записывает в итог задачи: `review.actor_id`, `review.run_id`, `review.sha` и
`review.verdict`. Без этих полей контроллер отказывает `review`, даже если ревьюер отработал:
завершённый run без записи в итоге для него не существует.

Карточка задачи в Multica обязана нести `metadata.task_id`, равный Task ID итога. Флага для этого
у `multica issue create` нет, поэтому сразу после создания выполняется
`multica issue metadata set <issue-id> task_id <T-ID>`. Без него контроллер отказывает `issue_scope`
и не читает ни GitHub, ни CI: связь между карточкой и итогом не подтверждена.

## Оркестрация

`runtime_bridge.py` — отдельный Claude stream-json профиль **только оркестратора**.
Он сравнивает содержательные состояния задач, комментариев других участников, native runs,
PR/CI и `app`. Heartbeat и собственные комментарии лидера не являются новой работой.
Повторный снимок завершает программный `no_action` с нулевыми токенами, без вызова Claude.
Реальному Claude сохраняются managed MCP/config параметры; передаётся только изменившаяся часть снимка.
Исключение — нарушенный инвариант очереди: меньше трёх `Todo` или готовая задача без активного
исполнения. Пока нарушение сохраняется, контроллер добавляет один `ALTERA_CONTROLLER_ATTENTION_V1`
на час. Повторы внутри того же часа остаются `no_action`; следующий час даёт оркестратору одну
новую возможность пополнить очередь или запустить работу даже при неизменном внешнем снимке.
Активное исполнение определяется по настоящему native run со статусом `queued`/`running`, а не по
полю карточки `in_progress`. Назначенная карточка без run получает причину `launch_assigned_work`.

Комментарии читаются с `--full --summary`: учитываются `revision`, `updated_at` и хеш preview,
включая сообщения resolved threads. `--since` не используется: CLI фильтрует по времени создания
и может пропустить правки старых комментариев. Если preview усечён и API не дал revision/updated_at,
снимок явно содержит `comment_edit_coverage: partial`; правку за границей preview тогда нельзя
обнаружить. Полное отслеживание требует версии/времени правки от API либо полного содержимого.

PR-инвентарь собирается полностью через GraphQL cursor pagination, включая закрытые и merged PR.
Контроллер проверяет последнюю страницу и отклоняет неполные ответы. Для последнего commit каждого
PR читаются CI-контексты: если их больше 100 и `hasNextPage` остаётся истинным, снимок блокируется с
`incomplete check context inventory`. Для такого PR требуется добавить пагинацию CI-контекстов
и повторить сбор; неполный снимок не превращается в успешный `no_action`.

SQLite journal хранится в установленном state directory вне worktree. Захват события атомарен;
успешный повтор не выполняется. Неопределённый `running` после сбоя требует сверки внешнего результата,
а не повторного merge. Первичная попытка + максимум два повтора неизменившейся ошибки.
Новая ревизия или содержательное событие получают новый ключ. Версия инструкций входит в ключ.

Освободившийся слот сразу передаётся готовой задаче; поддерживать три готовых задачи из бэклога.
Количество готовых задач не меняет лимит одного product writer. Новая работа начинается с fetch
и отдельного worktree свежего `origin/app`. При выборе учитывать возраст очереди и зависимости.
Native runtime получает канонические `MULTICA_SERVER_URL` и `MULTICA_WORKSPACE_ID`. Установленный
`multica` guard автоматически добавляет `--project` к `issue create` и отклоняет создание в другом
проекте. После записи оркестратор проверяет фактический `project_id`; карточки вне проекта не входят
в целевые три `Todo` и не считаются полезным результатом.

## Проверки и ресурсы

Перед server work выполнить preflight из `scripts/autonomy/preflight.py`; проверить новые env,
версии, GH и реальные MCP tool results того же runtime/run. Inventory/Connected не заменяет tools/call.
Development Neon остаётся текущей средой. Production не выбирать автоматически.
CI использует отдельные PostgreSQL 17 и Redis; миграции допускаются только на изолированной CI БД.

Уборка — [безопасная очистка](autonomy-cleanup.md). Без подтверждённого ограничения новых запусков
применение очистки запрещено; dry-run показывает кандидатов и причины. Штатный daemon GC сохраняет
свои сроки до отдельной проверки его гарантий относительно канонического Done.

Отчёт и метрики — [ежедневный аудит](daily-audit.md). Нельзя объявлять отсутствие данных нулём,
считать служебные задачи продуктовым результатом или восстанавливать потерянные доказательства догадкой.
