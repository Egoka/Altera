# Автоматический PR и merge

При изменениях backend/shared build inputs обязательна [проверка Render и Neon](infrastructure-checks.md): CI, merge, deploy и health фиксируются отдельно.

Узкое исключение к ожиданию финализации перед следующим dispatch — подтверждённый
`parked_release` по тому же контракту. Это не Done: handoff, освобождение slot и его повторный
захват recovery обязательны; без доказательств сохраняется прежняя последовательность.

Поручение владельца от 2026-09-14: после успешной работы создавать PR, а после зелёных
проверок сливать его в `app`. Это обязательный обычный путь выполнения каждой задачи с
изменениями репозитория. Отдельное «создай PR» или «можно merge» не требуется.

[Передача результата и восстановление](queue-flow-corrections.md) обязательны также после
локального исправления без открытого PR или delivery metadata. Новая T-задача использует
отдельную ветку и PR от актуальной app.

## Кто выполняет

Оркестратор ведёт существующий parent до интеграции результата. Исполнитель сохраняет
изменения задачи коммитами и передаёт baseline, branch/HEAD, локальные проверки, план и отчёт.
Релиз-инженер единолично публикует ветку и создаёт/обновляет PR в `Egoka/Altera`, base `app`.
Тестировщик и независимый ревьюер проверяют результат; релиз-инженер выполняет merge после
их обязательных стадий. По поручению владельца от 2026-09-14 оркестратор сам выполняет Done
после приёмки и финализации по [post-merge-continuation](post-merge-continuation.md).

## Создание PR

После успешных локальных проверок и подготовки результата релиз-инженер сверяет git status,
scope diff, baseline и HEAD; не включает чужие изменения и не публикует секреты.
Ветка задачи отправляется обычным push. Перед созданием проверить существующие PR по
репозиторию, head/base и связи с parent: существующий обновить, дубликат не создавать.
Если изменений нет, фиктивный PR не нужен — зафиксировать основание.

При таймауте или неопределённом результате push, создания или обновления PR сначала
перечитать remote head и PR во всех статусах по repo/head/base/parent. Найденный точный PR
использовать, а не создавать снова; если он уже merged, проверить результат и продолжить
финализацию. Закрытый без merge PR не переоткрывать автоматически. Если состояние невозможно
проверить, остановить публикацию с конкретной причиной. Push/create/update вслепую не повторять.

PR можно открыть до финального независимого ревью: это запускает CI, результаты которого
нужны для приёмки. Описание содержит результат, scope, фактические проверки, ограничения,
ссылки на parent и отчёты. Заголовок/описание отражают итоговый diff. URL и точный head SHA
сохранить в parent. Сам факт создания PR задачу не завершает.

## Условия merge

Все условия обязательны одновременно:

- PR относится к этой задаче, base равен `app`, он открыт и не draft, scope принят.
- Все обязательные стадии завершены. Независимое ревью принимает текущий head SHA; нет
  неустранённых блокирующих замечаний. GitHub review requirements также соблюдены.
- GitHub CI относится к текущему head SHA и известному workflow. Обязательный `test` и все
  обязательные проверки защиты ветки успешны. Для текущего workflow Checks успешны формат/
  lint/tests, web build/typecheck, browser smoke, server build/smoke и итоговый test.
  Отсутствие записей не равно успеху; pending, failure, cancelled, timed_out, action_required,
  neutral или skipped обязательной проверки запрещают merge. Условный lifecycle job,
  например удаление Neon-ветки до merge, может быть skipped только если он не обязателен.
- GitHub подтверждает возможность слияния без конфликтов; нет ручного блокера/запрета
  владельца, активной записи в ту же ветку или другой интеграции этого parent.

Непосредственно перед merge перечитать PR, head SHA, CI и состояние parent. Выполнить
обычный `gh pr merge <number> --merge --match-head-commit <reviewed-sha>` (без `--admin`,
обхода защит и ослабления CI). Не включать отложенный `--auto` на основании старого ревью:
последующий push мог бы поменять принимаемую ревизию.

Любой новый commit, rebase или исправление после приёмки отменяет допуск прежнего SHA:
снова проверить нужные тесты/CI и независимое ревью нового выхода. Конфликт или отказ
GitHub — конкретная причина остановки, а не повод автоматически force-push чужую ветку.

После команды проверить состояние MERGED, merge commit и вхождение результата в `app`.
При таймауте сначала перечитать PR; повторное слияние вслепую запрещено. Записать URL,
reviewed SHA, CI run URL, merge SHA и оставшуюся финализацию в исходный parent. Merge не
подменяет обязательную документацию, приёмку production-выпуска или обновление статусов.

Решение владельца от 2026-09-17: ветка задачи не остаётся на `origin` после слияния.
В репозитории включена настройка `delete_branch_on_merge`, поэтому GitHub снимает head-ветку
сам при любом merge, включая ручной; отдельной команды удаления агент не выполняет и вслепую
не повторяет. Это снимает только remote head-ветку — локальные worktree и ветка остаются под
[контрактом очистки](autonomy-cleanup.md) и его fence. Если ветка понадобилась снова, её
возвращает обычный push; удалённые коммиты остаются доступны по SHA из parent и receipt.

Решение владельца от 2026-09-19: PR сливаются только обычным merge-коммитом, squash и rebase
в настройках репозитория выключены. Так в истории `app` видно, какая ветка и когда влита, а
её коммиты становятся предками `app`: `git branch --merged app` показывает её слитой.

Ветки, слитые squash до этого решения, не стали предками `app`, поэтому
`git branch --no-merged app` показывает их живыми и после успешного merge. Признаком
несённой работы это не является: проверяется рибейзом ветки на `origin/app` — рибейз
отбрасывает коммиты, изменения которых уже в `app`. Ноль выживших коммитов означает, что
вливать нечего.

## Продолжение после CI

Ожидание CI — нормальная стадия, а не запрос владельцу. Сохранить в metadata существующего
parent: `delivery_state=waiting_ci`, `delivery_pr_url`, `delivery_head_sha`, последнюю
наблюдаемую CI-сводку и ожидаемый следующий шаг. При ожидании ревью — `waiting_review`;
при подтверждённом merge — `merged`, при реальном блокере — `blocked` с причиной.

После записи завершить run. Следующее native событие лидера или очередной scheduled run
очереди/восстановления перечитывает GitHub и parent. Наличие событий GitHub не предполагается:
почасовая очередь служит гарантированным периодическим просмотром ожидающих PR при работающем
daemon. Это проверка состояния в одном проходе, без polling/sleep внутри model run.

Проверка ожидающей интеграции выполняется **до** обычного no-op из-за занятого parent, но не
разрешает вторую цепочку: queued/dispatched/running/waiting_local_directory стадия не дублируется.
При неизменившемся pending — тихий no-op. При изменении SHA — вернуть лидеру на повторную
приёмку; при красном CI — на исправление в scope с прежним бюджетом ошибок; при зелёном CI —
лидер направляет недостающую проверку/ревью или релиз-инженера, если приёмка уже завершена.
Ровно одно native событие существующему лидеру, без одновременно assignment и mention.
Сначала перечитать состояние и активные run; сохранить fingerprint (PR, SHA, CI-сводка,
следующий шаг) и native run/event ID. Если такой переход уже исполняется, повтор не отправлять;
неопределённый результат отправки сначала сверить по native истории. При отказе восстановления
применять прежние правила диагностики, не обнуляя счётчик попыток.

Очередь и восстановление сами merge не выполняют и новых parent ради ожидания не создают.
Подготовка Todo из backlog не ждёт интеграции; только запуск новой цепочки ждёт
подтверждённого освобождения parent.
Частота существующих расписаний, права доступа и решения по production не изменяются.
