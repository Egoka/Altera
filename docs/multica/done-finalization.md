# Фаза Done после автослияния

**Статус: предложено 2026-09-26, ждёт решения владельца.** Установленный runtime, описания и триггеры
автопилотов не изменены. Разбор причин — [отчёт расследования](../reports/2026-09-26-review-dispatch-investigation.md).

## Зачем

С решения журнала §30 (PR #178, слит 2026-09-20 20:08 UTC) код попадает в `app` автослиянием GitHub
по зелёному CI, а независимое ревью и проверка выкладки проверяются только на переходе в Done.
Инструкции оркестратора описывают ревью как действие перед слиянием («на финальном head — том,
который пойдёт в merge»), а у перехода в Done нет ни владельца, ни триггера, ни порядка шагов.
Итог на 2026-09-21: 43 задачи в `in_review`, последний успешный `controller.py done` — 2026-09-19 15:20 UTC.

## Что проверяет `controller.py done`

Для задачи со слитым PR контроллеру нужны одновременно:

1. карточка в проекте Altera с `metadata.task_id`;
2. receipt: критерии `passed` с evidence, `tested_sha` = `pr.head_sha` = итоговый head PR
   (или head, отличающийся от него только файлами итога задачи), `pr.merge_sha` из GitHub;
3. `review`: завершённый run агента из `reviewer_ids` **в этой же карточке**, последняя непустая
   строка его вывода — `ALTERA_REVIEW_V1 {"sha": "<SHA>", "verdict": "approved"}`; SHA равен
   `tested_sha` или даёт тот же `patch-id` ветки;
4. `deployment` для PR, затронувших `server/`, `packages/`, lock-файлы, `package.json`, `.nvmrc`,
   `render.yaml` (признак вычисляет контроллер, `required: false` в receipt его не отменяет):
   `probe_actor_id` из `release_agent_ids` и `probe_run_id` завершённого run, в сообщениях которого
   есть результат `get_deploy` Render **не старше 3600 секунд** на момент вызова, со статусом `live`,
   коммитом, содержащим `merge_sha`, и ответом `/health` с тем же `revision` (таймаут 15 секунд);
5. `finalization`: Markdown итога в `app`, который содержит Task ID и `tested_sha`, и его SHA-256.

Одна свежая проба текущего live-деплоя подходит сразу всем задачам, чей `merge_sha` входит в
задеплоенный коммит: контроллер не привязывает probe-run к карточке.

## Порядок финализации одной задачи

1. **Отбор.** Карточка `in_review`, PR слит в `app`, в карточке нет `queued`/`running` run.
2. **Ревью.** Итоговый head PR — `headRefOid` слитого PR. Если в карточке нет завершённого run
   ревьюера с маркером `approved` на этом SHA (или на SHA с тем же патчем) — запросить ревью в этой
   же карточке на этом SHA. Отказ ревьюера — дефект уже в `app`: исправление идёт отдельной задачей
   (журнал §30), финализация этой карточки ждёт.
3. **Итог в `app`.** Если Markdown итога не называет итоговый head или receipt не содержит
   `review`/`pr.merge_sha`, обновить `docs/reports/tasks/<T-ID>.json` и `.md` одним docs-PR
   (пакетно для нескольких задач), включить автослияние и дождаться слияния в следующем проходе.
4. **Проба выкладки.** Для задач, требующих выкладки, один run агента из `release_agent_ids` с
   Render MCP: прогреть `/health` (холодный старт Render дольше 15 секунд), затем `list_deploys` и
   `get_deploy` для сервиса из installed config. Сейчас Render MCP есть только у ревьюера
   (`db94a617`, он входит в `release_agent_ids`); у релиз-инженера (`49314ca0`) его нет с 15.09.
5. **Done.** В течение часа после пробы: взять receipt из `app`, дописать локально
   `deployment.probe_actor_id`/`probe_run_id`, выполнить `controller.py verify`, затем `done`.
   Отказ — записать в карточку один раз вместе с конкретной причиной и не повторять до изменения.

## Вариант (б), рекомендуемый: отдельный автопилот «Altera — приёмка в Done»

| Параметр | Значение                                                                                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Агент    | отдельный, не оркестратор: новый «Altera — финализатор» или перепрофилированный «Altera — контроллер: приёмка» (`933edc82`, сейчас только канарейка фильтра событий) |
| Режим    | `run_only`, project Altera                                                                                                                                           |
| Триггер  | расписание раз в час в :30 — между «очередью» (:00) и «восстановлением» (:15)                                                                                        |
| Права    | чтение Multica/GitHub, запуск ревьюера и пробы в карточке, docs-PR итогов, `controller.py verify/done`; без кода продукта, без ручного `issue status`                |

Текст описания автопилота:

```text
Ты финализатор Altera. Действующий контракт: docs/multica/autonomy-controller.md и
docs/multica/done-finalization.md. Твоя единственная работа — довести до Done задачи в `in_review`,
чей PR уже слит в `app`. Новые задачи не создавай, код продукта не меняй, статусы вручную не ставь.

1. Отбор: карточки проекта в `in_review` с `metadata.task_id`, PR слит в `app`, в карточке нет
   `queued`/`running` run. Сначала самые старые; не больше пяти задач за проход. Остальные карточки
   (открытый PR, конфликт, красный CI) принадлежат оркестратору — не трогай их.
2. Ревью: итоговый head — `headRefOid` слитого PR. Если в карточке нет завершённого run ревьюера
   `db94a617` с последней строкой `ALTERA_REVIEW_V1 … "approved"` на этом SHA, запроси ревью в этой
   карточке на этом SHA. Одновременно в очереди ревьюера — не больше трёх твоих запросов.
   На один (карточка, SHA) — один запрос; второй — только если первый завершился без маркера.
   Вердикт без `approved` не перезапускай: оставь комментарий с дефектами — исправление в `app`
   ставит оркестратор отдельной задачей.
3. Итог: если Markdown итога не называет итоговый head или в receipt нет `review`/`pr.merge_sha`,
   обнови `docs/reports/tasks/<T-ID>.json` и `.md` одним docs-PR на все такие задачи прохода,
   включи автослияние (`gh pr merge <номер> --auto --merge`) и продолжай в следующем проходе.
4. Проба: если хотя бы одна отобранная задача готова ко всему, кроме выкладки, — один run
   агента из `release_agent_ids` с Render MCP в карточке первой такой задачи: прогреть `/health`,
   `list_deploys` и `get_deploy` для сервиса из installed config. Не больше одной пробы за проход.
5. Done: в течение часа после пробы для каждой готовой задачи — receipt из `app` плюс локальные
   `deployment.probe_actor_id`/`probe_run_id`, `controller.py verify`, затем `controller.py done`.
6. Каждое решение по карточке фиксируй одним комментарием с последней строкой
   `ALTERA_FINALIZE_V1 {"task": "<T-ID>", "stage": "<review|receipt|probe|done|blocked>", "sha": "<SHA>", "reason": "<код>"}`.
   Если последний такой комментарий совпадает с текущим состоянием — задачу пропусти молча.

Нет кандидатов или ничего не изменилось — заверши проход одной строкой `no_action`.
В конце укажи только задачи, переведённые в Done, запрошенные ревью, пробы и конкретные блокеры.
```

**Защита от дублей и зацикливания.** Идемпотентность перехода держит ledger контроллера
(ключ `done` + задача + `tested_sha`; бюджет — три попытки). Запрос ревью — не больше одного на пару
(карточка, SHA) плюс один повтор из-за формата; отказ ревьюера не перезапускается. Проба — одна
за проход и только при готовых задачах. Маркер `ALTERA_FINALIZE_V1` делает повтор неизменного
состояния пропуском без действий.

**Взаимодействие.** Оркестратор перестаёт ревьюить и финализировать слитые задачи: в его описание
добавляется строка «Слитые в `app` задачи в `in_review` ведёт автопилот „приёмка в Done“; ты их не
ревьюишь и не финализируешь». Ревьюер и probe-run работают в канонической карточке, как требует
контроллер. Суточный аудит продолжает считать Done по `verified/` контроллера.

## Вариант (а): правило в автопилоте «Altera — очередь разработки»

Блок для описания автопилота и инструкции оркестратора (оба автопилота оркестратора используют один
текст, поэтому правило попадёт и в «восстановление работы»):

```text
Фаза Done (журнал §30). После автослияния задача остаётся в `in_review`, пока не пройдёт
`controller.py done`. Каждый проход, до пополнения очереди: для слитых PR без активных run
запроси ревью на итоговом head слитого PR, обнови итог задачи в `app` отдельным docs-PR, закажи одну
пробу выкладки у агента из `release_agent_ids` и в течение часа вызови `controller.py done`
(порядок — docs/multica/done-finalization.md). Отсутствие поля `deployment_probe` в config не
означает отсутствия проверки выкладки: её доказывает probe-run.
```

## Сопутствующее (нужно в обоих вариантах)

- **Ревьюер**: в 4 из 13 запусков 20–21.09 последняя строка была прозой (уборка worktree, пересказ) —
  одобрение потеряно. В инструкцию ревьюера: уборку и комментарий делать до вердикта, маркер —
  последним действием.
- **Установленный config**: поле `deployment_probe: null` контроллер не читает, а оркестратор
  читал его как «нет проверки выкладки». Убрать поле при следующей установке runtime.
- **Сигнал внимания**: в варианте (б) исключить `in_review` из `launch_assigned_work` в
  `runtime_bridge.queue_attention`, иначе оркестратор каждый час получает ложный сигнал.
- **Ledger**: зависшая запись `running` фазы `done` больше не блокирует задачу навсегда, если карточка
  не в Done (исправлено вместе с этим документом; действует после переустановки runtime).
