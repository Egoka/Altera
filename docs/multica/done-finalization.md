## Зачем

С решения журнала §30 (PR #178, слит 2026-09-20 20:08 UTC) код попадает в `app` автослиянием GitHub
по зелёному CI, а независимое ревью и проверка выкладки проверяются только на переходе в Done.
Инструкции оркестратора описывают ревью как действие перед слиянием («на финальном head — том,
который пойдёт в merge»), а у перехода в Done нет ни владельца, ни триггера, ни порядка шагов.
Итог на 2026-09-21: 43 задачи в `in_review`, последний успешный `controller.py done` — 2026-09-19 15:20 UTC.

## Что проверяет `controller.py done`

Для задачи со слитым PR контроллеру нужны одновременно:

1. карточка в проекте Altera с `metadata.task_id`;
2. receipt: критерии `passed` с evidence, `tested_sha` = `pr.head_sha` = итоговый head PR
   (или head, отличающийся от него только файлами итога задачи), `pr.merge_sha` из GitHub;
3. `review`: завершённый run агента из `reviewer_ids` **в этой же карточке**, последняя непустая
   строка его вывода — `ALTERA_REVIEW_V1 {"sha": "<SHA>", "verdict": "approved"}`; SHA равен
   `tested_sha` или даёт тот же `patch-id` ветки;
4. `deployment` для PR, затронувших `server/`, `packages/`, lock-файлы, `package.json`, `.nvmrc`,
   `render.yaml` (признак вычисляет контроллер, `required: false` в receipt его не отменяет):
   `probe_actor_id` из `release_agent_ids` и `probe_run_id` завершённого run, в сообщениях которого
   есть результат `get_deploy` Render **не старше 3600 секунд** на момент вызова, со статусом `live`,
   коммитом, содержащим `merge_sha`, и ответом `/health` с тем же `revision` (таймаут 15 секунд);
5. `finalization`: Markdown итога в `app`, который содержит Task ID и `tested_sha`, и его SHA-256.

Одна свежая проба текущего live-деплоя подходит сразу всем задачам, чей `merge_sha` входит в
задеплоенный коммит: контроллер не привязывает probe-run к карточке.

## Порядок финализации одной задачи

1. **Отбор.** Карточка `in_review`, PR слит в `app`, в карточке нет `queued`/`running` run.
2. **Ревью.** Итоговый head PR — `headRefOid` слитого PR. Если в карточке нет завершённого run
   ревьюера с маркером `approved` на этом SHA (или на SHA с тем же патчем) — запросить ревью в этой
   же карточке на этом SHA. Отказ ревьюера — дефект уже в `app`: исправление идёт отдельной задачей
   (журнал §30), финализация этой карточки ждёт.
3. **Итог в `app`.** Если Markdown итога не называет итоговый head или receipt не содержит
   `review`/`pr.merge_sha`, обновить `docs/reports/tasks/<T-ID>.json` и `.md` одним docs-PR
   (пакетно для нескольких задач), включить автослияние и дождаться слияния в следующем проходе.
4. **Проба выкладки.** Для задач, требующих выкладки, один run агента из `release_agent_ids` с
   Render MCP: прогреть `/health` (холодный старт Render дольше 15 секунд), затем `list_deploys` и
   `get_deploy` для сервиса из installed config. Сейчас Render MCP есть только у ревьюера
   (`db94a617`, он входит в `release_agent_ids`); у релиз-инженера (`49314ca0`) его нет с 15.09.
5. **Done.** В течение часа после пробы: взять receipt из `app`, дописать локально
   `deployment.probe_actor_id`/`probe_run_id`, выполнить `controller.py verify`, затем `done`.
   Отказ — записать в карточку один раз вместе с конкретной причиной и не повторять до изменения.

## Сопутствующее (нужно в обоих вариантах)

- **Ревьюер**: в 4 из 13 запусков 20–21.09 последняя строка была прозой (уборка worktree, пересказ) —
  одобрение потеряно. В инструкцию ревьюера: уборку и комментарий делать до вердикта, маркер —
  последним действием.
- **Установленный config**: поле `deployment_probe: null` контроллер не читает, а оркестратор
  читал его как «нет проверки выкладки». Убрать поле при следующей установке runtime.
- **Сигнал внимания**: в варианте (б) исключить `in_review` из `launch_assigned_work` в
  `runtime_bridge.queue_attention`, иначе оркестратор каждый час получает ложный сигнал.
- **Ledger**: зависшая запись `running` фазы `done` больше не блокирует задачу навсегда, если карточка
  не в Done (исправлено вместе с этим документом; действует после переустановки runtime).
