# Безопасная очистка после подтверждённого завершения

`scripts/autonomy/cleanup.py` проверяет возможность удаления конкретного собственного worktree и его ветки.
По умолчанию выполняется dry-run. Отсутствующее, устаревшее или неоднозначное доказательство означает `skipped`.
Модуль использует только стандартную библиотеку Python и Git; `rm -rf`, `git clean` и принудительное удаление
worktree не используются.

## Входы и граница доверия

Receipt версии `schema_version: 1` содержит `task_id`, `tested_sha`, `worktree`, `branch`,
`pr.{number,head_sha,base_ref,base_sha,merge_sha,url}` и `finalization.{path,sha256}`.
Полный receipt контроллера может содержать дополнительные поля: они также входят в проверяемый хэш.
Хэш — SHA-256 от UTF-8 JSON с сортировкой ключей, без пробелов и без ASCII-экранирования Unicode.

Одного поля `Done` в тексте агента или receipt недостаточно. Доверенный адаптер контроллера проверяет
актуальные GitHub PR/CI, независимое ревью, deployment по политике и сохранённую финализацию задачи в Git-ветке `app`.
Затем его `read(receipt)` возвращает нормализованные данные:

```json
{
  "observed_at": 1789440000,
  "complete": true,
  "task": {
    "id": "task-id",
    "status": "done",
    "confirmed_done": true,
    "finalized_in_app": true,
    "receipt_sha256": "sha256-of-the-entire-receipt",
    "artifacts": [{ "id": "gitblob:full-git-blob-sha", "sha256": "report-sha256" }]
  },
  "pr": {
    "number": 123,
    "state": "MERGED",
    "head_sha": "full-git-sha",
    "base_ref": "app",
    "base_sha": "verified-pr-diff-base-sha",
    "merge_sha": "actual-merged-commit-sha",
    "url": "https://github.com/owner/repo/pull/123"
  },
  "runs": []
}
```

`observed_at` — Unix seconds фактического чтения внешнего состояния; возраст не больше 60 секунд.
`complete` означает полный список запусков, включая очередь и ожидающие approval, после обработки всех страниц API.
Нельзя подменять время сохранённого снимка временем чтения файла. Для активного постороннего запуска адаптер
передаёт `id`, `status`, `task_id`, `branch`, `worktree`; неполная связь с ресурсами блокирует очистку
(в режиме исключительного fence правило другое, см. «Fence новых запусков»).
Связь с текущей задачей, веткой или вложенным путём блокирует очистку независимо от других полей.
Неизвестный статус также блокирует очистку; его имя попадает в причину.

Адаптер обязан сверять repository/remote и владельца ресурса, а не только номер PR, проверять сохранение
полного receipt вне удаляемого worktree и финального отчёта в `app`. Присваивать `confirmed_done` на основании свободного текста
агента запрещено. Поля выше являются результатом проверки адаптера, а не механизмом удостоверения произвольного JSON.

Живой адаптер — `CleanupEvidence` в `controller.py`. `confirmed_done` он ставит, только когда карточка задачи
в проекте находится в Done и receipt совпадает с итогом, который контроллер сам принял и сохранил в
`<state_dir>/verified/<T-ID>.json`. Пробу выкладки адаптер не повторяет: свежесть пробы — условие перехода
в Done, а не сохранности работы, и через час после Done она законно устаревает. Путь worktree всегда берётся
из `git worktree list` по ветке задачи (ветка открыта не больше чем в одном worktree), а не из поля `worktree`
итога: оно есть не во всех итогах и может устареть. Без `pr.url` подставляется канонический URL PR
репозитория. Итог без `branch` не убирается.

## Fence новых запусков

Все запуски Multica по проекту идут в общей рабочей папке `.worktrees/autopilot`, и демон исполняет в ней
один запуск за раз: остальные ждут в `queued`/`waiting_local_directory`. Уборку вызывает контроллер внутри
такого запуска, под своим `dispatch.lock`. Поэтому, пока она идёт, другой запуск не стартует. Каждое чтение
адаптера это подтверждает, а не предполагает:

- перечисляются незавершённые запуски всех агентов workspace (`multica agent list --include-archived`,
  `multica agent tasks`), запуски карточек связываются с `metadata.task_id`;
- запуск вызывающего агента (`MULTICA_AGENT_ID`) должен однозначно найтись среди исполняемых;
- любой другой исполняемый запуск (`running`, `starting`, `dispatched`, `claimed`) блокирует уборку: fence
  не исключителен;
- ожидающий запуск этой же задачи блокирует уборку: доработке нужен её worktree. Ожидающие запуски других
  задач и автопилотов стартуют только после вызывающего и уборке не мешают;
- без `MULTICA_AGENT_ID` (ручной вызов вне запуска) общую папку никто не занимает, и ожидающий запуск может
  стартовать сразу: тогда уборка требует, чтобы незавершённых запусков в workspace не было вовсе;
- `lsof` не должен находить процесс с текущим каталогом внутри worktree: так защищены интерактивные сессии
  и dev-серверы вне Multica. Неизвестный результат `lsof` блокирует уборку.

Время свежести фиксируется перед чтением запусков и процессов. Guard адаптера проверяет, что
`dispatch.lock` занят; адаптер создаётся только под ним. Граница по-прежнему `managed_path_only`: агент
с доступом к shell может нарушить порядок вручную, а вызывающий запуск опознаётся по агенту, а не по
execution ID. Данных при этом не теряется: удаляется только чистый worktree, вся работа которого уже в
истории `app`.

## Запуск

Контроллер убирает worktree сам после успешного `controller.py done`, в том числе при сверке уже
выполненного Done, и под тем же `dispatch.lock`. Результат попадает в вывод `done` полями `cleanup` и
`cleanup_pending` и никогда не меняет результат Done.

Затем `done` досматривает до двух других принятых итогов, чьи worktree ещё открыты: уборка могла быть
отложена из-за чужого запуска. Бюджет `cleanup_budget_seconds` (по умолчанию 45 секунд от начала уборки после
Done) мягкий: он проверяется перед предпроверкой fence и перед каждым следующим итогом, а начатая уборка итога
доводится до конца. Предпроверка fence одна: если сейчас исполняется чужой запуск, досборка откладывается
целиком, а не тратит полное чтение на каждый итог. Кандидаты берутся в порядке давности последней
попытки (`<state_dir>/cleanup-attempts.json`), поэтому итоги, которые постоянно пропускаются (например, из-за
`.env` в worktree), не загораживают остальные.

Отдельная досборка — `controller.py cleanup --config <installed-config>`, по умолчанию до пяти итогов за
вызов (`--limit N`). С `--dry-run` она ничего не удаляет и показывает по живым доказательствам, что и почему
было бы удалено: так стоит начинать после установки. Проверки fence идут раньше Git-проверок, поэтому
пробный прогон из терминала при непустой очереди Multica покажет у всех итогов причину fence; Git-причины
видны, когда очередь пуста. `done` и `cleanup` вызываются из Bash-инструмента агента с таймаутом не меньше
10 минут: полное чтение запусков всех агентов занимает секунды, а прерванный `git worktree remove` оставляет
полуудалённый worktree, который потом пропускается как грязный и разбирается вручную.

Уборка включается ключом `cleanup_owned_root` в установленном конфиге (каталог `.worktrees`). Пути из
`cleanup_protected_worktrees` (общая рабочая папка `.worktrees/autopilot`) не удаляются, даже если окажутся
на ветке принятой задачи. Журнал пишется в `cleanup_log_dir`, который должен лежать вне всех worktree,
включая основной checkout. Если после удаления worktree поменялась ветка и результат `partial`, локальная ветка
остаётся: досборка смотрит только ветки, открытые в worktree, и такую ветку разбирают вручную.

Снимок используется для проверяемого предварительного результата:

```bash
python3 scripts/autonomy/cleanup.py \
  --repo /absolute/path/to/repository \
  --owned-root /absolute/path/to/owned-worktrees \
  --receipt /absolute/path/to/receipt.json \
  --activity-json /absolute/path/to/fresh-activity.json \
  --log-dir /absolute/path/outside/worktrees/cleanup
```

CLI со снимком и `--apply` возвращает `skipped` с exit code 2: повторное чтение JSON не подтверждает живое состояние.
Фактическую очистку вызывает контроллер с живым адаптером:

```python
result = cleanup(
    repo,
    verified_receipt,
    live_evidence_provider,
    owned_root=owned_worktrees,
    log_dir=durable_cleanup_directory,
    apply=True,
)
```

Для `apply=True` требуются `provider.live = True`, `provider.read(receipt)` и context manager
`provider.guard(receipt)`. Guard держит запрет новых dispatch на задачу, ветку и путь на всё время очистки.
Эта блокировка должна соблюдаться всеми компонентами, способными поставить работу в очередь; если такую
гарантию невозможно дать, адаптер не предоставляет guard и удаление остаётся недоступным.
Повторное чтение само по себе не устраняет гонку с новым запуском.

## Проверки и действия

Сначала проверяются принадлежность пути настроенному `owned_root`, отсутствие symlink во всех компонентах
пути, запись worktree в Git и точное совпадение ветки/HEAD. Основной checkout, текущий checkout, checkout
вызывающего процесса, защищённые ветки `app`, `main`, `master`, `develop`, `dev` и чужие worktree сохраняются.
Заблокированные, prunable и submodule worktree требуют отдельного подтверждения и не удаляются.

Git status проверяет tracked, untracked и ignored файлы. `assume-unchanged` и `skip-worktree` блокируют очистку,
поскольку могут скрыть незаписанные изменения. Незакоммиченный отчёт должен быть разобран отдельно.
Из игнорируемого допускаются только воспроизводимые артефакты: каталоги `node_modules`, `.nuxt`, `.output`,
`dist`, `test-results`, `coverage` на любой глубине и пути `server/src/generated/`, `.husky/_/`, `server/.storage/`
(зависимости, сборка, кодогенерация, хуки и локальное хранилище разработки). Они есть в каждом рабочем worktree
и удаляются вместе с ним. Любой другой игнорируемый файл, например `.env`, блокирует очистку: модуль не удаляет
его в обход защиты.

С 2026-09-19 PR сливаются обычным merge-коммитом (решение владельца): его второй родитель обязан совпасть
с проверенным head, а сам merge-коммит — присутствовать в `origin/app`; live адаптер подтверждает его серверную
принадлежность PR. Тогда все коммиты ветки сохранены в истории `app` по SHA, и удаление refs ничего не теряет.
Сверка diff от базы PR для такой формы не выполняется: ветку не догоняют до `app` перед merge (решение
владельца 2026-09-19), поэтому база PR законно не бывает предком head, а diff merge-коммита идёт от новой
вершины `app`. По итогам задач в `app` на 2026-10-01 строгая сверка отклоняла 34 из 110 слитых PR,
новое правило принимает все 34.
Ранее слитые squash-коммиты с одним родителем тоже поддерживаются, но head не становится предком `app`:
для них сверяется полный binary diff от подтверждённой базы PR до проверенного head с diff от первого родителя
до самого коммита, включая полные blob SHA, режимы файлов, пути и удаления. Неоднозначная база, пустой diff,
неподдерживаемая форма merge или расхождение дают `skipped`.

Перед удалением берутся общий Git-lock `<git-common-dir>/autonomy-cleanup.lock` и dispatch guard, повторно
читаются живые доказательства, проверяются пути, файлы и ветки. После durable записи намерения выполняется
`git worktree remove` без force. Затем заново проверяются live evidence и обе ветки. Remote-ветка удаляется
с явным `--force-with-lease=<ref>:<expected-sha>`; локальная — `git update-ref -d <ref> <expected-sha>`.
Обе операции сравнивают ожидаемый SHA, поэтому новая версия ветки сохраняется. При изменении состояния после
первого действия результат будет `partial`, а оставшиеся действия остановятся.

Общая блокировка предотвращает конкуренцию экземпляров cleanup даже при разных каталогах журнала. Защита
рассчитана на соблюдающий guard контроллер и обычные Git-операции; произвольная конкурентная запись в файловую
систему сторонним процессом не является транзакцией с внешним API. Передача guard без реальной блокировки
делает интеграцию небезопасной.

До 2026-10-01 живой apply-адаптер не подключался: не была подтверждена общая точка допуска запусков, и
доступен был только dry-run. Владелец выбрал довести fence до конца; общей точкой допуска служит
последовательная рабочая папка Multica, а исключительность проверяет каждое чтение адаптера
(«Fence новых запусков» выше). Снимок JSON по-прежнему годится только для dry-run.

Журнал `cleanup.jsonl` находится вне всех worktree. В нём сохраняются время, SHA receipt/evidence/финализации,
task/PR/head/merge/path/branch, намерение, выполненные действия и причина результата. Записи и каталог проходят
`fsync`; невозможность записать намерение блокирует удаление. Секреты и raw output внешних команд не сохраняются.
Полный receipt сохраняет контроллер вне удаляемого worktree, а отчёт остаётся в `app`.
`finalization.path` — относительный путь внутри `docs/reports/` без `..`. Модуль читает точные байты через
`git show origin/app:<path>`, проверяет SHA-256, наличие `task_id` и `tested_sha`, а затем сопоставляет Git blob SHA
с `task.artifacts[].id` в формате `gitblob:<sha>`. Проверка повторяется перед удалением и перед удалением веток.
Обновлять или принудительно сбрасывать локальную `app` не требуется; актуальность `origin/app` обеспечивает live адаптер.

## Runtime и daemon GC

Runtime-каталоги Multica не являются обычными собственными Git-worktree. Модуль возвращает для них
`runtime_gc.status = unsupported`: адаптер native GC здесь не настроен, ручного удаления runtime не происходит.

В upstream Multica предусмотрен daemon GC с `MULTICA_GC_ENABLED`, `MULTICA_GC_INTERVAL`, `MULTICA_GC_TTL`,
`MULTICA_GC_COMPLETED_TASK_TTL`, `MULTICA_GC_ORPHAN_TTL`, `MULTICA_GC_ARTIFACT_TTL`.
Версию установленного daemon и фактическую поддержку нужно сверять отдельно с
[исходником config.go](https://github.com/multica-ai/multica/blob/main/server/internal/daemon/config.go) и
[исходником gc.go](https://github.com/multica-ai/multica/blob/main/server/internal/daemon/gc.go).
Native GC опирается на terminal status, что само по себе не равно подтверждённому receipt контроллера.
До принудительного применения этой политики завершения native retention оставляется без изменений:
сокращать TTL для немедленной очистки небезопасно. Для инвентаризации применяют поддерживаемую установленной
версией команду `multica daemon disk-usage --all-profiles --output json`.

## Проверка

```bash
python3 -m unittest discover -s scripts/autonomy -p 'test_cleanup.py'
python3 -m unittest discover -s scripts/autonomy -p 'test_controller.py'
```

Тесты создают временные Git-репозитории и локальный bare remote. Они проверяют успешные merge-коммит и squash, ошибочный diff,
merge после параллельного изменения `app`, изменения refs и файлов между чтениями, активные/queued runs, исключительный
fence и процесс внутри worktree, stale evidence, app artifact, текущий/main checkout, symlink, untracked/ignored/скрытые
индексом изменения, воспроизводимые артефакты, общий lock и отказ snapshot CLI от apply. Тесты контроллера проверяют
адаптер `CleanupEvidence`, уборку после Done и досборку, а сквозной тест — адаптер вместе с настоящим `cleanup.py`.
Внешний API заменён адаптером теста; это не проверка живой интеграции GitHub/Multica.
