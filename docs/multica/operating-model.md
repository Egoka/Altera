# Операционная модель Multica для Altera

- **Статус**: подготовлено 2026-09-09 к проверке владельцем; автопилоты на паузе, задачи в
  Multica не созданы
- **Назначение**: правила, по которым сквад «Altera — автономная разработка» читает задачи из
  `docs/backlog/`, передаёт работу между стадиями, фиксирует доказательства и восстанавливает
  остановленную работу. Документ описывает **правила**, а не текущее состояние очереди: списки
  задач, расписания и назначения живут в Multica и в `docs/backlog/`, здесь не копируются.
- **Источники**: рабочий журнал решений `docs/decisions/role-review-working-log-2026-09-08.md`
  (главнее всего), `docs/spec/`, `docs/backlog/README.md`, `CLAUDE.md`. Продуктовые решения
  принимает только владелец; эта модель их не меняет.

## 1. Сквад и границы ответственности

Один сквад из десяти агентов. Роль агента и его расписание меняются только решением владельца;
агент не переназначает роли другим агентам и не создаёт новых агентов.

| Роль | Делает | Не делает |
|---|---|---|
| **Оркестратор** | ведёт очередь и зависимости по `docs/backlog/`; проверяет, что задача явно готова; назначает стадии; фиксирует единственную активную кодовую цепочку; останавливает работу при конфликте | не пишет продуктовый код; не меняет scope задачи; не принимает продуктовых решений; не создаёт задачи без источника |
| **Архитектор** | проектирует техническое решение задачи в границах спецификаций: схема данных, контракты GraphQL, модули, миграции; пишет технический план стадии; отвечает на «как», не на «что» | не реализует за разработчика; не меняет продуктовые правила; не задаёт числовых параметров, отсутствующих в журнале, без пометки `[ДОПУЩЕНИЕ]` и вопроса владельцу |
| **Разработчик** | реализует задачу по спецификации и техплану; пишет тесты уровня задачи; ведёт план и отчёт по ритуалу проекта | не расширяет scope; не правит спецификации и журнал; не трогает чужую активную ветку |
| **Тестировщик** | готовит проверки по критериям готовности заранее (параллельно), исполняет их после реализации, фиксирует результат командой и выводом | не «чинит» код сам; не подтверждает готовность без выполненной проверки |
| **Независимый ревьюер** | проверяет результат против источников задачи (журнал, спецификация, ADR), границ и критериев; ищет отклонения, скрытые решения и придуманные параметры | не участвует в реализации той же задачи; не утверждает продуктовые изменения |
| **Хранитель документации** | поддерживает `docs/backlog/`, `docs/issues/`, статусы ADR, спецификации в актуальном состоянии по результату задач; пишет ADR-0047+ по журналу | не принимает решений от имени владельца; не редактирует текст ADR и журнал; не трогает заметки владельца |
| **Дизайнер** | макеты и состояния по `docs/spec/20-public`, `30-account`, `40-admin` и `docs/vision/06-design-system.md`; токены и компоненты | не меняет состав страниц и матрицу прав |
| **Редактор и бренд-стратег** | тексты интерфейса и публичных страниц, тон, правила публикации в общей формулировке (журнал §24.3) | не публикует пороги проверки; не пишет юридические тексты за владельца |
| **SEO-специалист** | hreflang, sitemap, rss, OG, JSON-LD, `robots.txt` (включая запрет обучения ИИ, §24.2), `noindex` служебных страниц | не влияет на рейтинг и выдачу (журнал §21) |
| **Релиз-инженер** | сборка, CI, миграции при релизе, бэкапы и проверка восстановления, health, выкладка после завершённой цепочки | не выкладывает без независимого ревью и актуальной проверки; не хранит секреты в репозитории |

## 2. Как читать задачу

1. Задача — один файл `docs/backlog/tasks/T-NNN-*.md`. Она обязана читаться без чата: результат,
   источники, границы, зависимости, роли, навыки, критерии, доказательство, статус,
   параллельность (`docs/backlog/README.md` §3).
2. Перед началом агент открывает: этот документ, `docs/backlog/README.md`, файл задачи, её эпик и
   **все** источники из раздела «Источники» задачи. Спецификация главнее пересказа в задаче; журнал
   главнее спецификации.
3. Если задача ссылается на `Q-NN` (блокер владельца) или в её источниках встречается «отложено»
   или `[ВОПРОС ВЛАДЕЛЬЦУ]` по существу задачи — работа не начинается; агент возвращает задачу
   оркестратору с пометкой «требует решения владельца».
4. Всё, что не подтверждено кодом или спецификацией, помечается `[ДОПУЩЕНИЕ]` в отчёте стадии.
   Придуманные числа, провайдеры, цены и правила запрещены.

## 3. Стадии и передача работы

Порядок стадий одной задачи: **архитектура → разработка → тестирование → независимое ревью →
документация → релиз**. Стадии, не указанные в задаче, пропускаются. Каждая стадия завершается
записью evidence, без которой следующая стадия не начинается.

| Стадия | Вход | Выход (evidence) |
|---|---|---|
| Архитектура | задача, спецификации | техплан в `docs/plans/ГГГГ-ММ-ДД-<slug>.md` с базовым коммитом (ритуал `CLAUDE.md`), перечень затрагиваемых файлов, миграции с именами |
| Разработка | техплан | коммиты в ветке `server/*` или `web/*` (docs — `docs/*`), тесты задачи, отчёт `docs/reports/…-report.md` с «Как проверено» |
| Тестирование | критерии готовности задачи | выполненные команды и их вывод, результат по каждому критерию: «выполнен / не выполнен» |
| Независимое ревью | коммиты, отчёт, источники | заключение: соответствие журналу и спецификации, найденные отклонения, вердикт «принято / вернуть» |
| Документация | вердикт «принято» | обновлённые статусы в `docs/backlog/`, спецификации/ADR-статусы при необходимости |
| Релиз | всё выше | запись о выкладке, проверка health, при миграциях — репетиция на копии |

Правила передачи:

- Стадия передаётся дальше только с evidence в репозитории (план, отчёт, вывод команд, вердикт).
  Утверждение «работает» без выполненной проверки не является evidence.
- Возврат на предыдущую стадию оформляется записью в отчёте задачи с причиной; повторный проход
  стадии — новая запись, старая не удаляется.
- Задача завершена, когда выполнены все указанные в ней стадии, критерии проверены актуально
  (после последнего коммита), независимое ревью дало «принято» там, где оно требуется, и статус
  в `docs/backlog/` обновлён хранителем документации.

## 4. Формат готовой задачи

Задача может быть взята очередью только при одновременном выполнении условий:

1. Статус в файле задачи — `готова`. Значение ставит **только владелец** (или оркестратор по
   явному письменному подтверждению владельца для конкретной задачи). Значение `кандидат` — это
   предложение, а не готовность.
2. Все зависимости из раздела «Зависимости» имеют статус `завершена`.
3. Раздел «Требует решения владельца» содержит «нет» либо ссылку на закрытый `Q-NN`.
4. Критерии готовности сформулированы проверяемо (команда, тест, артефакт), а раздел
   «Доказательство» указывает, чем подтверждается результат.
5. Указаны роль-исполнитель и участники стадий.
6. Указана параллельность: `нет: меняет продуктовый код` или `да` с условием.

Очередь не создаёт задач и не угадывает scope: если условия не выполнены, задача не берётся,
и оркестратор фиксирует причину.

## 5. Параллелизм, единственный writer, восстановление

- **Один writer продуктового кода.** В каждый момент времени только одна активная цепочка
  меняет код в `server/`, `web/` и `packages/`. Вторая кодовая задача не стартует, пока первая не
  завершена или явно остановлена оркестратором с записью.
- **Параллельно допускаются** анализ, архитектура, документация, дизайн и подготовка тестов —
  если они не создают конфликтующих изменений в одних и тех же файлах и не требуют ещё не
  существующего кода. Параллельность задачи указана в её шапке.
- **Повторный запуск запрещён.** Перед стартом стадии агент проверяет, что та же задача и стадия
  не выполняются другим агентом (по записям очереди и активной ветке). Дубликат прекращается,
  не доводится до коммита.
- **Бюджет попыток стадии.** Две подряд неуспешные попытки одной и той же проверки внутри стадии
  останавливают работу: агент прекращает итерации и возвращает стадию с описанием причины, что
  именно проверялось, что менялось между попытками и каким был вывод. Попытки считаются по
  конкретной проверке, а не по стадии в целом: успешная проверка обнуляет счёт для себя.
  Правило применяется вместе с остановом по конфликту (ниже) и по вопросу владельцу (§7) —
  срабатывает то, что наступит раньше. Параметр подтверждён владельцем 2026-09-09; других
  числовых ограничений (таймаутов, лимитов на число задач, общего лимита итераций) не задано,
  и агент их не вводит.

- **Остановленная работа** восстанавливается только при трёх условиях: стадия реально
  остановлена (нет активного агента и незакрытой ветки в работе), конкретная причина остановки
  названа и устранена, восстановление затрагивает именно эту стадию. Восстановление не переходит
  к следующей задаче и не меняет scope.
- **Конфликт** (две цепочки затронули одни файлы, спецификация противоречит журналу, задача
  требует незафиксированного решения) — работа останавливается, вопрос уходит владельцу
  через `docs/backlog/owner-blockers.md`, а не решается по месту.

## 6. Контракт трёх автопилотов (все на паузе)

| Автопилот | Читает | Может менять | Никогда |
|---|---|---|---|
| **Актуальность контекста** | журнал, `docs/spec/README.md`, `docs/backlog/README.md`, статусы задач, последние отчёты | только подтверждённый обзор проекта (раздел «Текущее состояние» в `docs/backlog/README.md`), фиксируя источник и дату | не меняет спецификации, журнал, ADR, задачи, роадмап; не добавляет фактов без источника |
| **Восстановление работы** | очередь, evidence остановленной стадии, причина остановки | возобновляет **только** реально остановленную стадию после устранения конкретной причины; пишет запись о возобновлении | не берёт новую задачу; не меняет scope; не повторяет идущую работу; не снимает блокер владельца |
| **Очередь разработки** | `docs/backlog/tasks/*`, `matrix.md`, статусы зависимостей | берёт **только** существующую задачу со статусом `готова`, закрытыми зависимостями и проверяемыми критериями; назначает стадии по задаче | не создаёт задач; не угадывает scope; не запускает вторую кодовую цепочку; не ставит `готова` |

Включение каждого автопилота — отдельное решение владельца по чек-листу
`docs/multica/autopilot-checklists.md`.

## 7. Действия, требующие решения владельца

- Любое продуктовое правило, число, лимит, цена, провайдер, срок или роль, отсутствующие в
  журнале и спецификациях.
- Перевод задачи в статус `готова`; закрытие `Q-NN`; переоткрытие гейта Г1–Г9.
- Изменение состава сквада, ролей, расписаний и настроек автопилотов; включение автопилота.
- Выкладка в прод; включение платности; внешние интеграции с реальными провайдерами.
- Необратимые операции с данными (журнал #1, #49); удаление файлов документации.
- Push в удалённый репозиторий и слияние в `app` (по правилам `CLAUDE.md` — через pull request).
- Правка журнала решений и текста ADR; редактирование рабочих заметок владельца.

## 8. Актуализация контекста

1. Источник истины по решениям — журнал; по поведению — `docs/spec/`; по состоянию кода —
   код и `docs/vision/00-reality-check.md` с датой среза; по порядку работ — `docs/issues/00-roadmap.md`
   и `docs/backlog/`.
2. После завершения задачи хранитель документации обновляет её статус, `matrix.md` и раздел
   «Текущее состояние» в `docs/backlog/README.md`; если задача изменила поведение относительно
   спецификации — это отклонение фиксируется в отчёте и возвращается владельцу.
3. Обзор проекта («Текущее состояние») содержит только подтверждённые факты со ссылкой на
   коммит или отчёт; агент, обновляющий обзор, не выводит состояние из планов.
4. `CLAUDE.md` содержит правило и ссылку на этот документ; изменчивые списки в него не копируются.
