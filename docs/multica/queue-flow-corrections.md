# Движение очереди без потерянных передач

После merge применяется [продолжение и освобождение слота](post-merge-continuation.md):
оркестратор сам выставляет native Done после подтверждённого завершения исполнения.

Согласованное владельцем уточнение от 2026-09-14 заменяет прежнюю связь «Todo только при
свободном parent». Admission готовой задачи и запуск её исполнения — разные действия.
Условия источников, AC, закрытых зависимостей, Q/F-блокеров и проверка дублей сохраняются.

## Три независимые части прохода

1. **Подготовка Todo.** Читать актуальные `docs/backlog/tasks` из зафиксированного `origin/app`,
   проверить источники и уже выполненное. Дополнить запас до трёх подходящих Todo даже при
   занятом writer, ожидающем review или PR. Существующие готовые Todo учитываются в запасе;
   для каждого нового кандидата отдельно проверяются готовность и отсутствие дубля.
   Допуск не обязан ждать завершения чужой
   задачи, если кандидат от неё не зависит. Реальная незакрытая зависимость по-прежнему блокирует.
   Создание — `backlog` без assignee/mentions, затем `todo --no-start`; существующая запись
   обновляется без запуска. Очередь пишет только native issue/metadata, а не рабочие файлы repo.
2. **Передача и восстановление.** Проверить незавершённые parent на готовый результат без
   следующей стадии. При необходимости восстановить одну подтверждённую передачу тому же
   лидеру; это не новая кодовая цепочка. Проблема отдельного parent не отменяет admission.
3. **Запуск.** Только при подтверждённо свободном слоте и повторной проверке готовности
   назначить одну Todo squad. При занятом слоте оставить подготовленную Todo ждать без assignee
   агента/squad. Не отправлять mention, rerun или assignment ради её подготовки.

При сбое чтения/записи admission зафиксировать ошибку и продолжить независимое чтение
handoff, если его входы доступны. Не выдавать сетевой сбой за отсутствие кандидатов.
Глобальный no-op до проверки подготовки Todo запрещён. Лимит одного writer ограничивает
исполнение; подготовленная очередь пополняется до трёх готовых задач, без массового импорта backlog.

## Подтверждённая передача

Исполнитель после результата сохраняет в исходном parent T-ID, стадию, свой run ID, branch,
baseline, output SHA, dirty paths, план/отчёт, выполненные проверки, остаток и ожидаемый
следующий шаг. Пишет результат через штатное событие/адресованный лидеру комментарий:
просто финальный текст model run или неадресованное «готово» не подтверждает доставку.

Сначала проверить, не доставил ли native механизм этот результат автоматически, по ключу
перехода. Порядок обязателен: связанный queued/dispatched/running/waiting_local_directory run —
не дублировать; completed — лидер обрабатывает его новый результат; failed/cancelled —
диагностика по прежним правилам. Существующий event/comment ID без run требует readback,
затем `handoff_pending` либо `delivery_unknown`, а не повторной отправки.
Только если для ключа нет event/run и недоставка подтверждена, отправить один адресованный
callback лидеру по актуальному roster. Сохранить возвращённый event/comment ID; однократно
сверить native историю и ID связанного run. Если run ещё не появился, сохранить pending;
при следующем просмотре снова применять порядок выше, не отправлять callback заново.
Не объявлять доставку завершённой без подтверждения и не ждать в цикле.

Лидер после принятия результата выбирает следующий шаг и отправляет ровно одну делегацию.
Запись `handoff` в metadata содержит task/stage/output_sha/source_run_id, next_stage,
event_id, next_run_id (если получен), state и причину ожидания. Заполненное описание роли
само по себе не заменяет реальный native ID. `queued` и `waiting_local_directory` подтверждают
назначение, но не начало работы и не прохождение стадии.

После локального исправления порядок: публикация новой ревизии релиз-инженером в существующий
PR → актуальные CI и повторное независимое ревью → merge релиз-инженером. Можно начать review
локального SHA параллельно чтению CI, но merge требует актуальной полной приёмки итогового SHA.
Новый commit отчёта тоже явно учитывается в финальной проверке; старое review не переносится молча.
Оркестратор/очередь не заменяют релиз-инженера и сами merge не выполняют.
Автоматическое Done после приёмки и финализации определяется post-merge-continuation.

## Восстановление отсутствующей следующей стадии

Очередь и recovery смотрят не только `failed` и `waiting_ci`. Признак для сверки: последний
run исполнителя completed, результат/коммит существует, parent ещё не завершён, а следующего
активного run или принятого результата нет. Проверять также локальный HEAD против remote/PR:
готовое локальное исправление со старым PR SHA требует публикации, а не нового создания задачи.
Отсутствие `delivery_state`, PR или `handoff` у старой задачи не скрывает её от восстановления.

Реконструировать из native истории, комментариев и артефактов факт, SHA и следующий шаг.
Неизвестные данные не выдумывать. Проверять run всего parent, его подзадач и ожидаемого
исполнителя; queued/dispatched/running/waiting_local_directory не перезапускаются.
Проверять не только наличие ID, но его текущее состояние: завершённый run уже не активен.
Если следующий run completed, проверить его результат и продолжить от него, а не повторять
предыдущую делегацию; если failed/cancelled, применить прежние правила диагностики и бюджет.

Ключ передачи: parent + завершённая стадия + source_run_id + output SHA + следующий шаг.
Перед отправкой повторно проверить состояние. Если соответствующее событие/run уже есть,
использовать его. При неопределённом ответе сверить историю; если исход невозможно установить,
записать `delivery_unknown` и блокер доставки вместо повторной отправки.
Отсутствие нового события после подтверждённого недоставленного результата допускает одно
восстановление; сохранить ключ и ID результата. Старый ключ не снимается только по возрасту.
Изменение output SHA или следующий подтверждённый результат создаёт новый переход, не новый parent.

Ручной Blocked/Cancelled, ALTE-11, неустранённая причина ошибки и исчерпанный бюджет попыток
не обходятся. Recovery не заполняет Todo — admission принадлежит только очереди.

## Отдельная ветка и PR

Точный порядок получения свежей базы и создания worktree определён в [fresh-task-worktree](fresh-task-worktree.md).

Для каждой новой T-задачи после допуска к исполнению создать отдельную ветку от свежего
`origin/app`, с T-ID в имени, и сохранить baseline в parent. Один T-ID — одна ветка — один PR.
Нельзя продолжать новую задачу в накопленной ветке прежних задач или включать чужой diff.
Проверить чистоту выделенного checkout перед переключением; при чужих правках не применять
reset/clean/stash. Выделить отдельный checkout с явно записанным путём или зафиксировать
блокер запуска; подготовленная Todo при этом не теряется. Стадии одной задачи используют
один согласованный branch/checkout и неизменные ссылки на parent.

Текущий общий PR #26 — историческое исключение: его не разделять и не переписывать вслепую.
Завершить исправления и приёмку всех включённых частей, затем интеграцию и финализацию.
Новые задачи в эту ветку не добавлять. Он не препятствует подготовке независимых Todo.

## Наблюдаемый результат прохода

Каждый run очереди завершает краткой фактической сводкой:

- `todo_outcome`: created / promoted / already_ready / no_eligible / error; T-ID/native ID
  или проверяемая причина. Для no_eligible указать проверенные кандидаты и блокеры.
- `handoff_outcome`: recovered / already_delivered / active / none / error; parent,
  output SHA, event/run ID либо точный пробел в доказательствах.
- `dispatch_outcome`: started / busy / no_ready / error; ID запуска или причина ожидания.

Отсутствие Todo не означает отсутствие запуска; completed run не доказывает успешный admission.
Частота расписаний не меняется. Эти правила управляют native агентами инструкциями и readback;
это не утверждение о технической изоляции или exactly-once гарантиях экспериментального M4.
