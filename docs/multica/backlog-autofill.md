# Пополнение Todo из файлов backlog

Решение владельца 2026-09-14: «разрешим брать задачи из docs/backlog/tasks и формировать их
в TODO для выполнения новых». Это действующее разрешение для очереди разработки и оркестратора.
Оно заменяет прежнее ограничение «только владелец ставит готова/Todo» и ограничение первого
старта одной ALTE-10. Остальные полномочия, стадии и ограничения сохраняются.

## Источник и допуск

Источник новой работы — только существующий `docs/backlog/tasks/T-NNN-*.md` в актуальной
согласованной ветке `app`. Перед выбором получить свежий remote ref штатным `git fetch`,
прочитать файл из `origin/app` и записать SHA и путь. Не переключать рабочее дерево поверх
изменений и не сбрасывать его. Если источник недоступен, новую работу не назначать.

Допускаются `готова`, `кандидат` и `зависит: T-…`, если фактические зависимости уже завершены.
Надпись в старом индексе сама по себе ни готовность, ни завершение не доказывает. Проверить:

- Результат, scope, источники, роль и обязательные стадии явно определены, критерии проверяемы.
- Открыты все обязательные ссылки из источников, результата, AC и зависимостей. Файлы
  репозитория читаются на том же зафиксированном SHA. Отсутствующая, недоступная или
  неоднозначная обязательная ссылка означает отказ в Todo с точным блокером; её содержание
  не восстанавливается догадкой по заголовку.
- Все зависимости, в том числе скрытые в критериях, подтверждены отчётами и обязательным
  независимым review; при требуемом merge — merged PR и успешными обязательными CI checks
  проверенной ревизии. Один `completed` run или зелёный CI без приёмки задачи недостаточен.
- Нет открытого Q-блокера, неутверждённого решения по существу scope или отложенного этапа F.
  Ссылка на Q в разделе «не входит» не блокирует только когда результат, AC, зависимости,
  обязательные шаги реализации и evidence от этого решения не зависят. Иначе это блокер.
- Работа ещё не выполнена и не ведётся: сверить native issue, run, PR и отчёты. Устаревший
  файл не разрешает повторную реализацию. При частичной реализации в issue точно отделить
  выполненное от остатка, сохранив исходные AC. Если выполнено всё, новую задачу не создавать.

Расхождения трактовать явно: успешный merged результат в In Review не реализовывать заново;
проверить требуемую финализацию перед признанием зависимости закрытой. Если доказательств
недостаточно, пропустить зависимый кандидат, а не объявлять его готовым. Нативный Blocked,
Cancelled или ручная остановка не снимаются пополнением очереди. ALTE-11 не возобновляется.

Готовность для такого допуска фиксируется оркестратором в native issue: источник разрешения,
T-ID, путь, SHA, результаты проверки зависимостей и блокеров. Отметка владельца в файле не
требуется. Статусы файла и индексов синхронизируются в рамках той же задачи по обычному
ритуалу; сам короткий run очереди продуктовый код и файлы backlog не переписывает.

## Один проход очереди

Перед обычным выбором или no-op проверить ожидающую интеграцию текущего parent по
[правилу PR/merge](pr-auto-merge.md). Это продолжение той же цепочки, а не допуск новой задачи.

1. Перечитать весь список issue проекта с пагинацией, активные run и незавершённые стадии.
   Пока одна implementation parent занята, новая цепочка не запускается. In Review освобождает
   её только после доказанного завершения всех обязательных стадий и финализации.
2. Сначала использовать готовую Todo. Если подходящей Todo нет и цепочка свободна, выбрать
   одну допустимую задачу по зависимостям, приоритету и порядку roadmap/ready-candidates;
   при равенстве — по T-ID. Просмотр списка не означает массовый импорт всего backlog.
3. Искать существующую native issue по точному T-ID, пути источника и metadata во всех статусах.
   Проверять в том числе архивные записи, если они доступны отдельно. При неоднозначности
   не создавать ещё одну. Предпочитать существующую issue, сохраняя её обсуждение и вложения.
4. Для отсутствующей issue создать обычную задачу проекта Altera со ссылкой на файл,
   исходными AC, остатком работы, ролью и доказательствами допуска. `issue create` выполнять
   со статусом `backlog`, без assignee и без активных mentions (у create нет `--no-start`).
   Подготовленную issue переводить командой `issue status <id> todo --no-start`; обновления
   существующей записи также выполнять без старта. Это parent реальной T-задачи, а не
   служебная задача самого расписания. Не использовать `--allow-duplicate`.
5. Сохранить metadata `backlog_task_id`, `backlog_source_path`, `backlog_source_revision`,
   `backlog_admission` через штатные команды. Путь и T-ID также обязательны в описании:
   они позволяют восстановить соответствие, если запись metadata прервётся.
6. При таймауте/неопределённом результате записи перечитать issue и поиск по T-ID; не повторять
   создание вслепую. Перед dispatch снова проверить слот, отсутствие дубликата и готовность.
   Назначить эту issue существующей squad один раз: назначение само запускает лидера.
7. Завершить run. Следующие стадии идут по событиям Multica. Без новой информации — тихий
   no-op; новый существенный блокер сообщается один раз. Сетевые ошибки не обходятся выдуманным
   успехом, циклов ожидания внутри run нет.

Расписание очереди остаётся почасовым. Правила Done не изменены: человек или действующая
интеграция. Наличие права пополнять Todo не разрешает придумывать задачи, менять продуктовые
решения, отменять блокеры владельца, делать покупки или посылать внешние сообщения.

## Какие документы полезны для очереди

| Материал | Для чего читать |
| --- | --- |
| `docs/backlog/tasks/`, `epics/`, `matrix.md` | Точный scope, роли, зависимости и критерии выбранного T-ID; индекс сверять с файлом |
| `docs/backlog/ready-candidates.md`, `docs/issues/00-roadmap.md` | Порядок работ; исторический список не считать текущей очередью |
| `docs/backlog/owner-blockers.md`, `docs/spec/OPEN-QUESTIONS.md`, `docs/backlog/future-stages.md` | Исключить нерешённые и отложенные части |
| `docs/decisions/role-review-working-log-2026-09-08.md` и источники конкретной задачи | Проверить решения владельца; затем нужные спецификации и ADR |
| `docs/spec/00-registries/`, нужные файлы `10-flows/` и `50-access/` | Уточнить пользовательский сценарий и права, когда они входят в scope |
| `docs/reports/`, связанные PR/CI и native run | Найти уже выполненное и действительные блокеры; проверять SHA и область доказательства |
| `docs/development/testing.md`, `artifact-contracts.md`, `project-rules.md` | Выбрать реальные проверки и формат передачи результата |
| `docs/plans/`, `docs/backlog/_templates/task.md` | Подготовить план и постановку без потери исходных критериев |

Не загружать всю `docs` в каждый run: сначала индексы и выбранный файл, затем только его
источники, зависимости и evidence. `docs/status/`, старая `architecture/database_architecture.md`,
исторические планы, prompts и snapshots не подтверждают актуальное состояние и не запускаются
как новые поручения. `vision/00-reality-check.md` также сверять по дате и ревизии.

При сверке 2026-09-14 найдены устаревшие записи T-001/T-110 в ready-candidates и утверждения
T-002 об отсутствии Playwright. Они демонстрируют необходимость сверки, а не разрешают
автоматически принять T-002: её AC на публичную схему требуют отдельной проверки.
