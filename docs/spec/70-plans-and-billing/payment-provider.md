# Политика: Платёжный провайдер и вебхуки

- **Область**: планы и биллинг / интеграции
- **Статус**: утверждён (гейт Г5, 2026-09-09)
- **ADR**: ADR-0010 п. 2–4 (адаптер, копейки, автоплатёж), ADR-0011 (данные в РФ), ADR-0035 п. 6
  (порядок провайдеров заменён журналом §8.14: Т-Касса первой), ADR-0032
- **Этап**: 1 при платном запуске (§8.13 — отложено); настройки провайдера в админке — этап 4
  (журнал #36); предрелизная проверка чеков и бухгалтерии — §8.19

## 1. Назначение

Интерфейс `PaymentProvider` с реализациями `tkassa` (первая — журнал §8.14), другими адаптерами
(включая `yookassa`) по потребности и `fake` для тестов; приём и идемпотентная обработка вебхуков;
пять автоматических попыток списания в дату продления (§8.15); история обработок для раздела
«Платежи» (журнал #34). На файл ссылаются матрица #56, #66, события #23, #49, `routes.md` #66,
`subscription-lifecycle.md`, `refunds.md`.

## 2. Правила

1. **Адаптер**: код приложения вызывает только интерфейс — `createPayment`, `chargeSaved`,
   `refund`, `getPayment`, `verifyWebhook`; провайдер выбирается конфигурацией развёртывания;
   интеграция других провайдеров — отдельные адаптеры, не блокирующие первый запуск (§8.14).
   Секреты — только в переменных окружения.
2. **Деньги** — целые копейки, валюта RUB (ADR-0010 п. 2).
3. **Создание платежа**: `checkout.start` создаёт `Payment.pending` с идентификатором провайдера
   и возвращает адрес оплаты; сохранение способа оплаты для автосписаний — по согласию на checkout
   `[ДОПУЩЕНИЕ: согласие обязательно для подписки]`; цена берётся из централизованного источника
   (§8.12), не из кода экрана.
4. **Попытки списания при продлении** (§8.15): в дату окончания активного периода — пять попыток
   `chargeSaved` с 10:00 до 23:00 `[ДОПУЩЕНИЕ: равномерно; часовой пояс сервера]`; каждая попытка
   — запись `Payment` со статусом и логом `subscription.retry`; первая успешная останавливает
   серию; после пятой неудачи период истекает с 00:00 следующего дня (`subscription-lifecycle.md`
   п. 4). Пользователь получает письмо о неудаче серии (§8.23 — шаблоны и повторы отложены).
5. **Вебхук** `POST /api/webhooks/psp/{provider}` (`routes.md` #66): проверка подписи → запись
   `PspWebhookEvent` с уникальностью `(provider, eventId)` → обработка в транзакции; ошибка —
   `error` в записи, ответ 5xx для повтора `[ДОПУЩЕНИЕ]`, журнал ошибок (`admin-sections.md` #22).
6. **Результат**: `succeeded` — период в очередь и активация по приоритету; `canceled` / `failed` —
   `Payment.canceled`, период не создаётся; `refund` — `refunds.md`.
7. **Идемпотентность**: повторный вебхук с тем же `eventId` не меняет состояния; ручной повтор —
   `webhook.replay` (матрица #66) с аудитом.
8. **История обработок** (журнал #34): раздел «Платежи» — таблица платежей, попыток списания и
   вебхуков со статусами; чтение — `analyst`, `admin`, `owner`.
9. **Недоступность провайдера**: `checkout.start` — `PROVIDER_UNAVAILABLE`; попытка списания при
   недоступности считается неудачной и серия продолжается по расписанию `[ДОПУЩЕНИЕ]`; `system.health`
   отмечает `psp`.
10. **Ожидание вебхука**: страница результата опрашивает `payment`; если вебхук не пришёл за N
    минут `[ДОПУЩЕНИЕ: 15]`, система запрашивает статус (`getPayment`).
11. **Данные**: у платформы нет данных карт; у провайдера — токен способа оплаты; персональные
    данные плательщика — в РФ (ADR-0011).
12. **Чеки, налоги, документы** (§8.19): предмет расчёта, налоговый режим, состав документов и
    бухгалтерский контур — обязательная предрелизная проверка по материалам Т-Бизнеса и при
    необходимости с бухгалтером; до неё настройки чеков не утверждены (`receipts-54fz.md`).
13. **Тестовый провайдер** `fake` воспроизводит все ветки, включая серию из пяти попыток.

## 3. Исключения

| Исключение | Условие | Кто может | Аудит |
|---|---|---|---|
| Повторная обработка вебхука | ошибка обработки | `admin`, `owner` | `webhook.replay` |
| Ручной запрос статуса платежа | вебхук не пришёл | система; `admin`, `owner` `[ДОПУЩЕНИЕ]` | лог |
| Смена или добавление провайдера | отдельный адаптер; настройки — этап 4 | `owner` | `settings.change` |
| Служебная запись | `checkout.start` — `FORBIDDEN` (§8.17) | — | — |

## 4. Взаимодействие с другими политиками

- `subscription-lifecycle.md` — очередь периодов и продление; главнее он в части состояний.
- `receipts-54fz.md` — чеки после предрелизной проверки; `refunds.md` — возврат через адаптер.
- `80-observability/health-and-alerts.md` — `psp` в `/health`, алерт при доле ошибок.

## 5. Проверяемость

- Интеграционные тесты с `fake`: успех, отказ, повтор вебхука, неверная подпись, серия из пяти
  попыток с успехом на k-й и без успеха (истечение с 00:00), `replay`.
- Тест: два одинаковых `eventId` — одна запись.
- Тест: `checkout.start` служебной записью — `FORBIDDEN`; при недоступности — `PROVIDER_UNAVAILABLE`.
- Метрики: доля неудачных серий, время от платежа до активации, ошибки вебхуков.

## 6. Открытые вопросы и допущения

- `[ДОПУЩЕНИЕ]` Согласие на сохранение способа оплаты; равномерное расписание попыток; 5xx для
  повтора; опрос статуса через 15 минут; недоступность провайдера как неудачная попытка.
- Отложено (§8.19): чеки, налоги, бухгалтерия — предрелизная проверка; (§8.13) платный запуск.
- Закрыто Г5 (§8.14–15): Т-Касса первой; пять попыток 10:00–23:00, истечение с 00:00.
