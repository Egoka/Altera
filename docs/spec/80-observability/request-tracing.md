# Политика: Трассировка запросов

- **Область**: логирование
- **Статус**: утверждён (гейт Г8b, 2026-09-09)
- **ADR**: ADR-0032 п. 6 (`requestId` из Nuxt в API и в ответ), ADR-0023 (BFF: браузер → Nuxt →
  API), ADR-0020; `docs/vision/08-operations.md` §8; `20-public/error.md`; `40-admin/errors-and-health.md`
- **Этап**: 0–1

## 1. Назначение

Единый идентификатор запроса, связывающий действие пользователя, запись лога, ошибку в сборщике
и обращение в поддержку. На политику ссылаются `logging-policy.md`, `error-collector.md`,
`error-dictionary.md`, `20-public/error.md` («скопировать `requestId`»), `20-public/contact.md`
(поле `requestId` в обращении), `40-admin/errors-and-health.md` (поиск по `requestId`), `jobs.md`
(`jobId`).

## 2. Правила

1. **Один запрос — один `requestId`**: генерируется на входе в Nuxt (серверный маршрут
   `/api/graphql` и SSR-страницы), передаётся в API заголовком `[ДОПУЩЕНИЕ: `x-request-id`]`,
   возвращается клиенту в ответе и в `extensions` ошибки (ADR-0032 п. 6); если заголовок пришёл
   извне — не доверять, генерировать свой `[ДОПУЩЕНИЕ]`.
2. **Формат** — непрозрачная случайная строка без ПДн и без порядка `[ДОПУЩЕНИЕ: UUID v4]`; не
   содержит идентификатора пользователя.
3. **Везде в логах**: каждая запись `log` в рамках запроса несёт `requestId`
   (`logging-policy.md` п. 2); фоновые задания несут `jobId` и, если задание создано запросом,
   `originRequestId` `[ДОПУЩЕНИЕ]`.
4. **Пользователю** (журнал §28.4): только при технических сбоях — `INTERNAL_ERROR`,
   `PROVIDER_UNAVAILABLE`; на обычных состояниях и ошибках заполнения (`VALIDATION_ERROR`,
   `CONFLICT`, `NOT_FOUND`, `ARCHIVED`, `RATE_LIMITED`) `requestId` не выводится. На странице
   ошибки (`error.md`) и в состоянии сбоя показывается
   `requestId` с кнопкой «скопировать» и ссылкой на `/contact` с предзаполненным полем; в
   письмах пользователю `requestId` не пишется, кроме ответа поддержки `[ДОПУЩЕНИЕ]`.
5. **Сотруднику**: раздел ошибок ищет по `requestId` (`errors-and-health.md` §4); обращение в
   поддержку с `requestId` (матрица #117, `support.request.created` #80) ведёт к записи ошибки
   без раскрытия ПДн.
6. **Сквозные вызовы к провайдерам** (AI, платежи, почта): `requestId`/`jobId` передаётся в
   метаданные вызова, где провайдер это позволяет, и пишется в `ai.job.*`, `webhook.*`, `mail.*`.
7. **Вебхуки** провайдеров: свой `requestId` на входе плюс `eventId` провайдера
   (`payment-provider.md` п. 7) для идемпотентности.
8. **Не трассируем**: события вовлечённости `POST /api/engagement` (`engagement-tracking.md` §8) —
   без `requestId` в логах, чтобы не связывать чтение с запросами страниц `[ДОПУЩЕНИЕ]`.
9. **Распределённая трассировка** (span, OpenTelemetry) не вводится до потребности
   (`08-operations.md` §8 — Prometheus и метрики при потребности) `[ДОПУЩЕНИЕ]`.

## 3. Исключения

| Исключение | Условие | Кто может | Аудит |
|---|---|---|---|
| Кешированный SSR-ответ | `requestId` исходного рендера не переиспользуется; клиент получает новый на следующий запрос `[ДОПУЩЕНИЕ]` | система | — |
| `/health` | без `requestId` в ответе | внешняя проверка | — |

## 4. Взаимодействие с другими политиками

- `logging-policy.md` — обязательность поля; `error-collector.md` — группировка по сигнатуре, не
  по `requestId`; `error-dictionary.md` — `requestId` в каждой ошибке; `retention-and-pd.md` —
  `requestId` не ПДн, живёт со сроком логов.

## 5. Проверяемость

- Тест: ответ API на ошибку содержит `requestId`, совпадающий с записью лога.
- Тест: запрос через Nuxt и напрямую в API получают `requestId`; внешний заголовок не
  проходит.
- Метрика: доля логов без `requestId`/`jobId` — ноль (`logging-policy.md` §5).

## 6. Открытые вопросы и допущения

- `[ДОПУЩЕНИЕ]` Заголовок и формат; недоверие внешнему заголовку; `originRequestId` у заданий;
  события вовлечённости без трассировки; без OpenTelemetry до потребности.
- Отложено: обращения в поддержку как очередь (заход 8a → 8a «Итог по Г3» — не решено).
- Закрыто Г8b (§28.4): `requestId` — только при технических сбоях.
