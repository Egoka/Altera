# Раздел админки: Ошибки и состояние бэкенда

- **Реестр**: `00-registries/admin-sections.md` #22 · `00-registries/routes.md` — `/admin/errors`
  (маршрут добавлен Г3 вместе с разделом `[ДОПУЩЕНИЕ: строка `routes.md` — при закрытии 8b]`)
- **Статус**: на утверждении
- **ADR**: ADR-0032 (ошибки и логирование), ADR-0019; журнал §20.19, #38, §21.29, §21.40;
  `docs/vision/08-operations.md` §8–9; `80-observability/error-collector.md`,
  `health-and-alerts.md`, `request-tracing.md` (8b); события #53–54, #81; `20-public/error.md`
- **Этап**: 1 `[ДОПУЩЕНИЕ]` (журнал §20.19 — раздел обязателен; способ хранения логов — 8b)

## 1. Назначение и минимальная роль

Самостоятельный раздел наблюдения за ошибками и состоянием бэкенда (журнал §20.19): журнал всех
ошибок и сбоев API, веба и воркеров с поиском и просмотром записи; графики частоты ошибок по дням
и иным периодам; состояние зависимостей из `/health` (база, Redis, провайдеры платежей, AI,
почты — события #53). Технический способ хранения и доставки логов определяется при
проектировании инфраструктуры (8b) — это не отменяет обязательности раздела. Минимальная роль —
`admin` (чтение), `owner`; `analyst`, `moderator`, `editor` — недоступен `[ДОПУЩЕНИЕ: по реестру]`.
Раздел — только чтение; действия по устранению — вне продукта (деплой, инфраструктура).

## 2. Маршруты

- `/admin/errors` — список и графики; `/admin/errors/{id}` — запись `[ДОПУЩЕНИЕ: вложенный

- Из сводки (#1, карточка «здоровье и ошибки»), из заданий (#13 — ошибка задания), из
  `20-public/error.md` (по `requestId` из сообщения пользователю), из #22 → #13 и #9 (вебхуки).
- `noindex`; без сессии — 302; роли без доступа — 403.

## 3. Сущности и данные

| Сущность | Поля в списке | Поля в карточке | Источник (запрос) | Персональные данные (кто видит) |
|---|---|---|---|---|
| Запись об ошибке (`backend.error`, #81) | время, сервис (`api` / `web` / `worker`), код (`INTERNAL_ERROR`, `PROVIDER_UNAVAILABLE`, класс ошибки задания и т. д.), маршрут или задание, `requestId`, число повторов за период (группировка по сигнатуре `[ДОПУЩЕНИЕ]`) | стек без ПДн (#54, #81), контекст запроса (маршрут, роль актора — без идентификатора пользователя `[ДОПУЩЕНИЕ]`), связанное задание или вебхук, предыдущие вхождения той же сигнатуры | `errorLog(filters)`, `errorEntry(id)` | ПДн в записях быть не должно (ADR-0032 — стек без ПДн); если попали — дефект логирования, не право доступа |
| Графики частоты | ошибок по дням / часам, по сервисам, по кодам; сравнение с прошлым периодом | — | `errorStats(period, groupBy)` | нет |
| Состояние зависимостей | компонент (`db`, `redis`, `psp`, `ai`, `mail`), статус, время последней проверки, задержка `[ДОПУЩЕНИЕ]` | история статусов за период | `/health` (#53), `healthHistory(period)` | нет |
| Сбои движка рейтинга | прогоны с ошибкой и повторы (`ranking.run.failed` #48; §21.29 — последнее успешное значение; §21.40 — повтор по журналу ошибок) | — | в списке по сервису `worker` | нет |

## 6. Массовые операции

Массовых операций нет: раздел только для чтения.

## 7. Опасные операции и подтверждения

Опасных операций нет. Экспорт CSV подтверждения не требует (ПДн в записях нет).

## 8. Аудит действий

Аудит не пишется, кроме `stats.export` (#40): чтение журнала ошибок не касается ПДн (журнал #6).
Логи-источники: `backend.error` (#81), `error.unhandled` (#54), `system.health` (#53),
`job.failed` / `job.stuck` (#52), `ranking.run.failed` (#48), `webhook.failed` (#49),
`mail.failed` (#51). Что сознательно не входит: ошибки клиента (`page.error` #64 — метрика, не
сбой бэкенда `[ДОПУЩЕНИЕ: показывается отдельной вкладкой в 8b, если решится]`).

## 9. Состояния

| Состояние | Когда | Что показано |
|---|---|---|
| Загрузка | список / графики / состояние | скелеты |
| Пусто | ошибок за период нет | «сбоев не зафиксировано» и зелёное состояние зависимостей |
| Ошибка | сам раздел не смог получить данные (сборщик недоступен) | `ErrorState` с `requestId`; состояние зависимостей — из последнего `/health` с пометкой «устарело» |
| Нет прав на часть действий | не применимо: у допущенных ролей один набор | — |
| Конфликт (объект изменён другим администратором) | не применимо: раздел не редактирует | — |
| Лимит / превышение | экспорт CSV чаще лимита | `RATE_LIMITED` |

Дополнительно: зависимость в состоянии «недоступна» — плашка в шапке раздела и на сводке (#1);
алерты — 8b (`health-and-alerts.md`).

## 12. Открытые вопросы и допущения

- `[ДОПУЩЕНИЕ]` Этап 1; строка `routes.md` для `/admin/errors` — при закрытии 8b; группировка по
  сигнатуре; контекст без идентификатора пользователя; период 24 часа; задержка зависимостей;
  без состояния «решено»; клиентские ошибки — отдельной вкладкой по решению 8b; ретенция 90
  дней; `analyst` без доступа.
- Отложено (8b): хранение и доставка логов, сборщик ошибок, алерты, трассировка запросов,
  ретенция (`80-observability/*`).
- Закрыто Г3–Г4 (журнал §20.19, §21.29, §21.40): раздел обязателен с журналом, поиском и
  графиками; сбои движка — последнее успешное значение и повтор.
- `[ВОПРОС ВЛАДЕЛЬЦУ]` Нужно ли в разделе состояние «решено / в работе» у ошибки с отметкой
  сотрудника (лёгкий трекер), или раздел остаётся чистым журналом, а работа с инцидентами ведётся
  вне продукта? Если нужно — статус и аудит `admin.change`; если нет — как описано.
