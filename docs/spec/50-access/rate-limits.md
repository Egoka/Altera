# Политика: Лимиты запросов

- **Область**: лимиты
- **Статус**: утверждён (гейт Г2, 2026-09-08)
- **Источник правил**: журнал Г2 #57 (§18 — лимиты едины, серверные, не настраиваются
  персонально), матрица #10, #16, #45, #67, #114, события #6, #44; `plans.md` (лимиты планов);
  ADR-0024 (лимиты на вход), ADR-0027 (фильтр ботов), ADR-0032 (`RATE_LIMITED`); журнал не
  задаёт числовых значений — все числа `[ДОПУЩЕНИЕ]`
- **Этап**: 0 (вход и письма — закрытие дыры «rate limit отсутствует»), 1 (лимиты планов), 2
  (маяк прочтения), 3 (поиск)

## 1. Назначение

Сейчас лимитов нет ни на одном слое [ФАКТ: `docs/vision/00-reality-check.md` §4]: перебор
e-mail при запросе ссылки, спам письмами в редакцию, накрутка прочтений — всё открыто. Политика
задаёт, что лимитируется, по какому ключу, с каким ответом и где это проверяется. Лимиты —
серверное правило защиты от перегрузки и злоупотреблений, они не входят в ролевую модель, едины
для всех и не могут персонально отключаться или настраиваться ни для пользователя, ни для
служебной роли, ни для `owner` (журнал #57). Числовые значения — константы проекта с
допущениями здесь; лимиты, вытекающие из плана автора, описаны в `plans.md` и проверяются как
`PLAN_LIMIT`, а не `RATE_LIMITED`.

## 2. Правила

1. **Ответ на превышение** — `RATE_LIMITED` с полем `retryAfter` (ADR-0032); интерфейс
   показывает пояснение и время; лог `rate_limit.hit` с ключом корзины и хэшем IP (события
   #44), без ПДн.
2. **Ключи**: IP (хэш с солью дня для логов), e-mail (хэш) для входа, идентификатор
   пользователя для действий аккаунта. Лимиты по IP применяются до аутентификации, по
   пользователю — после проверки прав (`permission-checks.md` п. 3: лимиты — последними).
3. **Вход** (матрица #45; ADR-0024): запрос ссылки — 5 в час на e-mail и 20 в час на IP
   `[ДОПУЩЕНИЕ]`; подтверждение ссылки — 10 попыток в час на IP `[ДОПУЩЕНИЕ]`; превышение не
   раскрывает, существует ли аккаунт.
4. **Письмо в редакцию** (`pages.md` #14): 3 в час на IP, 10 в сутки на аккаунт `[ДОПУЩЕНИЕ]`.
5. **Жалобы** (матрица #16): лимит есть, значения — при отдельном разборе сценария жалоб
   (отложено).
6. **Маяк прочтения** (матрица #67; ADR-0027): один засчитанный маяк на пару (день, материал,
   `visitorHash`) — дедупликация в базе; сверх этого — сырой лимит 60 маяков в минуту на IP
   `[ДОПУЩЕНИЕ]`; известные боты отсекаются по user-agent до записи. Аномалии сверх лимита —
   вход антинакрутки (`60-ranking/anti-fraud.md`), а не блокировка.
7. **Поиск** (3): 60 запросов в минуту на IP, 300 на аккаунт `[ДОПУЩЕНИЕ]`.
8. **Мутации кабинета** (закладки, профиль, смена почты): 60 в минуту на аккаунт
   `[ДОПУЩЕНИЕ]`; смена e-mail — 1 запрос в сутки.
9. **Загрузка медиа**: 30 файлов в час на аккаунт `[ДОПУЩЕНИЕ]`; квота объёма — по плану
   (`plans.md`), отказ — `PLAN_LIMIT`.
10. **Отправка к публикации**: одновременно в очереди ≤ 5 материалов (`plans.md`) —
    `PLAN_LIMIT`; «перередактировать» — один раз на статью (журнал #9) — `FORBIDDEN` при
    повторе, не лимит.
11. **AI и переводы**: лимиты в сутки на автора — параметры Г4; бюджет провайдера — параметр
    настроек (этап 4); превышение бюджета — задание ставится в очередь, автор видит статус
    «ожидает» `[ДОПУЩЕНИЕ]`.
12. **Административные действия** не лимитируются числом, но аудируются; экспорт CSV — 10 в
    час на сотрудника `[ДОПУЩЕНИЕ]`; лимиты по IP для служебных ролей те же, что для всех
    (журнал #57).
14. **Оспаривание блокировки** (матрица #114): одно оспаривание на аккаунт — повтор `CONFLICT`;
    открытие формы — 10 в час на IP `[ДОПУЩЕНИЕ]`.
15. **Персональных исключений нет** (журнал #57): ни повышенных, ни отключённых лимитов для
    отдельного аккаунта или роли; значения меняются только релизом конфигурации проекта
    `[ДОПУЩЕНИЕ: константы, а не параметр настроек этапа 4]`.
13. **Реализация**: счётчики в PostgreSQL или Redis при его наличии (ADR-0019 — Redis
    необязателен; без него — таблица с TTL); лимит проверяется в одном middleware API до
    резолвера для IP-ключей и в хелпере для пользовательских.

## 3. Исключения

| Исключение | Условие | Кто может | Аудит |
|---|---|---|---|
| Системные вызовы (воркер, вебхук провайдера по подписи) | внутренние | система | логи подсистем |
| Служебные роли в админке | исключений нет: те же лимиты, что для всех (журнал #57) | — | аудит по действиям |
| Внешняя проверка `/health` | без лимита — это не пользовательское действие | мониторинг | лог `system.health` |
| Повышенный или снятый лимит для конкретного аккаунта или роли | невозможно (журнал #57) | — | — |

## 4. Взаимодействие с другими политиками

- `permission-checks.md` — порядок: права, затем лимиты; отказ по плану — `PLAN_LIMIT`, по
  частоте — `RATE_LIMITED`.
- `session-lifecycle.md` — лимиты входа защищают выдачу ссылок.
- `60-ranking/anti-fraud.md` — маяки сверх лимита и аномалии обрабатываются там.
- `80-observability/health-and-alerts.md` — всплеск `rate_limit.hit` по одному ключу — алерт.

## 5. Проверяемость

- Тесты middleware: N+1-й запрос ссылки с одного e-mail в час — `RATE_LIMITED` с `retryAfter`;
  ответ одинаков для существующего и несуществующего адреса.
- Тест маяка: повторный маяк того же `visitorHash` в тот же день не увеличивает `uniqueReads`.
- Тест деградации: без Redis лимиты работают на таблице.
- Метрики: `rate_limit.hit` по корзинам; доля запросов ссылки, отклонённых лимитом (сигнал
  перебора).

## 6. Открытые вопросы и допущения

- `[ДОПУЩЕНИЕ]` Все числовые значения выше — предварительные константы проекта.
- `[ДОПУЩЕНИЕ]` Превышение бюджета AI ставит задание в очередь, а не отклоняет.
- Закрыто Г2 (журнал #57): лимиты едины и не снимаются ни для кого; параметр настроек не
  проектируется.
