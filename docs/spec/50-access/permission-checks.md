# Политика: Проверка прав

- **Область**: доступ
- **Статус**: на утверждении
- **Источник правил**: журнал Г1 (§1, §7.4, #5, #7–8, #12–13, #29), матрица (колонка «Где
  проверяется», инварианты), `roles.md`; ADR-0003 п. 4, ADR-0012 (единый источник enum),
  ADR-0035 — в части, не противоречащей журналу
- **Этап**: 0 (хелперы и единый источник enum), 1 (права по плану и дефолтные наборы ролей)

## 1. Назначение

Права проверяются **только на сервере**, в резолвере, первой строкой; интерфейс скрывает
кнопки, но не является границей (журнал §7.4: «скрытие кнопки не заменяет проверку прав на
стороне системы»). Политика задаёт, какими хелперами и в каком порядке выполняется проверка,
как дефолтные наборы ролей и индивидуальные исключения складываются в решение, и что
возвращается при отказе. На неё ссылаются все строки матрицы `access-matrix.md` (колонка
«Где проверяется») и все спецификации мутаций.

## 2. Правила

1. **Единый источник ролей и планов**: `enum Role { reader author editor moderator analyst
   admin owner }` и `enum PlanTier { free standard pro }` в Prisma → SDL → сгенерированные
   типы фронта (ADR-0012). Ручных словарей ролей на фронте нет [ФАКТ: сейчас три словаря —
   `docs/vision/00-reality-check.md` §3.4].
2. **Иерархии по включению нет** (журнал §1): каждая служебная роль имеет дефолтный набор
   прав; `owner` — все права. Проверка `ensureRole(x)` означает «роль x или `owner`», а не
   «x и выше». Например, `ensureRole(moderator)` пропускает `moderator` и `owner`, но не
   `admin`.
3. **Порядок проверки в резолвере**: `ensureAuthenticated` → архивированный аккаунт →
   `FORBIDDEN` → роль или дефолтное право (`perm(p)`) → активность плана для авторских
   действий (`ensureActiveAuthor`) → владение объектом (`own`) → состояние объекта
   (`assertCanEditTranslation` и т. п.) → лимиты. Первая непройденная проверка возвращает
   код; дальнейшие не выполняются.
4. **Дефолтные права** (`perm(p)`): `publish` — `editor` (свои), `moderator`, `owner` (журнал
   #8); `review` — `moderator`, `owner`; `moderate` (архив чужого контента) — `moderator`,
   `owner`; `editorial` (создание редакционных статей) — `editor`, `owner`; `taxonomy` —
   `admin`, `owner` (журнал #29); `finance` — `analyst`, `admin`, `owner` (журнал #19);
   `accounts` (архив и восстановление аккаунтов) — `admin`, `owner` (журнал §5.3);
   `owner` — только `owner` (роли, исключения, «удалить навсегда», рейтинг, настройки).
5. **Индивидуальные исключения** (журнал #7): `perm(p)` истинно, если право есть в дефолтном
   наборе роли **или** выдано владельцем и не отозвано (`permission-exceptions.md`). Для
   `reader` и `author` исключений нет — проверка их не ищет.
6. **Авторские действия и план** (журнал #5, #20): создание, правка, отправка к публикации,
   возврат из архива, вторая языковая версия требуют `ensureActiveAuthor`: роль `author` **и**
   `planUntil` в будущем (или действующая выдача). Отказ — `PLAN_LIMIT` с указанием
   требуемого плана, не `FORBIDDEN`: интерфейс ведёт на `/pricing`. Архивирование своих,
   чтение истории, экспорт — без плана. Служебные роли (`editor`, `owner`) ведут свои
   материалы без плана.
7. **Владение**: автор и `editor` действуют только над своими материалами; проверка `own`
   сравнивает `Article.authorId` с пользователем. Чужой материал для них — `NOT_FOUND`
   (`visibility.md` п. 2), а не `FORBIDDEN`.
8. **Правка чужого текста запрещена всем, кроме `owner`** (журнал #12–13): `moderator` не
   редактирует; `admin` не редактирует; `assertCanEditTranslation` пропускает только автора
   версии, `editor` для своих и `owner`.
9. **Архив и уровень прав** (журнал #2): при архивировании сохраняются актор и уровень его
   прав; `article.restore` проверяет, что уровень восстанавливающего не ниже уровня
   архивировавшего, а автор восстанавливает только собственный архив; `moderator` не
   восстанавливает вообще.
10. **Инварианты владельцев** (журнал #10): операции над ролью `owner` выполняются в
    транзакции с проверкой «остаётся ≥ 1 владельца»; нарушение — `CONFLICT`.
11. **Аудит как часть проверки**: мутации из матрицы с непустой колонкой «Аудит» пишут запись
    в той же транзакции; административное чтение ПДн — `admin.read.personal`. Мутация без
    записи аудита не считается выполненной.
12. **Коды отказа**: `UNAUTHENTICATED` — нет сессии; `FORBIDDEN` — роль или право не
    подходит (только там, где существование объекта не скрывается); `NOT_FOUND` — чужой
    неопубликованный объект; `PLAN_LIMIT` — нужен план или лимит плана исчерпан; `CONFLICT` —
    инвариант (последний владелец, чужое решение, устаревшая ревизия).

## 3. Исключения

| Исключение | Условие | Кто может | Аудит |
|---|---|---|---|
| Право сверх дефолтного набора служебной роли | выдано `owner`, не отозвано | `editor`, `moderator`, `analyst`, `admin` | `permission.exception.grant` |
| Ведение материалов без плана | служебная роль | `editor`, `owner` | — |
| Действия системы (AI-проверка, вебхук, планировщик) | внутренний вызов без пользователя | worker с системным актором | лог `ai.job.*`, `webhook.*`, `subscription.*` |
| Процедура последней инстанции (утрата всех владельцев) | вне продукта | доступ к базе | запись в аудит скриптом (`08-operations.md` §13) |

## 4. Взаимодействие с другими политиками

- `visibility.md` решает, что видно; эта политика — что можно сделать; чтение проверяется по
  видимости, мутации — здесь.
- `permission-exceptions.md` — источник истины для правила 5.
- `session-lifecycle.md` — правило 3 начинается с валидной сессии.
- `rate-limits.md` — лимиты проверяются последними, после прав.
- `escalation-and-demotion.md` — как меняются роли, от которых зависят проверки.

## 5. Проверяемость

- Контрактный тест по SDL: каждая мутация имеет декларированное требование (роль / право /
  план / владение); мутация без декларации — тест красный.
- Тесты хелперов: `ensureRole(moderator)` отвергает `admin`; `ensureActiveAuthor` отвергает
  автора с истёкшим планом кодом `PLAN_LIMIT`; `assertCanEditTranslation` отвергает `moderator`
  на чужой версии.
- Тест инварианта владельцев: отзыв последнего `owner` — `CONFLICT`.
- Тест аудита: мутация из матрицы с аудитом без записи — падает.
- Метрика нарушения: доля `FORBIDDEN` на маршрутах кабинета автора (должна быть заменена
  `PLAN_LIMIT` там, где дело в плане).

## 6. Открытые вопросы и допущения

- `[ДОПУЩЕНИЕ]` Набор кодов дефолтных прав (`publish`, `review`, `moderate`, `editorial`,
  `taxonomy`, `finance`, `accounts`, `owner`) — первое приближение; уточняется при
  проектировании разделов админки (журнал §7).
- `[ДОПУЩЕНИЕ]` Уровни прав для правила 9: автор < `moderator` < `owner`; `editor` для своих
  статей — как автор.
- `[ВОПРОС ВЛАДЕЛЬЦУ]` Могут ли служебные роли ставить закладки и подписываться на авторов
  (сейчас — да, как любой аккаунт)? Если нет — исключить из наборов служебных ролей.
