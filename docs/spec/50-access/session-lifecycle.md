# Политика: Жизненный цикл сессии

- **Область**: сессии
- **Статус**: утверждён (гейт Г2, 2026-09-08)
- **Источник правил**: журнал Г1 (§5, #4, #30, #43), журнал Г2 (#48, #50, #55), матрица #45–47,
  #49–50, #54, #80, #113–115, события #42–43, #78; журнал §34 п. 6–9 (вход по паролю); ADR-0009 (таблица сессий, ротация, отзыв), ADR-0022 (magic link — единственный
  вход; частично заменён журналом §34 п. 6–8), ADR-0023 (BFF и httpOnly-cookie), ADR-0024 (почта и лимиты) — в части, не
  противоречащей журналу
- **Этап**: 0 (полный цикл сессии — закрытие дыр), 1 (архив аккаунта и согласия)

## 1. Назначение

Сейчас refresh-токен выдаётся, но нет ни обновления, ни отзыва, ни выхода, ни хранения
сессии; magic link печатается в лог [ФАКТ: `docs/vision/00-reality-check.md` §3.3, §4].
Политика задаёт полный цикл: запрос ссылки или ввод пароля → вход → сессия с ротацией → выход или отзыв →
истечение; поведение при архивировании аккаунта (доступ закрывается сразу — журнал §5.1) и
при смене версии оферты. На неё ссылаются `guest.md`, `reader.md`, `flows.md` #1, #11–13,
`20-public/login.md`, `verify.md`, `30-account/reader/sessions.md`.

## 2. Правила

1. **Два равных способа входа — одноразовая ссылка из письма и пароль** (журнал §34 п. 6).
   Отменено (журнал §34): правило «единственный вход — ссылка из письма; пароли не вводятся
   никогда» (ADR-0022 п. 1, п. 3). Причина: решение владельца о равной альтернативе входу по
   ссылке.
   - **Ссылка**: запрос по e-mail создаёт одноразовый токен на 15 минут (хранится хэш); письмо
     уходит через почтовую зависимость (ADR-0024); повторное использование токена — `NOT_FOUND`.
   - **Пароль**: необязателен: регистрация по ссылке или с паролем взаимозаменяемы (журнал §34 п. 7); при регистрации с паролем адрес подтверждается письмом до первого входа; сброс
     пароля — письмом; вход по одноразовой ссылке остаётся альтернативой (журнал §34 п. 7).
     Аккаунты, созданные без пароля (по ссылке или перенесённые), могут оставаться без пароля и
     входить по ссылке (журнал §34 п. 8).
   - Требования к паролю и лимит попыток входа по паролю — параметр не задаётся; предложение
     архитектора на утверждение владельцу (T-116), лимит попыток — вместе с порогами лимитов
     частоты (журнал §34 п. 9, §36; `rate-limits.md`). Хранение, подтверждение адреса, сброс и
     смена пароля — T-115. OAuth нет.
2. **Регистрация создаёт аккаунт** (с паролем — журнал §34 п. 7; при первом входе по ссылке —
   как прежде, см. §6) с планом `free`, случайным хэндлом и записью версии и
   времени согласия с офертой и политикой ПД (матрица #54); без согласия вход не завершается —
   `VALIDATION_ERROR`. Аккаунт создаётся читателем (журнал §25.1); базовые авторские возможности
   открываются при первом «Создать статью» (`70-plans-and-billing/plan-free.md` п. 6а).
3. **Сессия — запись в таблице** (ADR-0009): `Session(userId, tokenHash, previousTokenHash,
   userAgent, ip, createdAt, expiresAt, revokedAt)`; клиент хранит только httpOnly-cookie через
   BFF-прокси Nuxt (ADR-0023); в браузерном JS токенов нет.
4. **Ротация**: refresh меняет `tokenHash`, старый переходит в `previousTokenHash`;
   предъявление старого токена после ротации — признак кражи: сессия отзывается, пишется лог
   `session.reuse_detected` с алертом (события #43).
5. **Истечение**: access — 15 минут, refresh — 30 дней без активности `[ДОПУЩЕНИЕ: значения
   из текущего CI-конфига 15m/7d пересматриваются]`; истёкшая сессия делает запрос запросом
   посетителя (`visibility.md`).
6. **Выход и отзыв**: пользователь отзывает любую свою сессию или все сразу (матрица #47);
   `admin` и `owner` отзывают чужие (#80) с аудитом `user.sessions.revoke`.
7. **Архивирование аккаунта закрывает доступ сразу** (журнал §5.1, #4, #30): все сессии
   отзываются в той же транзакции; попытка входа по ссылке для архивированного аккаунта не
   создаёт новый аккаунт на тот же e-mail (матрица #46). При самостоятельном архиве
   (`archiveMode = self`) вход создаёт **ограниченную сессию** `[ДОПУЩЕНИЕ: флаг `Session.limited`]`,
   в которой доступны только экран состояния `/me/archived` (`routes.md` #73), кнопка
   «Восстановить аккаунт» (#116) и выход; любой другой запрос с такой сессией отвечает
   `FORBIDDEN` и редиректом на экран состояния (журнал §5.2, Г3). При административном архиве
   (`mode` admin или emergency) сессия не создаётся — сообщение и переход к форме оспаривания
   `/auth/appeal?token=` по тому же токену входа (журнал #48; матрица #114; `routes.md` #71)
   `[ДОПУЩЕНИЕ: форма при любом административном архиве]`. Восстановление после блокировки —
   `admin`/`owner`; оплаченный план всё это время продолжает идти (журнал #48, #50).
8. **Смена роли или плана действует немедленно**: роль и план читаются из базы на каждый
   запрос (ADR-0003 п. 4 — роль не в JWT-клейме [ФАКТ: `server/src/prisma.ts:29-31`]);
   деактивация доступа владельца (журнал #10) — то же.
9. **Смена версии оферты**: при следующем запросе пользователь с устаревшей версией согласия
   получает экран повторного согласия; до принятия — только чтение публичного `[ДОПУЩЕНИЕ]`.
10. **Смена e-mail** (матрица #49; журнал §25.8): пользователь вводит новый адрес, получает на
    него код и вводит его в том же окне; после проверки адрес меняется без повторного входа и
    без принудительного завершения сессий; подтверждения со старой почты и отката нет.
    Административная смена (#50) — только в процедуре восстановления доступа, с аудитом.
11. **Ретенция** (`07-commerce.md` §8): сессии — 30 дней после истечения; токены входа —
    после использования или 15 минут; IP сессии виден только владельцу при расследовании.
12. **Уведомления** (журнал #43): вход с нового устройства — письмо `[ДОПУЩЕНИЕ]`; решения по
    статьям и по оспариванию блокировки — письмом (журнал #48); правила рассылок — отложены.
13. **Окончание плана не отзывает сессию** (журнал #55): пользователь остаётся в аккаунте как
    читатель и может продлить подписку; сервер немедленно отклоняет каждый API-вызов, требующий
    активного плана, включая сохранение и правку материала, кодом `PLAN_LIMIT` с логом
    `plan.action.rejected` (события #78); клиент показывает уведомление о неактивной подписке
    вместо успешного сохранения.

## 3. Исключения

| Исключение | Условие | Кто может | Аудит |
|---|---|---|---|
| Отзыв чужих сессий | архивирование аккаунта или ручной отзыв | `admin`, `owner` | `user.sessions.revoke`, `user.archive` |
| Просмотр IP сессий другого пользователя | расследование | `owner` | `admin.read.personal` |
| Смена e-mail без доступа к старому адресу | потеря почты, проверка личности | `admin`, `owner` | `user.email.change` (via: recovery) |
| Системные вызовы без сессии | AI-воркер, вебхук, планировщик | система | логи подсистем |

## 4. Взаимодействие с другими политиками

- `permission-checks.md` п. 3 начинается с валидной сессии; архив аккаунта — `FORBIDDEN` на
  любой запрос с сессией и отзыв сессий.
- `rate-limits.md` — лимиты на запрос ссылки и попытки подтверждения; лимит попыток входа по
  паролю — там же, после утверждения предложения архитектора (журнал §34 п. 9, §36).
- `visibility.md` — истёкшая или отозванная сессия = посетитель.
- `escalation-and-demotion.md` — смена роли не требует повторного входа (правило 8).

## 5. Проверяемость

- E2E: запрос ссылки → письмо (Mailpit) → вход → сессия в таблице; повторный переход по
  ссылке — ошибка; выход отзывает сессию; `/me` без сессии — редирект.
- E2E входа по паролю (T-115): регистрация с паролем → письмо подтверждения → вход до
  подтверждения невозможен → после подтверждения вход по паролю; сброс пароля письмом; аккаунт
  без пароля входит по ссылке.
- Тест ротации: старый refresh после ротации → сессия отозвана, лог `session.reuse_detected`.
- Тест архива: архивирование аккаунта отзывает все сессии в той же транзакции; вход по новой
  ссылке для самостоятельно архивированного — ограниченная сессия, `me` отвечает состоянием
  архива, `translation.save` — `FORBIDDEN`; после `account.restore.self` сессия обычная; для
  заблокированного — сессии нет, новый аккаунт не создан.
- Тест немедленности: смена роли отражается на следующем запросе без нового входа.
- Тест плана: после истечения `planUntil` сессия валидна, `me` отвечает ролью `reader`,
  `translation.save` — `PLAN_LIMIT`, лог `plan.action.rejected` записан.
- Тест оспаривания: ссылка входа для аккаунта с `mode = emergency` открывает форму без сессии;
  повторная отправка — `CONFLICT`.
- Метрики: доля неудачных подтверждений ссылки; число `session.reuse_detected` (алерт).

## 6. Открытые вопросы и допущения

- `[ДОПУЩЕНИЕ]` Сроки: access 15 минут, refresh 30 дней без активности, до 10 устройств.
- `[ДОПУЩЕНИЕ]` Повторное согласие с офертой блокирует всё, кроме чтения публичного.
- `[ДОПУЩЕНИЕ]` Письмо о входе с нового устройства.
- `[ДОПУЩЕНИЕ]` Форма оспаривания доступна при любом административном архиве, не только при
  экстренной блокировке; ограниченная сессия реализуется флагом на записи сессии.
- Закрыто Г2 (журнал #55): сессии при истечении плана не отзываются; блокирует сервер на
  уровне действий.
- Закрыто (журнал §34 п. 6–8): два равных способа входа — ссылка и пароль; регистрация и вход — двумя взаимозаменяемыми способами: по ссылке (без пароля) или с паролем (журнал §34 п. 7); при регистрации с паролем адрес подтверждается письмом до первого входа, сброс — письмом; аккаунты без
  пароля входят по ссылке.
- Открыто (журнал §34 п. 9): требования к паролю и лимит попыток входа — предложение архитектора
  на утверждение владельцу (T-116).
- Закрыто (журнал §34 п. 7): первый вход по ссылке для нового адреса создаёт аккаунт без пароля; регистрация по ссылке и с паролем взаимозаменяемы.
