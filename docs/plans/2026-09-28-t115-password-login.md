## 1. Что требуется

Два равных способа регистрации и входа (журнал §34 п. 6–8): одноразовая ссылка и пароль. При
регистрации с паролем адрес подтверждается письмом до первого входа; забытый пароль сбрасывается
письмом; аккаунты без пароля продолжают входить по ссылке. Требования к паролю и лимит попыток
входа утверждены владельцем целиком (журнал §44 п. 1) по предложению
`docs/reports/2026-09-27-t116-rate-limit-thresholds-proposal.md`.

Критерии готовности из файла задачи:

1. Регистрация по ссылке и с паролем обе создают аккаунт; при регистрации с паролем вход до
   подтверждения адреса невозможен — e2e.
2. Аккаунт без пароля входит по ссылке — e2e.
3. Сброс пароля идёт письмом; ответы не раскрывают существование аккаунта — тест.
4. Попытки входа ограничены лимитом, утверждённым владельцем — тест.

## 3. Границы этого прохода

Входит: хранение хэша, регистрация с паролем, письмо подтверждения, вход по паролю, сброс письмом,
смена и установка пароля в кабинете, лимит попыток.

Не входит: OAuth; реальная доставка писем (транспорт `console`/Mailpit до выбора провайдера,
журнал §34 п. 2); перенос остальных утверждённых чисел RL-01…RL-13 в `rate-limits.md` (отдельная
задача, журнал §44 п. 1); MFA; экран «вход с нового устройства».

## 4. Решения прохода

1. **Аккаунт создаётся сразу.** Регистрация с паролем заводит запись с `emailVerifiedAt = null`
   (критерий 1: «обе создают аккаунт»); вход по паролю до подтверждения отвечает отдельным
   исходом `email_unconfirmed`, сессии нет.
2. **Ответ регистрации не раскрывает существование аккаунта** (`login.md` §4). Занятый адрес
   получает тот же ответ `{ ok: true }`, чужой аккаунт не меняется, а на адрес уходит письмо «у вас
   уже есть аккаунт» со ссылкой входа `[ДОПУЩЕНИЕ]`.
3. **Неподтверждённая регистрация не захватывает чужой адрес.** Если владелец адреса входит по
   ссылке в запись, где `emailVerifiedAt = null`, пароль такой записи снимается, а адрес
   отмечается подтверждённым: иначе тот, кто «зарегистрировал» чужой адрес, знал бы пароль
   аккаунта `[ДОПУЩЕНИЕ, безопасность]`.
4. **Требования к паролю — утверждённые (журнал §44 п. 1)**: 15…128 code points после NFC, без
   обязательных классов символов, сверка с локальным blocklist (включая название сервиса, адрес и
   хэндл), хранение Argon2id `m=19 MiB, t=2, p=1` PHC-строкой. Argon2id берётся из `node:crypto`
   Node 24 — новой зависимости не требуется.
5. **Лимит попыток — RL-14/RL-15**: 5 за 15 минут на нормализованный e-mail и 30 за 15 минут на
   IP; считаются только неуспешные проверки, успешный вход очищает корзину e-mail, отказ идёт при
   исчерпании любой корзины. Неизвестный адрес проверяется против фиктивного хэша, чтобы ответ и
   стоимость не различались. Постоянной блокировки нет.
6. **Сброс письмом**: `requestPasswordReset` всегда отвечает одинаково, письмо уходит только
   существующему аккаунту; токен одноразовый, живёт как ссылка входа (15 минут). Успешный сброс
   подтверждает адрес, отзывает все прежние сессии и выдаёт новую.
7. **Кабинет**: `setPassword` — одна мутация для установки и смены; текущий пароль обязателен,
   если он задан; успешная смена отзывает остальные сессии, текущая остаётся.
8. **Новых кодов событий и аудита не вводится**: реестр `events-and-logs.md` сверяется с кодом
   биективно (`event-code-registry.test.ts`, `audit-zone-registry.test.ts`), а новый код — это
   продуктовое правило. Ветка пароля пишет `auth.login`, `auth.login.failed`,
   `auth.link.requested`, `session.revoked`, `rate_limit.hit`.
