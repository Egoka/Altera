## 1. Контекст и решение по ordering

Техплан `docs/plans/2026-09-15-t053-locale-routing-slugs.md` §4.3 поставил запуск AC-T053-2 в
зависимость от «принятых schema-входов T-013/T-014/T-015» — на эту дату они завершены и
применены на боевой базе (см. `docs/reports/2026-09-17-neon-development-branch-migrations-incident-report.md`).
Формальный prerequisite владельца (вариант «а» из треда ALTE-34) закрыт.

Тот же §4.3 требует полного `(locale, slug)`-теста, опирающегося на физическое удаление через
**T-076** («удалить навсегда», только `owner`, только из архива). T-076 зависит от T-072, T-073,
T-062 — ни одна не завершена (`docs/backlog/matrix.md`), T-072/T-073 и вовсе не в работе. Полный
сценарий из §4.3 («создать → физически удалить через T-076 → повторно занять → CONFLICT»)
технически невозможно проверить: в продукте ещё нет пути физического удаления.

**Решение**: не расширять scope до полного T-076-сценария. Вместо этого закрыть конкретный,
независимо обнаруженный дефект — единственную мутацию, которая физически удаляет `Article` и тем
самым освобождает адрес уже сегодня, до T-076.

## 2. Баг на baseline

`server/src/graphql/article/resolver.ts:617-646` (`bulkDeleteArticles`) — единственное место в
кодовой базе, где строка `Article` удаляется физически (`ctx.prisma.article.deleteMany`). Все
остальные переходы статуса уже не удаляют строку:

- `archiveArticle` (resolver.ts:522-543) — `status: "archived"`, автор архивирует свой материал;
- `bulkUpdateArticleStatus` (resolver.ts:648-697) — допускает `status: "archived"` как обычное
  обновление;
- `taxonomy/service.ts` — `archiveSection`/`archiveTag` архивируют так же, заполняя
  `archivedAt`/`archivedByActorId`/`archivedByRole`.

Миграция T-015 (применена на проде, см. §1) уже добавила `Article.archivedAt`,
`archivedByActorId`, `archivedByRole`, `archiveReason` — колонки существуют, но `Article` их нигде
не использует: ни один резолвер их не заполняет. `bulkDeleteArticles` — единственный разрыв между
намерением схемы («материал архивируется, а не удаляется») и фактическим поведением.

Нарушение: после `bulkDeleteArticles` уникальный индекс на `Article.slug` освобождается, и другой
материал может занять тот же адрес — прямое нарушение ADR-0004 и журнала §26.10 («публичные
адреса не освобождаются архивированием или физическим удалением»).

## 3. Исправление

`bulkDeleteArticles` архивирует вместо удаления — тот же паттерн, что уже используют
`archiveArticle` и `taxonomy/service.ts`:

```ts
await ctx.prisma.article.updateMany({
  where: { id: { in: ids } },
  data: {
    status: "archived",
    archivedAt: new Date(),
    archivedByActorId: ctx.currentUser!.id,
    archivedByRole: ctx.currentUser!.role,
    archiveReason: "bulk_delete"
  }
})
```

Строка и её `slug` остаются в таблице навсегда — уникальный constraint PostgreSQL/Prisma
гарантирует, что адрес нельзя занять повторно. Публичные запросы (`article`, `latestArticles`,
`featuredArticles`, `articleDetail`, `articles` и т. д.) уже фильтруют `status: "published"`
(проверено `grep` по `resolver.ts`), поэтому архивный материал автоматически перестаёт быть
видимым публично без дополнительных изменений фильтров.

Новой Prisma-модели или миграции не требуется: используются уже примененные на проде колонки
T-015. Это не вводит вторую таблицу резервов и не конфликтует с ограничением архитектора
(«T-053 не вводит конкурирующую Prisma-модель», §4.1 варианта 2).

## 4. Явно не входит в этот заход

- Полный `(locale, slug)`-тест на `ArticleTranslation` с физическим удалением через T-076 —
  невозможен до T-076 (→ T-072/T-073/T-062). ALTE-34 остаётся blocked именно на эту цепочку.
- Проверка reserved-segment валидатора (T-014) — отдельный, уже покрытый в T-014 контур.
- SEO/sitemap-фильтрация архивных материалов (T-100/T-055) — вне scope.
- Экспонирование `archivedAt`/`archiveReason` в GraphQL-схеме `Article` — не требовалось ни одним
  AC; добавлять не стал.
