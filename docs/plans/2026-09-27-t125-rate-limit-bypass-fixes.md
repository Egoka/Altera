## Что есть сейчас

Три дефекта одного механизма.

1. BFF берёт адрес самым левым элементом `X-Forwarded-For`
   [ФАКТ: `web/server/api/graphql.post.ts:53`], то есть значением, которое подставил клиент.
2. Петлевой адрес доверенного запроса объявлен «системным вызовом» и лимиту не подлежит
   [ФАКТ: `server/src/rate-limits/client-address.ts:24-31`]. Вместе с п. 1 это снимает все
   лимиты по адресу: достаточно послать `X-Forwarded-For: 127.0.0.1`.
3. Корневые поля собираются в `Set`, поэтому документ с N алиасами одного поля расходует одно
   обращение корзины [ФАКТ: `server/src/rate-limits/plugin.ts:63-68,99`].

Исключение §3 «системные вызовы» в коде не имеет ни одного настоящего источника: воркер
(`server/src/jobs`) работает внутри процесса и в GraphQL по HTTP не ходит, `/health` отвечает
до Yoga [ФАКТ: `server/src/health.ts:140`, `server/src/server.ts:105`], вебхуков провайдеров в
схеме нет. Петлевой адрес был подставлен вместо проверки происхождения.

## Что делаю

1. **`web/server/utils/clientAddress.ts`** (новый) — `resolveTrustedClientAddress`: адрес берётся
   из элемента `X-Forwarded-For`, который добавил доверенный прокси платформы, а не из
   клиентского. Число доверенных прокси перед BFF — параметр `trustedProxyHops` (по умолчанию
   `1`, `NUXT_TRUSTED_PROXY_HOPS`): отбрасываются `hops - 1` правых элементов, берётся следующий
   справа; при пустом или недостаточном списке — адрес соединения. Значение проверяется
   `node:net.isIP`, иначе адрес не передаётся вовсе.
2. **`web/server/api/graphql.post.ts`** — вместо `getRequestIP(event, { xForwardedFor: true })`
   вызов нового хелпера.
3. **`server/src/rate-limits/client-address.ts`** — исключение по петлевому адресу убирается:
   остаются `client` (доверенный адрес от BFF) и `unverified` (общая корзина запросов мимо BFF).
   Петлевой адрес доверенного запроса становится обычной клиентской корзиной.
4. **`server/src/rate-limits/plugin.ts`** — `rootFieldCounts` считает каждое вхождение
   корневого поля, включая алиасы и повторные развороты фрагментов; счётчики складываются по
   корзинам, `enforce` вызывается один раз на корзину со стоимостью N. Превышение отклоняет весь
   документ (`enforce` бросает `RATE_LIMITED`).
5. **Стоимость обращения** в `counter-store.ts`, `database-store.ts`, `redis-store.ts`,
   `limiter.ts`, `tests/helpers/rate-limit.ts`: `consume(..., cost)` и `enforce(..., cost)`.
   Документ с тысячей алиасов остаётся одним обращением к хранилищу, а не тысячей.
6. **Тесты**: серверные — алиасы и повторные фрагменты, петлевой адрес под лимитом, стоимость в
   обоих хранилищах, источник исключения §3 (воркер и `/health` не проходят через middleware);
   веб — разбор `X-Forwarded-For` с подставленным клиентским значением.
7. **Сквозные сценарии**: специи, которые действительно обменивают токен входа, чистят
   `rate_limit_counters` перед прогоном — раньше их прикрывало исключение по петлевому адресу.
8. **AC-4**: отчёт T-024 и receipt `docs/reports/tasks/T-024.{json,md}` восстанавливаются из
   записи PR #181 и плана T-024; выдуманных результатов проверок в них нет.
9. Отчёт и receipt T-125 по ритуалу проекта.

## Границы

Пороги не меняются (T-116, журнал §36 п. 1). Неприменённые корзины реестра остаются
неприменёнными. Значение `trustedProxyHops` для боевой площадки подтверждает релиз-инженер:
за Cloudflare и Gateway (`docs/infrastructure/cloudflare-altera-com.md` п. 4.2.6) прокси два,
на Render — один `[ДОПУЩЕНИЕ]`.
