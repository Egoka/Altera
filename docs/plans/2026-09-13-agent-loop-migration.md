## Цель и подход

Развить существующие правила, `.claude/` и Multica так, чтобы агент доводил небольшую
разрешённую задачу до проверяемого результата, сохранял знания и не мог выдать завершение
run за приёмку. Репозиторий хранит контракты и evidence; runner обеспечивает права;
Multica координирует стадии. Выполнение идёт по одному этапу с проверяемым результатом.

## Общие ограничения

- Журнал → spec → ADR → vision для требований; код и проверки для текущего состояния.
- Один writer продуктового кода. Две последовательные неудачи одной проверки останавливают стадию.
- Сохранить десять ролей, все действующие разрешения §7, trace-routing, T/E/Q/F и старые ссылки.
- Не удалять знания, не переписывать историю, не вводить числовые бюджеты без решения.
- Не включать автопилоты и не менять их настройки в рамках подготовки документации.
- План/отчёт остаются в `docs/plans/` и `docs/reports/`, с базовым commit и взаимными ссылками.
- Все проверки фиксируют конкретное дерево. Существующие продуктовые критерии не ослабляются.

## Зависимости этапов

`M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8`.
Аудит Multica уже подготовлен; применять C1–C5 плана Multica следует в M6 после M1–M5.
Каждый этап имеет отдельный план/отчёт исполнения; его SHA определяется на старте, а не
копируется из этого документа. При возврате этапа сохраняются прежние попытки и их evidence.

**Файлы:** изменить `docs/backlog/_templates/task.md`, `.claude/commands/multica-start.md`,
`.claude/commands/multica-stage.md`, `docs/multica/operating-model.md` только в согласованной части.

- [ ] Добавить фиксируемые AC-ID, scope, сохранённый API, источник разрешения и базовую ревизию.
- [ ] Разделить run outcome, stage outcome и task acceptance без изменения native-статусов вслепую.

- [ ] Разрешить запуск по действующему прямому поручению без выдуманной готовности всего бэклога.

**Пробы:** готовая задача с закрытыми зависимостями допускается; кандидат, открытый Q,
устаревшее evidence и успешный run без review не допускают следующую стадию/Done.
**Гейт:** все положительные и отрицательные пробы дают ожидаемый исход без запуска продукта.
**Восстановление:** вернуть адаптеры стадий и шаблон, сохранить новые артефакты как проект.

## M4. Исполняемые ограничения harness — P4

**Исполнитель:** архитектор/релиз-инженер; код механизмов пишет назначенный разработчик.
**Файлы:** `.claude/settings.json`, `.claude/agents/multica-*.md`,
`.claude/hooks/ritual-check.sh`; будущие тесты `tests/harness/` — после проверки принятого runner.

- [ ] Подтвердить реальные права всех ролей: отсутствие Edit не запрещает shell/Write.
- [ ] Спроектировать проверяющим чтение продукта и изолированное место для результатов.
- [ ] Проверить охват Stop-hook: committed изменения, dirty tree, другой план той же даты,
      отсутствующая связь плана с задачей, повторный Stop. Hook не является сертификатом приёмки.
- [ ] Обеспечить устойчивый счёт двух неуспехов и защиту от повторного запуска стадии.
- [ ] Проверить ограничение writer между ресурсами/runner; in_place одной папки само по себе
      не доказывает глобальный mutex. Если технического механизма нет — ручной dispatch.
- [ ] Инвентаризировать реальные таймауты, квоты и лимиты стоимости; предложить недостающие
      значения отдельно, не принимать их от имени владельца.

**Пробы:** запись синтетического защищённого файла через shell и Write отклонена;
два запуска на одну стадию не дают двух writer; счёт сохраняется после рестарта; внешняя
инструкция в fixture не выдаёт полномочий; запрет не обходится другим инструментом.
Проверки выполняются на безопасных fixture, без чтения реальных секретов.

**Гейт:** каждое ограничение обозначено `проверено средой / только инструкция / недоступно`.
Необеспеченное критическое ограничение блокирует автономную очередь, а не подготовку документов.
**Восстановление:** вернуть последнюю проверенную конфигурацию; не восстанавливать более широкие
права автоматически; сохранить тексты и журнал сбоя.

масштабирование. **Восстановление:** остановить пилот, handoff той же стадии; не брать другую задачу.
