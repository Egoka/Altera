## Цель и порядок

Согласовать настройки существующих объектов Multica с принятыми репозиторными правилами,
проверить исполнение ограничений и сохранить все уникальные сведения. C0 доступен как
read-only следующий шаг; C1–C5 готовят конкретные изменения после M1–M5 основного плана.
Применение настроек и включение автопилотов требуют поручения на конкретное действие по §7.

Последовательность: `C0 → C1 → C2 → C3 → C4 → C5 → C6`.
Состояние снимка не переносится через паузу работы без повторной сверки.

## C0. Полный безопасный snapshot — MC0

**Исполнитель:** хранитель документации. **Вход:** аудит с ID и доступ к read-only UI/API.
**Выход:** `docs/multica/snapshots/ГГГГ-ММ-ДД/manifest.json` и очищенные тексты/метаданные
затрагиваемых полей; создать каталог при исполнении. Никакие значения секретов не сохранять.

- [ ] Перечитать Project description/resources/folder mode/status, текущую доску и run.
- [ ] Сохранить полный SKILL.md `altera-project-rules`, 32-навыковый inventory и тексты
      реально подключённых процедур, назначения role → skill, доступные версии/ID.
- [ ] Для всех десяти агентов сохранить prompt, runtime, model, thinking, concurrency,
      scope access, MCP/integrations, Custom Args и факт наличия environment без значений секретов.
- [ ] Сохранить squad instructions, member instructions, roster/leader и три autopilot:
      prompt, project, assignee, output mode, state, timezone, triggers, run history.
- [ ] Для каждого поля: object ID, UI/API path, observed_at, digest, источник; проверить,
      что старое значение может быть восстановлено в том же объекте.

**Гейт:** ноль неизвестных старых значений среди полей, которые собираемся менять.
Неподдерживаемый экспорт не обходить придуманным API; использовать чтение UI и файл
текста для обычных полей. Неэкспортируемые секреты оставлять без изменения.

## C3. Все десять агентов и реальные права — MC3

**Находки:** F03/F04/F09/F11. **Объекты:** Agents из таблицы аудита; runner-adapters M4.

| Роль                     | Точечное изменение prompt/контракта                                                                                                                 |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Оркестратор              | Repo `готова` + Todo + закрытые зависимости + нет Q + критерии + slot; run/stage/acceptance отдельно; сохранить roster/mention и отсутствие polling |
| Архитектор               | Контракт до решения, trace impact, неизвестные отдельно; диагностика не возобновляет проваленную стадию сама                                        |
| Разработчик              | Воспроизведение, минимальное изменение, API/scope, защищённые критерии и evidence точного дерева                                                    |
| Тестировщик              | Независимые сценарии, реальные команды, границы mocks/browser, запись только в разрешённые артефакты                                                |
| Независимый ревьюер      | Первичное задание + diff + evidence + trace_ref; не автор реализации; устаревшее ревью инвалидируется                                               |
| Дизайнер                 | Контракт интерфейса и состояния; отличие макета от доказанного поведения браузера; передача разработчику                                            |
| Релиз-инженер            | Действующая автономия §7 и условия выпуска, safe build, целевая среда/миграции/восстановление                                                       |
| Хранитель документации   | Ledger без потерь, актуальные факты с источником; не переписывать журнал/ADR/owner notes                                                            |
| Редактор и бренд-стратег | Источник и рамки текста, достоверность, запрет новых продуктовых/юридических правил без владельца                                                   |
| SEO-специалист           | Технические критерии и артефакты, существующие права/роуты/рейтинг сохраняются                                                                      |

- [ ] Для каждого подготовить отдельный old/new diff; общий текст брать из одного skill,
      но не терять уникальные ограничения существующего prompt.
- [ ] Runtime/model/thinking/concurrency/access/credentials оставить по свежему snapshot,
      если конкретное изменение не было отдельно разрешено.
- [ ] Проверить загрузку правил Codex и Claude; `.claude/settings.json` не доказывает
      ограничение Codex. Текст skill тоже не ограничивает filesystem.
- [ ] Проверить read-only продукта для reviewer/tester и глобальное ограничение writer.
      Per-agent concurrency 1 и folder in_place фиксировать как частичные механизмы.

**Гейт:** все десять ролей прочитаны и сверены; тестовые попытки недопустимой записи и
конкурентного запуска дают ожидаемый отказ. Если этого нет, автоматизация не получает
статус готовой. **Rollback:** вернуть прежние prompt/назначения; права не расширять автоматически.

| Объект                 | Разрешённый diff                                                                                                       | Приёмка                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |

старый prompt и его версию, сохранив выключенное состояние; не возобновлять расписание по догадке.

## C6. Контролируемая проверка, включение и rollback — MC6

**Вход:** принятые C0–C5 и M7; все критические неизвестные закрыты.

- [ ] Подготовить точный сценарий и expected outcome до проб; сначала read-only/dry-run,
      если такой режим реально поддерживается; иначе согласованная ручная имитация.
- [ ] Проверить: нет работы → no-op; Todo без ready → отказ; активная стадия → нет дубля;
      устаревший SHA → нет приёмки; Q-NN → нет восстановления; две ошибки → handoff.
- [ ] Проверить обычную разрешённую задачу, независимое review и открываемые артефакты.
- [ ] Для каждого автопилота отдельно подготовить включение после закрытия checklist;
      порядок сохранить: контекст → очередь → восстановление. Разрешение явно фиксируется.
- [ ] После включения проверить timezone, будущий Next и ровно ожидаемый dispatch;
      прошлый Next выключенного объекта не считается успешной проверкой scheduler.
- [ ] При неверном dispatch/потере гейта остановить соответствующий автопилот, сохранить
      run/evidence, отменить только ошибочное назначение в пределах разрешений, восстановить
      текст по snapshot. Не повторять автоматически и не закрывать полезную чужую работу.

**Гейт завершения:** все F01–F11 имеют закрывающее evidence либо явно оставленный блокер;
обновлены checklist, ledger и отчёт. Отсутствие изменений в UI или успешный текстовый
ответ агента не заменяет проверку фактического результата.

## Решения, которые потребуются перед применением

1. Выбрать одну область записи контекст-автопилота (C1).
2. Принять точные изменения действующих инструкций/полей после snapshot, включая правила диагностики.
3. Утвердить список причин восстановления и недостающие числовые бюджеты, если они нужны runner.
4. Разрешить конкретный пилот и включение каждого автопилота после проверок.

На стадии подготовки этого плана эти решения не блокируют создание документов и аудит.
Никакое из них не выведено из молчания владельца или самого наличия нового промпта.
