- **Authorization**: диспетчеризация оркестратора в комментарии `01a0bb7d-bfaf-7bb3-8362-2265244f79fb`
- **Preflight**: `scripts/autonomy/preflight.py --runtime-id claude-code_2-1-278_agent --run-id 01a0bb8b-bfbe-71d1-abbf-d81128317758` → `ok: true`
- **Отчёт**: `docs/reports/tasks/T-079.md` (после реализации)

**Цель**: раздел аудита в админке, где служебная роль видит записи своей зоны, `admin` и `owner` —
весь журнал; фильтры по коду, актору, субъекту, периоду и `requestId`; экспорт CSV без полей с ПД;
просмотр аудита не создаёт записей.

## 1. Контракт и границы

Источники по старшинству: журнал решений (#37, #39, §27.5 п. 5), затем `docs/spec/40-admin/audit-log.md`,
замороженный реестр `docs/spec/00-registries/events-and-logs.md`, `docs/spec/50-access/visibility.md` п. 10,
`docs/spec/00-registries/access-matrix.md` #92, `docs/spec/50-access/rate-limits.md` п. 12.

Инварианты:

1. `auditLog`, `auditEntry`, `auditSummary` ничего не пишут в `AuditLog` (журнал §27.5 п. 5). Единственная
   запись, которую порождает раздел, — `stats.export` (#40) при экспорте.
2. Зона определяется кодом события, а не ролью актора: код → зона берётся из явного серверного реестра,
   построенного по темам зон `visibility.md` п. 10 и колонкам «Кто инициирует»/«Файл» реестра событий.
   Неизвестный или незакреплённый код для служебной роли закрыт: его видят только `admin` и `owner`.
3. `admin` и `owner` обходят зонный фильтр (журнал #39).
4. Экспорт CSV — только `admin` и `owner` (`audit-log.md` §1, §5, §9 — `[ДОПУЩЕНИЕ: analyst без экспорта]`);
   лимит 10 в час на сотрудника (`rate-limits.md` п. 12 `[ДОПУЩЕНИЕ]`), превышение — `RATE_LIMITED`.
5. CSV консервативен: время, код, роль актора, признак «система», тип сущности, `requestId`. Поля
   `actorId`, `entityId`, `subject`, `context`, `purpose`, `diff` в файл не попадают.
6. Запись вне зоны служебной роли — `NOT_FOUND` (404, `audit-log.md` §2 `[ДОПУЩЕНИЕ]`); отсутствие
   доступа к разделу — `FORBIDDEN` (матрица #92); без сессии — 302 на `/login`; обычный аккаунт — 403.
7. Журнал только для чтения: мутаций создания, изменения и удаления записи нет ни для одной роли.

Не входит (границы задачи T-079 §3): признак «критичная запись» и фильтр `?critical=1` (§26.1, Q-08).
Поэтому состояние «Критичные» в списке и сводке не появляется; строка §9 «Конфликт» неприменима
по самой спецификации (журнал не редактируется) и не имеет UI.

  применяется к audit-кодам.

## 3. Принятые технические решения

### 3.1. Серверный реестр зон

`server/src/audit/registry.ts`: `AUDIT_EVENT_CODES` (все утверждённые `audit`-коды реестра) и
`AUDIT_CODE_ZONES: Record<AuditEventCode, readonly AuditZone[]>`, где `AuditZone` —
`editorial` (редакционные статьи), `moderation` (решения по материалам и AI),
`financeAndPd` (финансы, чтения ПДн, AI-метрики). Пустой список = только `admin`/`owner`.
Тест сверяет набор кодов с реестром спецификации построчно (тип ячейки начинается с `audit`,
статус «утверждён»), поэтому реестр нельзя рассинхронизировать вручную.

Альтернативы отклонены: вывод зоны из `actorRole` неверен для системных записей (`ai.decision`,
`engagement.exclusion`, `permission.exception.expire`); колонка `zone` в таблице потребовала бы
миграции и неоднозначного backfill неизменяемого журнала.

### 3.2. Сервис и авторизация

`server/src/admin/audit.ts` — весь доступ и все фильтры до Prisma-запроса:

- `listAuditLog(ctx, filters)` — `ensurePermission(..., "admin.enter", "audit.read", ...)`, зонный
  `action: { in: … }` для служебных ролей, курсорная пагинация по `createdAt`+`id`
  (`limit` 20, максимум 100 — `audit-log.md` §4 `[ДОПУЩЕНИЕ]`), период по умолчанию 7 дней `[ДОПУЩЕНИЕ]`.
- `getAuditEntry(ctx, id)` — та же авторизация, вне зоны `NOT_FOUND`.
- `getAuditSummary(ctx, filters)` — число записей, разбивка по кодам и акторам, без ПД.
- `exportAuditCsv(ctx, filters)` — `ensureRole(..., "admin", …)` (даёт `admin` и `owner`), лимит
  считается по самому журналу: число собственных записей `stats.export` за час; затем одна запись
  `stats.export` с `report: "audit"` и `rows`.

Актор в выдаче — роль и служебное имя (`«система»`, когда `actorId` пуст); имена читаются одним
`user.findMany` по собранным `actorId`.

### 3.3. GraphQL

`server/src/graphql/audit/{schema.graphql,resolver.ts}`: `auditLog(filters, limit, cursor)`,
`auditEntry(id)`, `auditSummary(filters)`, мутация `exportAudit(filters)`. Enum `AuditZone`,
input `AuditLogFilters` (зона, код, актор, «система», тип и идентификатор сущности, `requestId`,
период `from`/`to`).

### 3.4. Страница

`web/app/pages/admin/audit/index.vue` + composable `useAdminAudit`: фильтры из URL и в URL
(`?zone=`, `?action=`, `?actor=`, `?entity=`, `?subject=`, `?requestId=`, `?period=`, `?id=`, `?cursor=`),
боковая панель записи по `?id=`, `noindex`, состояния §9: скелеты загрузки, пусто
(«за период действий не было»), `ErrorState` с `requestId`, отсутствие кнопки экспорта у
`editor`/`moderator`/`analyst`, `RATE_LIMITED` при превышении лимита экспорта. Подтверждение
«файл содержит сведения о персональных данных» перед экспортом (`audit-log.md` §7 `[ДОПУЩЕНИЕ]`).
Пагинация курсорная, поэтому вместо `?page=` в URL сохраняется `?cursor=` — это следствие
`[ДОПУЩЕНИЕ: курсорная по времени]` из §4 спецификации.

## 4. Шаги

1. Реестр зон + тест биекции с реестром событий (RED → GREEN).
2. Сервис аудита: зонная видимость по ролям, фильтры, курсор, `NOT_FOUND` вне зоны, сводка.
3. Тест «просмотр не пишет в журнал» (критерий 2): `auditLog.create` не вызывается ни в одном из
   трёх запросов.
4. Экспорт: права, лимит, состав CSV без ПД, ровно одна запись `stats.export`.
5. GraphQL schema + resolver, контрактный тест SDL (нет мутаций изменения записей, нет ПД-полей в CSV-типе).
6. Codegen операций веба, composable, страница, i18n ru/en.
7. Vitest для веба: разбор и сборка URL-фильтров, состояния списка.
8. Playwright `web/tests/e2e/admin-audit.spec.ts`: все строки §9 под ролями + маршрутные коды
   (302 гостю, 403 обычному аккаунту, 404 записи вне зоны) + проверка, что просмотр не создал записей.
9. Проверки: `pnpm codegen --check`, `pnpm format`, `pnpm lint`, `pnpm test`,
   `pnpm --filter server run build:ci`, `pnpm --filter nuxt-app run build`, `typecheck`; e2e — в CI
   (job `web-smoke` на изолированной БД).
10. Отчёт `docs/reports/tasks/T-079.md` + receipt `docs/reports/tasks/T-079.json`, PR в `app`,
    запрос независимого review.

## 5. Риски

- Расхождение реестра зон и замороженного реестра событий — закрыто тестом биекции.
- Ложное срабатывание лимита экспорта в тестах: лимит считается по журналу, поэтому e2e чистит
  свои записи `stats.export` перед сценарием.
- Курсорная пагинация на равных `createdAt` — сортировка и курсор по паре (`createdAt`, `id`).
