## Global Constraints

Сохранить исходное вложение, старые документы и уникальные правила. Не править журнал владельца и продуктовые ADR. Не менять продуктовые статусы без критериев и evidence. Один implementer одновременно; независимый reviewer не создаёт проверяемую реализацию. Две подряд неуспешные попытки одной проверки останавливают эту проверку; счёт не сбрасывается новым run. Продуктовые изменения в server/web/packages имеют одну активную цепочку. Проверки привязаны к точной ревизии и dirty diff. Не читать и не выводить секреты. Сохранять существующие модели, расписания, состав сквада и ресурс in_place. Реальное ограничение runtime нельзя подменять промптом. Автопилоты включать только после применённых и проверенных изменений и выполненных чек-листов. Неподтверждённые возможности и стоимость обозначать неизвестными.

## Task 5: Граница проверки и runtime canary (уточнение M4/M7)

Подготовить минимальные контейнерные wrappers семейств Codex/Claude для реальных процессов проверяющих ролей, сохранив agent IDs, модели и resource in_place. До внешней привязки собрать очищенный manifest необходимых путей запуска; секретные значения не читать и не журналировать. Исходный checkout, .git/common-dir и policy — read-only, evidence/cache/temp только отдельными RW каталогами; Docker socket, персональный HOME и host shell/RPC write bridge не доступны контейнеру. Сначала safe fixture проверяет реальные OS-denials (create/overwrite/delete/rename/symlink/alternate-path) и допустимую запись evidence. Затем проверить stdin/stdout protocol, сигналы и exit code без модели, потом фактическую авторизацию/модель/trace в отдельной canary каждого семейства. Успех fake executable не считать запуском модели. Если необходимые managed paths, авторизация или отсутствие host-write обхода не установлены, внедрение профилей и автопилоты остаются blocked, а не получают номинальную приёмку. Прямое поручение разрешает подготовку и проверки; если штатный логин потребует человека, запросить только конкретный необходимый ввод в этот момент. Не заменять модель и не покупать API как обход.

## Task 6: Полный цикл исправления и публикация evidence (уточнение M3/M4/M7)

Независимый разбор минимального gate выявил ещё два ограничения полного цикла: завершённая
стадия не допускает обычный возврат на исправление; commit только отчётов меняет HEAD и
создаёт цикл самоссылки evidence. Эти ограничения нужно устранить до сквозного пилота,
не выдавая приёмку минимального Task 2 за готовность всей автономии.

Добавить явные типы стадий: зафиксированный контракт, реализация и проверка. Продуктовый
снимок может изменяться в разрешённой реализации; тестирование и review закреплены за её
актуальным выходом. Возврат по первому дефекту происходит в той же задаче и scope, по заранее
объявленному return target, с сохранением parent, всех событий, старого evidence и счётчиков
task/stage/check_id. Новая итерация не обнуляет неуспехи. Второй неуспех проверки останавливает
её и не разрешает третий проход через return. Не добавлять reset или новый scheduler.

Для сохранения отчётов в Git добавить узкую проверяемую связь исходной проверенной ревизии
с последующим commit только собственных gate-артефактов задачи. Gate сам доказывает ancestry,
точный список изменённых путей, неизменность checked source/dirty fingerprint и старых
proof-хэшей; произвольные docs/config/test/source изменения не подходят. Исходный SHA в
evidence не переписывается. История хранит обе ревизии и доказательство эквивалентности.
Архивы отчётов по stage/run сохраняются до final finish, который освобождает parent.

Приёмка: реальный fixture plan→изменение кода→test→review, возврат на исправление и повторные
проверки; две неудачи review через разные итерации; commit финального evidence без ложного
заявления о запуске тестов на будущем SHA; отказы при любом изменении проверяемого входа,
чужом actor/run, подмене пути/архива, повторном событии и конкурирующей parent. Выполнить
регрессии Task 2 и независимое ревью. Старое/повреждённое state не превращать молча в новую
задачу; неподдержанный переход версии останавливается с сохранёнными счётчиками и журналом.

Проверка полноты до dispatch уточнила ещё две обязательные части. Для хранителя документации
добавить тип публикации с зафиксированными точными metadata-путями и отдельным принятием
их diff. Это связь неизменного проверенного кода с новым принятым metadata, а не равенство
всего дерева. Путь к смешанному документу не разрешает менять его правила или замороженный
контракт. Документация до выпуска и финализация статусов после обязательного выпуска
остаются явными стадиями той же задачи; parent освобождается после последней проверки.

Для реально остановленной стадии предусмотреть отдельный recover после доказанного
устранения её конкретной причины, без активного дубля и без изменения scope. Счёт два
сохраняется: только фактический успех обнуляет свой check; неуспех продолжения увеличивает
прежний счёт и немедленно останавливает проверку снова. Доказательство устранения причины
одноразово и не возобновляется таймером, новым именем или косметическим commit. Gate
проверяет структуру и свежесть доказательства; истинность причины и отсутствие native run
подтверждает контроллер. Это не разрешение повторить текущий остановленный typecheck Task 3.

Дополнительная приёмка: source review → metadata diff → независимая проверка → release →
финализация хранителем → последняя проверка; отказы на чужие paths/правки контракта/устаревшие
доказательства и непрошедший обязательный release. Recovery отклоняется до устранения
причины, затем продолжает ту же проверку с прежним счётом; второй неуспешный запуск recovery
по тому же доказательству невозможен. Сохранять исходный дизайн и отдельное дополнение как
исторические источники; не выдавать fixtures за принятие runtime и native pilot.

## Task 8: Постоянные native adapters (продолжение 2026-09-14)

После rebase на app работать в основном дереве на `docs/agent-loop-autonomy`.
Постоянные entrypoints Claude/Codex закрепляют deployment config и доверенный
registry, а каждое разрешённое выполнение получает fresh ticket/snapshot/run.
Повтор consumed ticket запрещён. Native run ID присваивается daemon при старте:
первоначально он может быть не связан, затем закрепляется атомарно один раз;
issue/agent/workspace берутся из trusted ticket/config и проверяются readback.
Digest ticket хранится снаружи его неизменяемых bytes, без самоссылки.

Сохранить исходные модели/medium/max1, конечный parser opaque argv, accepted
D1/D2/managed mapper, project context, запрет hooks проверяющих и RO boundary.
Claude выбирает текущее поколение credentials без чтения содержимого и повторного
login; bounded lock не выдаётся за доказательство cleanup погибшего контейнера.
Проверить два новых ticket через неизменный entrypoint, отказы на подмену/повтор,
затем независимое ревью и фактическое подключение к двум агентам Multica.

## Task 9: Trusted сборщик результатов и приёмка runtime

Связать adapters с существующим gate через `admit/bind/collect/check/transition/reconcile`.
Gate остаётся владельцем стадий и счётчиков. Добавить в runtime наблюдение raw
Docker-client exit, identity/terminal/cleanup своего контейнера и provider resources,
сохранив публичный integer exit и native stdin/stdout/stderr. Unknown остаётся unknown.
Trusted fixed command runner выдаёт отдельный check receipt; модель не пишет
авторитетный passed. Process receipt, результат проверки и решение приёмки различны.

После выхода child и до выхода wrapper подтверждать exact active native row по
четырём ID. После wrapper exit controller отдельно сверяет terminal того же run;
не ждать собственного terminal callback внутри wrapper. При недоставленном событии
reconciliation не запускает модель повторно. Нет нового scheduler и обхода two-failure stop.

Приёмка: реальные gate CLI/filesystem integration fixtures, независимое ревью,
no-model observer canary, затем реальные постоянные профили с context/MCP и
точной атрибуцией результата. Product auth и включение автопилотов не предшествуют
этому runtime-пилоту без auth. Успешная браузерная canary8 и её независимое ревью
сохранены отдельно; окончательная runtime аттестация должна соответствовать
замороженной версии после observer integration.
