## Global Constraints

Сохранить исходное вложение, старые документы и уникальные правила. Не править журнал владельца и продуктовые ADR. Не менять продуктовые статусы без критериев и evidence. Один implementer одновременно; независимый reviewer не создаёт проверяемую реализацию. Две подряд неуспешные попытки одной проверки останавливают эту проверку; счёт не сбрасывается новым run. Продуктовые изменения в server/web/packages имеют одну активную цепочку. Проверки привязаны к точной ревизии и dirty diff. Не читать и не выводить секреты. Сохранять существующие модели, расписания, состав сквада и ресурс in_place. Реальное ограничение runtime нельзя подменять промптом. Автопилоты включать только после применённых и проверенных изменений и выполненных чек-листов. Неподтверждённые возможности и стоимость обозначать неизвестными.

## Task 1: Контракты и сохранение правил (M0–M3)

Прочитать M0–M3 исходного плана, текущие CLAUDE.md, operating-model, backlog README, десять .claude/agents и четыре .claude/commands. Создать migration-ledger с old→new для уникальных правил и R01–R45. Сохранить полный старый CLAUDE как исторический источник. Создать короткий AGENTS.md с дословным trace-mcp блоком из пользовательской инструкции; CLAUDE сделать адаптером со ссылками на сохранённые подробности. Новые фактические утверждения проверять по текущим командам/конфигам, без заявлений о неподтверждённых исправлениях. Создать testing.md, исправить конкретные устаревшие утверждения про отсутствие тестов. Добавить AC-ID, authorization, baseline/revision, check_id, actor/run, trace_ref, dirty fingerprint, persistent failures и критерии handoff в шаблоны задач, планов, отчётов и четыре команды; отличать run/stage/task. Уникальные роли не переписывать целиком. Прямое поручение владельца позволяет исполнить этот план без выдуманного ready в бэклоге. M4 enforcement здесь не заявлять работающим. Проверить ссылки, сохранение исходника, форматирование только изменённых файлов и git diff --check. Записать точные результаты в отчёт; не коммитить чужие файлы.

## Task 2: Исполнимые проверки и границы (M4)

На основе контрактов Task 1 заменить ложную гарантию Stop hook на проверяемый механизм с тестами. Сначала trace outline/context существующего hook, затем meaningful red tests. Проверять план и парный отчёт задачи по точной исходной и итоговой ревизии включая уже закоммиченный diff, dirty изменения, отсутствие/чужой план и отчёт. Повторный Stop не означает принятую стадию. Ввести минимальный сохраняемый контракт состояния check_id/failure count/actor/run/lease с отказом на дубликате и двух неуспехах, атомарной записью, без своего scheduler. Проверить no-op, повтор run, устаревшее evidence, подмену пути и неверную стадию безопасными fixtures. Согласовать .claude/settings.json и tester/reviewer: текст о read-only допустим только при реальном ограничении; минимальные разрешения, не расширять доступ к секретам. Не приписывать Claude hook действию в Codex; для неподдержанного runner оставить явный gate и ограничение. Тестировать до pass или установленного стопа, задокументировать поддержанные входы и обходы. Не активировать внешнюю очередь из этой задачи.

## Task 3: Проверяемая инфраструктура продукта (M5)

Выполнить оставшиеся обоснованные части T-001 и T-002: согласовать версии Node/pnpm, server build:ci, web build/typecheck в CI, реально исполняемые контрактные и браузерные smoke проверки. Читать задачи и их источники перед кодом; trace-mcp первым. Сохранить существующие 24 теста. Сначала тесты на требуемое поведение, затем минимальная реализация в scope задачи. Не реализовывать весь продукт под видом T-112: проверить применимость его сценариев; отсутствующие фичи и зависимости оформить непроверенными, не skipped pass. Не менять статусы T-001/T-002/T-112 автоматически. Не исполнять build с migrate deploy и реальные внешние сервисы. Проверить стандартные CI команды; ошибки baseline отделить от введённых изменением.

## Task 4: Синхронизация, пилот и включение (M6–M8, C0–C6)

Контроллер выполняет read-only полный snapshot изменяемых полей Multica, затем формирует адресный diff с source SHA/digest, сохраняет старые значения, применяет разрешённые изменения и читает сохранённые значения обратно. Сохранить runtime/model/thinking/concurrency/ресурс/расписание. Неизвестное старое значение не заменять. Проверить реальную загрузку контрактов runner. Выполнить независимый пилот и негативные сценарии (empty/not-ready/live/old-revision/Q/two-failures), не создавать фиктивные приёмки. Зафиксировать доступную стоимость и ограничения; не выдумывать baseline сравнения. Только после этого проверить чек-листы каждого автопилота; конкретные расширения безопасности и недостающие решения запрашивать на последнем шаге. Отчёт должен отделять выполненное, проверенное, применённое и включённое. Закрыть исходные этапы только по evidence.

## Уточнение исполнения: обнаруженное ограничение runtime

После C0 и независимой архитектурной проверки установлено: штатная Multica на macOS не обеспечивает filesystem sandbox. Task2 реализует проверяемый gate и сохраняемое состояние, а принятие M4 дополнительно требует ограниченного запуска реальных tester/reviewer. Подробность и основания фиксируются в отчёте. Числовые лимиты, роли и модели не меняются.

## Task 5: Граница проверки и runtime canary (уточнение M4/M7)

Подготовить минимальные контейнерные wrappers семейств Codex/Claude для реальных процессов проверяющих ролей, сохранив agent IDs, модели и resource in_place. До внешней привязки собрать очищенный manifest необходимых путей запуска; секретные значения не читать и не журналировать. Исходный checkout, .git/common-dir и policy — read-only, evidence/cache/temp только отдельными RW каталогами; Docker socket, персональный HOME и host shell/RPC write bridge не доступны контейнеру. Сначала safe fixture проверяет реальные OS-denials (create/overwrite/delete/rename/symlink/alternate-path) и допустимую запись evidence. Затем проверить stdin/stdout protocol, сигналы и exit code без модели, потом фактическую авторизацию/модель/trace в отдельной canary каждого семейства. Успех fake executable не считать запуском модели. Если необходимые managed paths, авторизация или отсутствие host-write обхода не установлены, внедрение профилей и автопилоты остаются blocked, а не получают номинальную приёмку. Прямое поручение разрешает подготовку и проверки; если штатный логин потребует человека, запросить только конкретный необходимый ввод в этот момент. Не заменять модель и не покупать API как обход.
