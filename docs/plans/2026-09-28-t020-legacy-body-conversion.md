## 3. Замысел

### 3.1 Одна реализация конверсии — в SQL

Конверсию выполняет persistent-функция PostgreSQL
`t020_legacy_body_to_document(jsonb) RETURNS jsonb`, созданная миграцией. Её используют
и сама миграция, и обновлённый trigger T-015, и скрипт проверки. Второй реализации того же
алгоритма на TypeScript не будет: расхождение SQL и TS — главный риск этой задачи.

Правила функции:

| Вход | Результат |
| ---- | --------- |
| уже документ (`type = doc`, целый `attrs.schemaVersion`) | возвращается без изменений |
| JSON `null` | документ из одного пустого абзаца |
| JSON-строка, пустая после `trim` | документ из одного пустого абзаца |
| JSON-строка с legacy-корнем `{"type":"root"\|"doc","children":[…]}` | разбирается как объект |
| JSON-строка обычного текста | каждая непустая строка текста → отдельный абзац |
| JSON-объект legacy-корня | каждый дочерний узел → абзац с его текстом, порядок сохраняется |
| JSON-массив узлов (случай `body: []`) | то же, что `children` |
| число, boolean, иная форма | `NULL` — «неконвертируемое тело» |

`NULL` — сознательный отказ: миграция на таком теле падает, а не молча теряет текст.
Функция идемпотентна: повторный вызов на своём результате возвращает его же.

### 3.2 Миграция `20260928120000_legacy_body_content_document`

1. `CREATE OR REPLACE` функции извлечения текста и конверсии.
2. Предпроверка: если есть тело, для которого функция даёт `NULL`, — `RAISE EXCEPTION`.
3. `UPDATE article_translations` и `article_revisions` для тел, которые ещё не документ.
4. Замена тела функции trigger T-015 на запись документа.
5. Постпроверка в той же транзакции: число статей, версий и ревизий не изменилось;
   ни одного тела-недокумента не осталось.

### 3.3 `pnpm verify:legacy-bodies`

`server/scripts/verify-legacy-bodies.ts`, корневой алиас в `package.json`.

Для каждого источника (`articles.body`, `article_translations.body`, `article_revisions.body`)
скрипт читает тело, прогоняет его через SQL-функцию и **проверяет результат настоящим
валидатором каталога** — `readDocument` из `@altera/content` (`migrateDocument` → `validateDocument`).
Так один алгоритм конверсии проверяется каталогом, а не второй копией правил.

Вывод: по каждому источнику — всего тел, уже документов, legacy, неконвертируемых; список
первых идентификаторов проблемных строк. Exit 1, если неконвертируемых больше нуля.

`@altera/content` подключается к `server` как **devDependency** (`workspace:*`): скрипт и тесты,
`server/src/**` пакет не импортирует. Тесты берут исходники пакета через alias в
`server/vitest.config.ts`, поэтому сборка `dist` для `pnpm test` не нужна.

### 3.4 Тесты

`server/tests/legacy-body-conversion-database.test.ts` (`T020_TEST_DATABASE_URL`), по образцу
`account-name-migration-database.test.ts`: baseline-миграции → legacy-данные всех форм
(обычный текст, многострочный текст, legacy-JSON строкой, legacy-объект, готовый документ,
`[]`, пустая строка) → целевая миграция → проверки:

1. каждое тело проходит `readDocument` из `@altera/content`;
2. текст сохранён (порядок абзацев и содержимое);
3. `attrs.schemaVersion` равен `CONTENT_SCHEMA_VERSION` — контракт SQL и TS;
4. число статей, версий и ревизий до и после совпадает;
5. повторное применение миграции ничего не меняет (идемпотентность);
6. запись в legacy-поле `articles.body` после миграции даёт в версии документ, а не строку.

## 4. Репетиция миграций

Две репетиции, обе на локальном PostgreSQL из `docker-compose.yml` (порт 25432).
Development Neon и любая внешняя база не читаются и не изменяются.

- **Р1 «весь набор E-03»**: новая база → четыре pre-E-03 миграции 2025 года → legacy-данные
  со строковыми телами → `prisma migrate deploy` применяет весь остаток ledger, включая T-020.
  Число статей до и после — SQL.
- **Р2 «копия населённой базы»**: `CREATE DATABASE … TEMPLATE altera_dev` — настоящая копия базы
  с 487 статьями → `prisma migrate deploy` применяет только T-020 → `verify:legacy-bodies`
  до и после, число статей до и после — SQL.

## 5. Критерии готовности и способ подтверждения

1. `pnpm verify:legacy-bodies` сообщает 0 неконвертируемых тел — фактический вывод на копии Р2.
2. Репетиция `migrate deploy` на копии прошла без ошибок, число статей до и после совпадает —
   вывод CLI и SQL-выборки по Р1 и Р2.

## 7. Риски

- Расхождение SQL-конверсии и каталога `content` — закрывается тем, что результат каждой строки
  проверяется настоящим `readDocument`, и контрактным тестом на `CONTENT_SCHEMA_VERSION`.
- `createArticle` продолжает писать `body: []`. Форму проверю на настоящей базе в ходе репетиции;
  найденное зафиксирую в отчёте. Правка резолвера сверх минимума в объём не входит.
- Потеря семантики заголовка и цитаты при уплощении в абзац — следствие границы Q-02, текст
  сохраняется полностью; возврат семантики — отдельная задача после утверждения каталога.
