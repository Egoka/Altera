# T-087 — сквозной requestId и http.request

- **Базовый коммит:** `df5963e`
- **Задача:** T-087 / ALTE-32
- **Спецификации:** `docs/spec/80-observability/request-tracing.md`,
  `docs/spec/80-observability/logging-policy.md`, ADR-0032

## Цель

Один `requestId`, созданный на входе Nuxt, проходит через BFF в GraphQL API, связывает
техническую ошибку и логи и возвращается клиенту только в публичных данных технической
ошибки. Завершение каждого GraphQL HTTP-запроса создаёт `http.request` с шаблонным маршрутом,
статусом, длительностью, внутренним `userId` и снимком роли. Job-логи допускают
`originRequestId`, если задание создано запросом.

## Архитектура

API использует request-scoped состояние на `AsyncLocalStorage`. Плагин Yoga оборачивает весь
HTTP pipeline через request instrumentation: выбирает ID из внутреннего BFF-заголовка либо
генерирует новый, выставляет ответный заголовок и после завершения пишет `http.request`.
GraphQL context берёт ID из этого состояния и после аутентификации сохраняет снимок пользователя;
masker использует тот же request-scoped ID. Nuxt middleware всегда создаёт новый ID на входе,
а GraphQL proxy передаёт его API.

## Ограничения

- Не менять GraphQL schema и существующий auth/roles API.
- Не добавлять несуществующую очередь или Prisma-модель задания: в текущем коде job storage нет.
- `requestId` скрывается у обычных ошибок и остаётся у `INTERNAL_ERROR` и
  `PROVIDER_UNAVAILABLE`.
- Не логировать тела запросов/ответов, токены и персональные данные.
- Маршрут в `http.request` — шаблон GraphQL endpoint `/`, без параметров.
