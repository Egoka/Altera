## 1. Что требуется

`uploadMedia(translationId, file, license, attribution)` без `alt`: приём в карантин, проверка типа
по содержимому, целостности и размеров, удаление EXIF и геолокации, ориентация и цветовой профиль,
мастер-файл как постоянный оригинал; статусы `uploading` → `queued` → `processing` → `ready` /
`failed`; частичная ошибка повторяется без потери мастера; публичный доступ только после успеха.

Критерии готовности из файла задачи:

1. В мастер-файле нет EXIF — тест с файлом, содержащим геометку.
2. Загрузка без лицензии или атрибуции → `VALIDATION_ERROR` — тест.
3. Все статусы обработки достижимы в тестах, включая повтор после частичной ошибки.

## 3. Границы этого прохода

Входит: шаги конвейера по утверждённым принципам (`docs/2026-09-09-media-upload-processing-notes.md`
п. 1–4, 9; `upload-pipeline.md` п. 5), лицензия и атрибуция обязательны.

Не входит: варианты, placeholder, thumbnails и матрица размеров (T-064); аватары (T-065); обложки

владельцем числовые пороги (F-04, Q-03).

## 4. Проектное решение

### 4.1 Карантин в раскладке ключей

`keys.ts` получает четвёртый вид ключа `quarantine/{assetId}.upload`
(`[ДОПУЩЕНИЕ: карантинный префикс]`, `storage-layout.md` §6). Байты загрузки лежат там до создания
мастера. Расширение нейтральное: фактический тип на этом шаге ещё не доверенный.
`decidePublicAccess` для карантина отвечает `closed` — как для мастера и выгрузки, публичен только
вариант.

### 4.2 Синхронная часть (резолвер `uploadMedia`)

Порядок: права → лимит частоты → проверки поля → байты → тип по содержимому → размер → `sha256` →
дедупликация → запись `MediaAsset` (`uploading`) → запись в карантин → `queued` + задание.

- права: автор версии (`ArticleTranslation` → `Article.authorId`); для редакционного материала
  (`Article.isEditorial`) — право `editorial` (матрица #39). План автора проверяется
  `ensureActiveAuthor` → истёкший план даёт `PLAN_LIMIT` (`article-edit.md`);
- лимит `media.upload.user` через `ctx.rateLimiter.enforce` после прав
  (`permission-checks.md` §2 п. 3) → `RATE_LIMITED`;
- пустая атрибуция или лицензия вне справочника → `VALIDATION_ERROR` с `field`, `rule`
  (критерий 2);
- тип определяется по сигнатуре содержимого, а не по имени и не по заголовку `content-type`
  (`upload-pipeline.md` п. 3); неподдерживаемый тип или превышение размера →
  `VALIDATION_ERROR` с `field: file`;
- дедупликация по `(ownerId, sha256)` возвращает существующую запись без повторного хранения
  (`storage-layout.md` п. 6);
- сбой хранилища → `PROVIDER_UNAVAILABLE` с `provider: storage` (журнал §29.3).

### 4.3 Асинхронная часть (задание `media.process`)

`processing` → загрузка байтов → `sharp`: целостность, фактический формат, размеры, число пикселей
→ снятие всех метаданных, применение ориентации EXIF, единый профиль sRGB → мастер по ключу
`{yyyy}/{mm}/{id}.{ext}` → обновление записи (`storageKey`, `mimeType`, `byteSize`, `width`,
`height`) → снятие карантина → `ready`. Любой отказ до `ready` — `failed`; мастер, если успел
создаться, сохраняется.

Повтор после частичной ошибки (критерий 3) держится на состоянии самой записи, без новой колонки:
мастер существует, когда `storageKey` разбирается как ключ вида `master` и объект есть в хранилище.
Повторное задание такой мастер не создаёт заново, а доделывает недостающие шаги. В этом проходе
единственный шаг после мастера — снятие карантина; T-064 добавляет к нему варианты, не меняя
модель повтора.

### 4.4 Адаптер обработки изображений

`ImageProcessor` — порт с двумя операциями (`inspect`, `createMaster`); реализация на `sharp`
(ADR-0030 п. 3: `sharp` — зависимость сервера). Тесты конвейера работают с двойником, а критерий 1
проверяется настоящим `sharp` на JPEG с геометкой: двойник удаление EXIF не доказывает.

### 4.5 Закрытая загрузка до утверждения порогов

§33 п. 3: до утверждения владельцем числовых параметров загрузка пользователям не открывается.
Мутация закрыта признаком окружения `MEDIA_UPLOAD_ENABLED` (по умолчанию выключена) и отвечает
`FORBIDDEN` с `action: "media.upload"`. Редактора статьи ещё нет (T-040), поэтому интерфейсного
пути к мутации тоже нет.

### 4.6 Числовые пороги — предложение архитектора

Все числа собраны в одном файле `server/src/media/limits.ts` с пометкой `[ДОПУЩЕНИЕ]` и выносятся
владельцу в receipt: размер файла 20 МиБ (ADR-0008 п. 6), предел числа пикселей, качество
перекодирования мастера по форматам. Мастер не уменьшается: задача требует проверки размеров, а не
их приведения.

## 7. Риски

- `sharp` — нативная зависимость. Джоб `server-smoke` ставит зависимости отдельным
  `cd server && pnpm install --frozen-lockfile`, поэтому платформенные бинарники должны попасть в
  lockfile. Проверяется локальной сборкой `build:ci` и прогоном тестов.
- Перекодирование мастера меняет байты относительно загрузки. Это следует из §29.2 (сырые байты
  постоянным оригиналом не считаются) и отражено в отчёте.
- GIF в спецификации разрешён (`upload-pipeline.md` п. 3), но этим проходом исключён. Отказ
  помечается отдельным правилом и выносится в остаток.

`MEDIA_UPLOAD_ENABLED` выключен. Вопрос владельцу уходит в receipt задачи.
