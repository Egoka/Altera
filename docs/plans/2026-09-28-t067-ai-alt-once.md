# T-067: AI-описание `alt` один раз при загрузке, правка только `admin` — план

- **Дата**: 2026-09-28
- **Задача**: T-067 / ALTE-150, эпик E-10 «Медиа»
- **Источник**: `docs/backlog/tasks/T-067-ai-alt-once.md` (`1c8b1467`)
- **Спецификации**: `docs/spec/85-media-and-binary/upload-pipeline.md` п. 3, 5, 6а;
  `docs/spec/00-registries/access-matrix.md` #40; `docs/spec/00-registries/events-and-logs.md`
  #46, #75; `docs/spec/40-admin/ai-processes.md` §1, §3–4, §8; журнал §27.4, §28.3, §29.11–13,
  §34 п. 4
- **Baseline**: `origin/app` `0c8deb4eb5beff2e223bd015cf13ae61c725fe4e`
- **Ветка**: `server/t067-ai-alt`

## 1. Что входит

1. **Задание описания**: после того как конвейер довёл файл до `ready`, лёгкая модель описывает
   изображение, и описание сохраняется в `alt` самого медиафайла (журнал §29.11).
2. **Адаптер модели** с `fake`-реализацией и выбором по окружению — по образцу AI-проверки
   допустимости (T-048).
3. **Мутация исправления** `alt` для `admin` с аудитом `admin.change` (`entity: mediaAsset`),
   нового кода события не добавляется (§28.3).

## 2. Что не входит

- Выбор модели, языки, качество и стоимость описания — отдельный проход (`upload-pipeline.md`
  п. 6а, Q-01, Q-03). Значение `AI_ALT_ADAPTER=real` останавливает запуск, а не притворяется
  рабочим провайдером.
- Поведение при ошибке генерации: остаётся поведение очереди T-047 — задание повторяется,
  `alt` остаётся пустым; запасного текста вместо ответа модели не появляется.
- Раздел админки «AI-процессы» (#14) и его фильтр по виду `alt` — записи создаются, экран
  задачей не затрагивается.
- Показ `alt` в свойствах медиа автору — вместе с редактором свойств (матрица #40).

## 3. Решения реализации

**Отдельное задание, а не шаг внутри обработки.** Постановка задачи прямо говорит «задание
вызывает лёгкую модель». Описание — платное обращение к внешнему провайдеру: держать его внутри
`media.process` значило бы, что отказ провайдера возвращает уже собранный файл в `failed` и
заставляет заново пересобирать мастер и варианты. Поэтому `media.process` после `ready` ставит
`ai.alt`, а у задания описания свои повторы.

**Описывается мастер, а не карантин.** До готовности `storageKey` указывает на карантинную копию
загрузки — с EXIF и геолокацией (`upload-pipeline.md` п. 5). Шаг описания требует
`processingStatus = ready` и ключ вида `master`, иначе задание падает и повторяется.

**Однократность держится обновлением, а не чтением.** Журнал §29.13: описание создаётся один
раз. Условие «`alt` ещё пуст» ставится в само обновление записи (`updateMany` с `alt: null`),
поэтому два задания по одному файлу не перепишут друг друга. Прочитанное состояние проверяется
раньше только ради того, чтобы не платить за лишний вызов модели.

**Аватар задания не получает.** Он идёт тем же конвейером синхронно и без очереди (журнал
§29.5), а его `alt` нигде не выводится: `avatarViewOf` отдаёт адрес и набор вариантов, без
описания. Вопрос «нужно ли описывать аватары» выносится владельцу, а не решается здесь.

**Исправление `alt` и аудит — одной транзакцией.** Матрица #40 требует `admin.change` для
каждого исправления; запись значения без следа в журнале недопустима, поэтому обе записи идут
одной транзакцией порта хранилища.

## 4. Критерии готовности и как проверяются

1. Мутация изменения `alt` от `author` и `moderator` → `FORBIDDEN`; от `admin` — запись
   `admin.change` — тест резолвера на двойнике хранилища с настоящей проверкой прав.
2. `alt` не входит в аргументы `uploadMedia` и `updateMediaMeta` — контрактный тест по собранной
   схеме GraphQL: перечень мутаций с аргументом `alt` должен совпадать с одной — исправлением
   администратором.
