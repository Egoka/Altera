# Синхронизация статусов бэклога с Multica и слитыми PR

- **Дата**: 2026-09-26
- **Ветка**: docs/backlog-status-sync
- **Базовый коммит**: 753d7cc (origin/app)
- **Отчёт**: docs/reports/2026-09-26-backlog-status-sync-report.md
- **Статус**: завершён

## 1. Цель

Шапки `docs/backlog/tasks/T-*.md` и производные от них таблицы (`matrix.md`, таблица задач
`README.md` §7, таблицы эпиков, `ready-candidates.md`) снова показывают фактическое состояние
задач после автономии 14–21 сентября (PR #52–#210). Синхронизацию можно повторить одной
командой после того, как параллельные сессии закончат ревью 43 задач в `in_review`.

## 2. Контекст

- Автономия влила в `app` 505 коммитов, но шапки задач почти не обновляла: у слитых T-022,
  T-023, T-054 и других остались «зависит: …», у принятых T-006, T-092 и других — «кандидат».
- Скрипт генерации `matrix.md`, о котором пишет `README.md` §4 п.3, в репозитории отсутствует
  (отчёт `2026-09-09-roadmap-revision-and-backlog-report.md`: «скрипты в рабочей папке сессии»).
  После этого `matrix.md` правили вручную, поэтому она расходится и с файлами задач.
- Устаревшие шапки уже порождают повторную работу: Multica выдаёт принятые задачи заново
  (ALTE-87 по T-097, ALTE-103 по T-006, дубли T-108/T-109).

## 3. Словарь статусов и правило сопоставления

Словарь — `README.md` §2: `кандидат`, `зависит: T-…`, `решение владельца: Q-…`, `отложена: F-…`,
`готова`, `в работе`, `завершена`. Статуса «влито, ждёт приёмки» нет, новый не вводится.

| Multica (актуально на момент прогона) | Статус в шапке |
|---|---|
| есть `done`, открытой повторной выдачи с незакрытым критерием нет | `завершена (PR #N, merge <sha>; приёмка ALTE-…)` |
| `in_review` и слитый PR | `в работе (влита PR #N, merge <sha>; ждёт приёмки ALTE-…)` |
| реализована при открытом Q-блокере | к пометке добавляется `; реализована при открытом Q-NN` |
| `blocked` | прежний статус из словаря; причина уходит в отчёт |
| задачу никто не брал | `зависит:` сокращается до незавершённых зависимостей; пусто → `кандидат` |

Статусы `решение владельца: Q-…` и `отложена: F-…` у невзятых задач не трогаются, Q-блокеры не
закрываются. Предложение отдельного статуса для «влито, ждёт приёмки» выносится владельцу.

## 4. Шаги

1. Скрипт `scripts/backlog/sync_status.py` (stdlib Python). Он только читает Multica
   (`multica issue list`), `gh pr list --state merged` и `docs/reports/tasks/T-*.json`. Затем
   сверяет данные, по флагу `--apply` правит строку `- **Статус**:` в шапках и пересобирает
   производные таблицы. Отчёт сверки пишется в JSON и Markdown. Код, e2e-тесты и receipt
   скрипт не трогает.
2. Прогон, ручная проверка расхождений: повторные выдачи, `blocked`, задачи поверх Q.
3. `owner-blockers.md`: у Q-01, Q-04, Q-08 и Q-09 появляется факт «реализовано при открытом
   вопросе». Статус «открыт» не меняется.
4. Блок «Что сломано» в корневом `CLAUDE.md` сверяется с кодом по каждому пункту и
   переписывается как актуальный список.
5. `README.md` §2 и §4 получают ссылку на скрипт и порядок повторного прогона.
   `ready-candidates.md` пересобирается. У `docs/status/*` исторический баннер получает ссылку
   на матрицу бэклога.
6. `00-reality-check.md` §С2.7 не переписывается; расхождения идут в отчёт.
7. Отчёт, PR в `app` обычным merge-коммитом, удаление ветки.

## 5. Не входит

Изменение статусов в Multica, назначение задач, правка кода, e2e-тестов, receipt, журнала
решений, закрытие Q-блокеров, переписывание среза реальности.

## 6. Проверка

- Повторный прогон `sync_status.py --check` после `--apply` не находит расхождений.
- Каждая строка `matrix.md` и README §7 совпадает со статусом файла задачи.
- `pnpm format` / pre-commit проходят без `--no-verify`.
