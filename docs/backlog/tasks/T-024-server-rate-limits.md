# T-024: Серверные лимиты частоты: единые пороги, `RATE_LIMITED`, `rate_limit.hit`

- **Эпик**: E-04 Вход, сессии и лимиты
- **Статус**: решение владельца: Q-04
- **Параллельность**: нет: меняет продуктовый код
- **Роль-исполнитель**: разработчик
- **Участники стадий**: архитектура — архитектор; тестирование — тестировщик; ревью — независимый ревьюер
- **Навыки**: GraphQL Yoga middleware, Redis/память

## 1. Результат
Лимиты на запрос ссылки входа, проверку токена, мутации API и загрузки заданы в проекте едино для всех ролей, не отключаются персонально; превышение отвечает `RATE_LIMITED` и пишет `rate_limit.hit`.

## 2. Источники
- Журнал: #57
- Спецификации: `docs/spec/50-access/rate-limits.md`, `docs/spec/80-observability/error-dictionary.md`
- ADR: ADR-0024, ADR-0032

## 3. Границы и явно исключённое
- Входит: Механизм лимитов и точки применения по `rate-limits.md`.
- Не входит: Персональные настройки лимитов — их нет по правилу #57.

## 4. Зависимости и что разблокирует
- Зависит от: T-022
- Разблокирует: T-059

## 5. Критерии готовности и способ проверки
1. Превышение порога даёт `RATE_LIMITED` без раскрытия существования аккаунта — проверка: тест.
2. Лимит не зависит от роли — проверка: тест с `owner`.

## 6. Доказательство результата
Тесты, вердикт ревью. Отчёт по ритуалу проекта (`docs/reports/`) с разделом «Как проверено».

## 7. Пометки
Числовые пороги в спецификации не заданы; журнал #57 фиксирует только принцип.

## 8. Требует решения владельца
Q-04 — Пороги серверных лимитов частоты (см. `docs/backlog/owner-blockers.md`). Почему без этого задача не готова — в разделе 7.
