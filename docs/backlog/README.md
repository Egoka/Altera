- **Статус**: с 2026-09-14 владелец разрешил автоматический допуск существующих задач в Todo по [правилам пополнения](../multica/backlog-autofill.md). Исходная ревизия backlog — 2026-09-09; статические списки ниже требуют сверки.
- **Источники по старшинству**: журнал решений `docs/decisions/role-review-working-log-2026-09-08.md` → `docs/spec/` (включая `OPEN-QUESTIONS.md`) → ADR, `docs/vision/`, `docs/issues/00-roadmap.md`. При расхождении журнал главнее всего.
- **Операционная модель**: `docs/multica/operating-model.md` — читается перед планированием и исполнением любой задачи.

## 2. Идентификаторы и статусы

- `E-NN` эпик, `T-NNN` задача, `Q-NN` блокер владельца, `F-NN` будущий этап. Номера сквозные и не переиспользуются.
- Статусы задачи: `кандидат` (нет зависимостей и блокеров; предлагается владельцу), `зависит: T-…`, `решение владельца: Q-…`, `отложена: F-…`, `готова` (владелец или допуск оркестратора по правилам пополнения), `в работе`, `завершена` (после актуальной проверки и независимого ревью, где оно указано).
  Код, влитый в `app` без независимой приёмки, остаётся `в работе` с пометкой
  `(влита PR #N, merge <sha>; ждёт приёмки ALTE-…)`; отдельного статуса для этого состояния нет.
- Задача со ссылкой на «отложено» или `[ВОПРОС ВЛАДЕЛЬЦУ]` по существу не может быть `кандидат`.

## 3. Формат задачи

Шапка: эпик, статус, параллельность, роль-исполнитель, участники стадий, навыки, authorization,
baseline и проверяемая revision. Разделы: 1 результат; 2 источники; 3 границы, scope и
сохраняемый контракт; 4 зависимости; 5 критерии с AC-ID и способом проверки; 6 evidence с
`check_id`, actor/run, revision, dirty fingerprint и `trace_ref`; 7 пометки
`[ФАКТ]`/`[ДОПУЩЕНИЕ]`; 8 решение владельца; 9 handoff остановленной стадии. Шаблон —
`_templates/task.md`.

Запрещено в задачах: оценки в человеко-днях, цены, числовые лимиты и провайдеры, которых нет в журнале или спецификациях; пересказ спецификаций вместо ссылок; слова словаря ревизии 1 («витрина», «контур», «отбор», «правило-арбитр», «AI-оценка», «балл», «словесное объяснение»).

## 4. Как менять бэклог

1. Новая задача — только из источника (решение журнала, строка реестра, файл спецификации). Задача без источника не создаётся. Прямое письменное поручение владельца может разрешить конкретный план вне очереди; для него фиксируют authorization и scope, не создавая фиктивную `готова`.
2. Готовность — владелец или оркестратор по [разрешению на пополнение Todo](../multica/backlog-autofill.md). Для автодопуска запись в native issue достаточна до синхронизации файла; `завершена` — хранитель документации после evidence по операционной модели.
3. После правки файлов задач пересобираются `matrix.md`, `coverage.md`, `ready-candidates.md` и таблицы в `README.md` и эпиках — командой `python3 scripts/backlog/sync_status.py --apply` (см. п. 6). `coverage.md` статусов не содержит и скриптом не меняется.
6. Сверка с фактом: `sync_status.py` читает Multica (`multica issue list`, только чтение), слитые в `app` PR (`gh`) и receipt `docs/reports/tasks/T-*.json`, правит строку `Статус` в шапках и пересобирает таблицы. Запуск без флагов печатает таблицу сверки, `--check` возвращает 1 при расхождении. После закрытия ревью в Multica достаточно повторить `--apply`, проверить `git diff` и влить PR. Правила сопоставления — `docs/plans/2026-09-26-backlog-status-sync.md` §3. Тесты правил: `python3 -m unittest discover -s scripts/backlog`.
4. Ответ владельца на `Q-NN` вносится в журнал, затем меняются статусы задач; строка блокера получает «закрыт §N».
5. Устаревшая задача помечается `отменена: причина`, файл не удаляется.
