## 2. Что сделано

**Область линта.** Причина оказалась не там, где предполагал план. Корневой `eslint.config.mjs`
исключал `.nuxt`, но не `.output`; при этом обнаружился второй конфиг `web/eslint.config.mjs` —
почти дословная копия корневого, которая перекрывает его при запуске `pnpm -r exec eslint .` из
каталога пакета. Правка только корневого файла ничего не дала: eslint из `web/` его не читает.
`**/.output/**` и `**/.data/**` добавлены в оба конфига. `.prettierignore` `.output` содержал
изначально — расхождение было только в eslint.

**Мёртвый код.** После сужения области осталась одна настоящая ошибка: `mockStats` в
`web/app/pages/types/index.vue` — объявленная и нигде не используемая моковая статистика.
Удалена: это предмет T-005 («удаление мёртвого кода»), а не обход проверки.

**Тест-раннер.** `vitest@5.0.0` в `server` и `web`, конфигурации с `include: ["tests/**/*.test.ts"]`.
Тесты сервера лежат в `server/tests/`, вне `rootDir: src`, поэтому `tsc` их не собирает и
`dist` не растёт.

**Тесты сервера (19).**
`server/tests/permissions.test.ts` — `ensureAuthenticated` и `ensureHasRole`: единственный контур
доступа в API. `server/tests/admin.test.ts` — `validatePagination`, `validateSort`,
`calculatePagination`, `getCacheKey`. Допущение плана подтвердилось запуском: из `../prisma`
импортируется только тип, подключения к Redis при импорте не происходит, тесты идут без
внешних сервисов.

**Тесты веба (5).** `web/tests/i18n-locales.test.ts` — паритет ключей `ru`/`en` в обе стороны,
отсутствие пустых переводов, все значения строки. Выбор не случаен: ключ, добавленный в одну
локаль и забытый в другой, ломает страницу молча — vue-i18n подставляет сам ключ.

**CI.** Проверка старта вынесена в `server/scripts/smoke.sh`, который вызывают и CI, и локальный
запуск, — проверяется один и тот же код. Скрипт поднимает собранный сервер, ждёт готовности,
шлёт настоящий GraphQL-запрос `{__typename}` с заголовком CSRF и печатает вывод сервера при
неудаче. Задание `checks` дополнено шагами `pnpm format` и `pnpm test`; в задание `server-smoke`
добавлен сервис Redis.

## 4. Отклонения и находки

**Дымовая проверка не подтверждает связность с Redis.** Проверено: при `REDIS_URL`,
указывающем в мёртвый порт, сервер всё равно стартует и отвечает `{"data":{"__typename":"Query"}}`
— запрос `__typename` кеша не касается, а `ioredis` с `maxRetriesPerRequest: null`
переподключается в фоне. Сервис Redis в CI нужен потому, что `server/src/redis.ts` бросает
исключение при отсутствии самой переменной `REDIS_URL`, а не потому, что проверка тестирует
Redis. Что проверка действительно доказывает: сервер собирается, запускается и отвечает на
GraphQL-запрос. Полноценная проверка зависимостей — это эндпоинт `/health`, он относится к
задачам наблюдаемости (E-13), здесь не делался.

**Ошибка в предположении плана про линт**, зафиксирована как отклонение: план называл причиной
корневой `eslint.config.mjs`, фактическая причина — второй конфиг в `web/`, перекрывающий
корневой. Дублирование двух почти одинаковых конфигов сохраняется и относится к T-005; в этом
заходе не устранялось, чтобы не выходить за границы плана.

**Локальный `dotenv` маскирует отсутствие переменных.** `server/.env` существует, поэтому
`unset REDIS_URL` в локальном запуске ничего не меняет: `dotenv/config` подставляет значение из
файла. Первая попытка обратной проверки из-за этого дала ложный успех и была заменена на поломку
сборки. В CI файла `.env` нет, переменные приходят из задания.

**Pre-commit и commitlint не запускались вообще — обнаружено при проверке.** План исходил из
того, что хук репозитория падает на `format && lint && test`. Фактически он не выполнялся ни разу:
в `.git/config` стоял `core.hooksPath = .githooks`, а каталога `.githooks` в репозитории нет.
husky 9 ожидает `.husky/_`. Следствие шире, чем pre-commit: не работал и `commit-msg`, то есть
**commitlint не проверял ни одно сообщение коммита** — правило conventional commits из
`CLAUDE.md` держалось только на дисциплине автора.

Исправлено двумя шагами. Локально: `git config core.hooksPath .husky/_`. Долговечно: в корневой
`package.json` добавлен скрипт `prepare: husky`, которого не было, — поэтому husky не
устанавливал привязку ни при одной установке зависимостей.

Проверено:

```
$ git config core.hooksPath .githooks   # ломаем обратно
$ npm run prepare
> husky
$ git config core.hooksPath
.husky/_                                # привязка восстановлена

# commit-msg на заведомо плохом сообщении
$ git commit -m "Плохое Сообщение Без Типа."
✖   subject may not be empty [subject-empty]
✖   subject may not end with full stop [subject-full-stop]
✖   type may not be empty [type-empty]
✖   found 3 problems, 0 warnings
husky - commit-msg script failed (code 1)
```

Оговорка: `core.hooksPath` живёт в `.git/config` и не версионируется. В свежем клоне привязку
ставит `prepare`, но только при установке зависимостей через npm или pnpm с включёнными
скриптами жизненного цикла.

**Пять коммитов этой сессии, сделанные до находки, прошли без проверки хуками** — они помечены
`--no-verify`, но фактически хуки не сработали бы и без флага. Их сообщения соответствуют
conventional commits, проверено чтением, но commitlint их не валидировал.

**Версии Node и pnpm не пинованы**: локально Node 24 и pnpm 10.12.4/10.18.3, в CI Node 20 и
pnpm 10.13.1. Это остаётся в T-001 и здесь не делалось.

**Тесты написаны под существующее поведение.** Дефектов, требующих правки продуктового кода,
тесты не выявили. Известные дыры доступа (`article(slug)` отдаёт черновики, `user.email` в
публичном типе) тестами не покрывались: их исправление — отдельные задачи, а закреплять
тестом текущее ошибочное поведение неверно.

## 5. Что это меняет для автономного цикла

Шаг наблюдения перестал быть слепым: `pnpm test`, `pnpm lint` и `pnpm format` теперь различают
рабочее состояние и поломку, а CI не скрывает падение старта. Хуки репозитория впервые реально
работают: pre-commit гоняет проверки, commitlint валидирует сообщения, `--no-verify` больше
не нужен.

Остальные условия автономности не выполнены и в границы плана не входили: в статусе `готова`
по-прежнему одна задача (T-108), бюджет итераций стадии остаётся `[ДОПУЩЕНИЕ]` без решения
владельца, механизм повторного входа в цикл (автопилоты, расписание) не включён.
