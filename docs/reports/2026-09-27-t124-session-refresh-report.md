Задача закрывает два дефекта, найденных независимым ревью 2026-09-26 у возвращённой T-023
(ALTE-97, PR #168): `refreshSession` не вызывался ни клиентом, ни BFF, поэтому сессия жила
15 минут; ротация меняла `tokenHash` без условия на прежнее значение.

## 1. Что изменилось

### Обмен refresh при SSR (AC-1)

`web/server/middleware/session-refresh.ts` — новый middleware Nitro. Через 15 минут браузер
перестаёт присылать access-cookie (`maxAge` = `ACCESS_COOKIE_MAX_AGE_SECONDS`), и навигация
вошедшего выглядела навигацией гостя: `web/app/middleware/auth.global.ts` уводил её на `/login`,
хотя refresh-cookie жива 30 дней. Middleware обменивает refresh до маршрутов и рендера, а
обновлённую пару пишет и в ответ, и в заголовки самого запроса (`withUpdatedCookies`): SSR читает
cookie из запроса, поэтому без подмены страница всё равно считала бы посетителя гостем, а её
запрос к API ушёл бы с прежним токеном.

Обмен ограничен навигацией страницы (`needsNavigationExchange`): внутренние вызовы страницы
(`/api/*`), ресурсы сборки (`/_nuxt/*`) и файлы с общим кешем (ленты, `sitemap.xml`,
`robots.txt` — им `feedRoutes.ts` ставит общий `cache-control`) исключены, иначе `Set-Cookie`
попал бы в кеш, общий для всех читателей.

### Обмен по ответу `UNAUTHENTICATED` и один повтор (AC-1)

`web/server/api/graphql.post.ts` отдаёт запрос через `sendWithSessionRefresh`: если API ответил
`UNAUTHENTICATED`, а refresh-cookie есть, маршрут обменивает refresh и повторяет исходный запрос
**один раз**. Второй отказ означает мёртвую сессию: обе cookie стираются. Недоступный апстрим
cookie не трогает — сессия может быть жива. Операции, распоряжающиеся сессией сами
(`refreshSession`, `logout`, `logoutAll`, ветки входа, самостоятельное восстановление,
подтверждение архива), из обмена исключены.

### Один общий обмен на сессию (AC-3)

Реестр `sessionRefreshExchanges` (`web/server/utils/sessionRefresh.ts`) делает один обмен на
предъявленный токен и держит его результат ещё 30 секунд после завершения. Вкладки просыпаются
вместе и уходят со одной и той же старой cookie; без общего обмена вторая предъявила бы уже
ротированный токен, и сервер прочитал бы это как кражу — по `session-lifecycle.md` §2.4 он
отзывает **все** сессии пользователя. Результат «апстрим недоступен» не запоминается: следующий
запрос пробует обмен снова.

### Условная ротация refresh (AC-2)

`server/src/auth/session.ts`: `rotateSession` заменяет `tokenHash` через `updateMany` с условием
`{ id, tokenHash: прежний, revokedAt: null }` вместо `update({ where: { id } })`. `count > 0` —
ротация, строка результата собирается из прочитанной и новых полей. `count === 0` — гонка
проиграна или сессию отозвали между чтением и заменой: исход считается как у повторного
предъявления (`reuse_detected` по `previousTokenHash` победителя) либо `revoked`/`expired` по
оставшейся строке, но не `unknown`. `SessionClient` получил `tokenHash` в `where` у `updateMany`
и `SessionWriteData` в `data`; неиспользуемый `update` из интерфейса убран.

Пара победителя больше не теряется поверх пары проигравшего: до исправления оба параллельных
обмена писали свой `tokenHash`, и последний записавший обесценивал токен, уже отданный первому.

### Прочее

- `web/server/utils/nitroFetch.ts` — единственное место вызова `$fetch.raw` в BFF. Второй вызов
  (в новом middleware) разворачивал типизацию маршрутов Nitro ещё раз, и проверка типов серверного
  проекта падала с `TS2321: Excessive stack depth`; общий типизированный `nitroFetchRaw` это снимает.
- `web/tests/e2e/helpers/session-token.ts`: `createSession` отдаёт и refresh-токен (в базе лежит
  только его хэш), `signAccessToken` принимает срок — отрицательный даёт уже истёкший токен.
- Двойники сессии в `server/tests/session-rotation.test.ts` и `session-mutations.test.ts` отдают
  **копию** строки из `findUnique`/`findFirst`/`create`, как настоящий клиент. До этого прочитанный
  объект менялся вместе с хранилищем, и условная замена по прежнему `tokenHash` всегда сходилась бы
  — двойник не увидел бы гонку.

## 4. Границы и остаток

- **Независимое ревью** с маркером `ALTERA_REVIEW_V1` на финальном head не получено: его
  назначает контроллер, исполнитель свою работу не принимает.
- **Реестр обменов живёт в памяти процесса Nitro.** При нескольких экземплярах веб-сервера защита
  от ложного reuse работает в пределах одного: вкладки, попавшие на разные экземпляры, снова могут
  предъявить один токен дважды. Сейчас экземпляр один (прод-окружения в РФ нет, T-103); для
  масштабирования нужен общий счёт обменов — отдельная задача.
- **Лимит «до 10 устройств»** (`[ДОПУЩЕНИЕ]` §6 `session-lifecycle.md`) в задачу не входил.
- **Перенос access-токена из тела ответа в cookie целиком** не делался: по границам задачи это
  либо часть ADR-0023 по признанию архитектора, либо отдельная задача. Сейчас access приходит в
  теле ответа входа, а cookie ставит BFF.
- **Спецификации не менялись**: §2.4 и §2.5 `session-lifecycle.md` уже описывают ротацию,
  реакцию на повторное предъявление и сроки; правило «обмен делает BFF» задано ADR-0023 п. 3.
- **Приёмка T-023** (ALTE-97) идёт в её карточке: эта задача её разблокирует.
- **Гонка двух вкладок остаётся кражей на стороне API.** Сервер по-прежнему отзывает все сессии,
  если один токен предъявлен дважды; смягчения правила §2.4 задача не вносит — от ложного
  срабатывания защищает общий обмен в BFF.
