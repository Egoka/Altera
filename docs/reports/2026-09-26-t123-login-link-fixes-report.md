## Результат

Вход по одноразовой ссылке больше не создаёт сессию заблокированному администратором аккаунту ни
одним путём, работает при переходе из веб-почты и оставляет в браузере httpOnly refresh-cookie.
Отметка использования токена атомарна.

## Что изменено

`server/src/graphql/auth/resolver.ts`. Ветка архива аккаунта вынесена в `archivedOutcome` и
вызывается и `verifyMagicLink`, и `acceptConsent` — до записи согласия. Административный архив
сессии не получает, токен не гасится (форма оспаривания открывается им же, журнал #48), согласие
не записывается; самостоятельный архив получает только ограниченную сессию
(`session-lifecycle.md` п. 7). Гашение токена вынесено в `consumeToken`: условный `updateMany`
по `{ id, usedAt: null }` с проверкой числа строк; нулевой счёт отвечает как использованный
токен (`NOT_FOUND`, лог `auth.login.failed` с `reason: "used"`).

`web/server/utils/sessionCookie.ts`, `web/server/api/graphql.post.ts`. Появился
`isLoginTokenExchange`: обмен токена входа — единственное исключение из проверки происхождения.
Для остальных мутаций `isSameOriginMutation` работает как прежде.

`web/app/composables/useGraphQL.ts`. Серверная ветка читает сырой ответ BFF и переносит его
`Set-Cookie` в ответ навигации, а заголовки запроса переносит сама — так же, как это делает
`useRequestFetch`, кроме заголовков соединения и тела (у подзапроса своё JSON-тело).

`.github/workflows/pull_request.yml`. Новый шаг `server-smoke` с `T123_TEST_DATABASE_URL`.

## Решение по §7 [ДОПУЩЕНИЕ]

Задача оставляла выбор между промежуточным экраном с кнопкой и исключением для обмена токена.
Выбрано исключение: AC-2 требует, чтобы открытие ссылки завершало вход, и отдельно требует,
чтобы «межсайтовая мутация, не являющаяся обменом токена» продолжала отклоняться. Полномочие в
`verifyMagicLink` и `acceptConsent` даёт секрет из письма, а не cookie браузера, поэтому CSRF на
них не действует: чужая страница токена не знает, а знающий его может обменять его и напрямую.

Исключение сужено тремя условиями, чтобы им нельзя было прикрыть чужую мутацию:

1. все корневые поля операции — только `verifyMagicLink` и `acceptConsent`, поэтому батч обмена с
   любой другой мутацией исключения не получает;
2. тип тела — `application/json`: простую форму со чужого сайта с таким типом без CORS не
   отправить, а preflight на маршруте не разрешён;
3. запрос является переходом документа (`sec-fetch-mode: navigate` либо заголовка нет, как у
   серверного вызова): фоновый запрос со чужой страницы исключения не получает.

Остаточный риск, который исключение не закрывает, — login CSRF: чужая страница может увести
браузер по ссылке из письма злоумышленника и войти его аккаунтом. Промежуточный экран с кнопкой
этот риск закрывал бы, но нарушал бы формулировку AC-2 о завершении входа по открытию ссылки.
Риск не изменился относительно прежнего поведения перехода по ссылке и требует решения владельца,
если промежуточный экран всё же нужен (он же защищал бы от почтовых сканеров, §7).

## Критерии

| Критерий                                                                         | Статус | Доказательство                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC-1: `acceptConsent` отвечает как `verifyMagicLink` на архив                    | passed | `server/tests/auth-magic-link.test.ts`, блок «acceptConsent and an archived account»: административный архив — `outcome: archived_admin`, `session: null`, результат совпадает с `verifyMagicLink`, сессий 0, согласий 0, `usedAt` остаётся `null`; самостоятельный — `archived_self` с `limited: true`                     |
| AC-2: межсайтовый переход завершает вход, прочие межсайтовые мутации отклоняются | passed | `web/tests/session-cookie.test.ts`, блок `isLoginTokenExchange` (10 случаев); `web/tests/e2e/23-login-cross-site.spec.ts`: переход с `http://webmail.test` доходит до `/me`; на настоящем сервере с `Sec-Fetch-Site: cross-site` обмен токена отвечает 200, `logoutAll` — 403, фоновый обмен (`sec-fetch-mode: cors`) — 403 |
| AC-3: после `/auth/verify` в браузере есть httpOnly refresh-cookie               | passed | тот же спек на реальном сервере (Nitro `.output` + API, не мок BFF): `altera_refresh` присутствует, `httpOnly: true`, `sameSite: Lax`, в `document.cookie` отсутствует, `refreshSession` его принимает и ротирует, в базе одна сессия                                                                                       |
| AC-4: два параллельных обмена одного токена — не больше одной сессии             | passed | `server/tests/auth-magic-link-database.test.ts` на PostgreSQL, 3 сценария (новый аккаунт, существующий, самостоятельный архив): одна попытка успешна, вторая — `NOT_FOUND`/`magicLink`, в базе одна сессия                                                                                                                  |

RED зафиксирован по каждому исправлению: без условного `updateMany` три сценария PostgreSQL дают
две сессии на два обмена; без исключения для обмена токена межсайтовый переход остаётся на
`/auth/verify` (таймаут ожидания `/me`); без переноса `Set-Cookie` refresh-cookie в браузере нет.
