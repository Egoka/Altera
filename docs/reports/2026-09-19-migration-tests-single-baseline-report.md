- **Статус**: завершён, PR в `app`

## 1. Итог

Тесты миграций на PostgreSQL 17, которые запускает CI, стали быстрее в 4–6 раз: 2,1–3,7 с на тест вместо
10,6–18,7 с. Нестабильный T-016 (38,2 с при таймауте 30 с) теперь занимает меньше 4 с. Что проверяют тесты,
не изменилось: базовые миграции применяются по порядку, каждая в своей транзакции; целевая миграция
применяется отдельным вызовом с проверкой кода выхода; все проверки результата прежние. Таймауты не менялись
и остаются 30 с.

## 2. Причина

`applyBaselineMigrations()` запускал `pnpm exec prisma db execute --file` отдельно для каждой миграции старше
целевой. Каждый запуск pnpm и Prisma CLI в CI стоит около секунды:

| Тест                                             | Базовых миграций | Запусков Prisma на тест |
| ------------------------------------------------ | ---------------- | ----------------------- |
| T-016 `media-asset-migration-database.test.ts`   | 11               | 12                      |
| T-017 `bookmark-plan-migration-database.test.ts` | 12               | 13                      |
| T-047 `job-queue-database.test.ts`               | 15               | 16                      |

Каждая новая миграция добавляет ещё запуск. Когда раннер работает медленно (прогон
https://github.com/Egoka/Altera/actions/runs/35454090217, попытка 1), время растёт пропорционально числу
запусков, и тест выходит за 30 с. Сам код не менялся: повтор того же коммита прошёл за 14,0 с.

## 3. Изменения

| Файл                                                    | Изменение                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server/tests/helpers/migration-database.ts`            | `migrationsBefore(target)`; `baselineMigrationScript(target)` — файлы по порядку имён, после каждого `;` и `COMMIT;`; `applyBaselineMigrations(target, url)` — один `prisma db execute --stdin`, при ошибке исключение с выводом Prisma; `applyMigration(migration, url)` — отдельный `--file` |
| `server/tests/migration-database-helper.test.ts`        | тест без базы: точный список 11 миграций до `20260916170000_media_assets`, порядок, отдельный `COMMIT` после каждой, без целевой                                                                                                                                                               |
| `server/tests/media-asset-migration-database.test.ts`   | T-016 использует helper; локальные `runPrisma`/`applyBaselineMigrations`/`applyTargetMigration` удалены                                                                                                                                                                                        |
| `server/tests/bookmark-plan-migration-database.test.ts` | T-017 — то же                                                                                                                                                                                                                                                                                  |
| `server/tests/job-queue-database.test.ts`               | T-047 — `applyMigrations` через helper                                                                                                                                                                                                                                                         |

Почему `COMMIT` после каждого файла. `prisma db execute` отправляет скрипт одним простым запросом.
PostgreSQL выполняет такой запрос одной неявной транзакцией до ближайшего явного `COMMIT`. Если просто склеить
файлы, границы транзакций сдвинутся: например, значения `Role`, добавленные `ALTER TYPE … ADD VALUE` в
`20260915090000`, остались бы незафиксированными до `COMMIT` в `20260915170000`. `COMMIT` после каждого файла
фиксирует каждую миграцию отдельно, как при прежних отдельных вызовах. Если открытой транзакции нет, PostgreSQL
только пишет `WARNING: there is no transaction in progress`. В журнале PostgreSQL CI таких предупреждений
ровно по одному на базовую миграцию: 11 + 11 (T-016), 15 + 15 (T-047), 12 × 3 (T-017) = 88. Значит, каждая
миграция зафиксирована отдельно.

## 4. Расширение: T-047

Пока шла работа, в `app` влили T-047 (PR #123). `job-queue-database.test.ts` устроен так же, CI запускает его
в том же job, а в зелёных прогонах он уже занимал до 18,7 с при таймауте 30 с. Поэтому ветка приняла свежий
`origin/app` (merge-коммит `a700954`), и T-047 тоже переведён на helper. В плане и в сообщении коммита
`8f05cdd` число базовых миграций T-047 указано как 13. Верное число — 15 (по списку каталогов и по числу
предупреждений выше). План исправлен; уже отправленный коммит не переписывался.

## 8. Ограничения и дальнейшее

- Четыре migration-теста вне CI (`admin-records`, `article`, `audit-review-thread`, `taxonomy`) всё ещё
  запускают Prisma на каждую миграцию. Их можно перевести на helper отдельной задачей.
- Если появится миграция из одного оператора, который нельзя выполнять в транзакции (`CREATE INDEX
CONCURRENTLY`), общий скрипт на ней упадёт с выводом Prisma. Тогда такую миграцию нужно будет применять
  отдельным вызовом.
- В журнале PostgreSQL CI появились предупреждения `there is no transaction in progress`, по одному на
  базовую миграцию. Это ожидаемый след `COMMIT` после каждого файла, а не ошибка.
