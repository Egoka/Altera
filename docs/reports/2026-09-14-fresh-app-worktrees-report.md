## Результат

Правило старта новой задачи задаёт явный порядок: успешный fetch origin/app → полный SHA →
проверка готовности на нём → новая ветка и worktree → совпадение HEAD и чистота → сохранение
baseline, пути и evidence в parent → передача исполнителю. При ошибке fetch нельзя использовать
старую локальную ссылку. Продолжение начатой задачи сохраняет прежние ветку, baseline и историю.

Полный контракт размещён в [fresh-task-worktree](../multica/fresh-task-worktree.md); ссылки
добавлены в AGENTS.md и документы движения очереди. Claude Code получает его через существующий
адаптер CLAUDE.md → AGENTS.md. Исходный код приложения не изменён.

## Проверка

Эта правка создана в отдельном worktree от app после успешного fetch. До первых изменений:
`git rev-parse HEAD` вернул полный baseline выше, `git status --porcelain=v1` не вывел строк.
Это проверяет создание и начальную чистоту worktree, но не утверждает, что все будущие native
агенты технически лишены возможности нарушить инструкцию.

`pnpm install --frozen-lockfile --offline` завершился с exit 0, lockfile не изменён.
Независимый reviewer `/root/infra_preflight` принял контракт,
защиту уже начатых задач и чужих dirty worktree: PASS, Critical/Important нет.
Обязательные локальные hooks и GitHub CI привязаны к PR публикации этой ревизии.

В Multica правило добавлено перед прежними инструкциями десяти ролей, squad, очереди и recovery.
Полный применённый [prefix](../multica/snapshots/2026-09-14-fresh-task-worktree/prefix.json)
и [readback](../multica/snapshots/2026-09-14-fresh-task-worktree/verified.json) сохраняют текст,
SHA-256 значений до/после и время проверки. Статусы автопилотов и расписания не меняются.
Предыдущие инструкции сохранены без сокращения; текущие задачи не перезапускались.

При проверке первого коммита reviewer выявил лишнюю пустую строку в конце текстового snapshot.
Snapshot перенесён в JSON: поле `text` сохраняет точные применённые bytes, включая разделитель
перед прежними инструкциями. Поэтому live-настройки и их SHA-256 не менялись. После исправления
проверяется полный staged diff от baseline, включая новые файлы; первый дефект не скрывается
успешной проверкой только unstaged diff.

Проверка native поведения нового старта будет относиться к следующей реально выбранной задаче:
не создавалась фиктивная задача и не сбрасывалась работа текущих исполнителей ради теста правила.
