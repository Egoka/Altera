## Результат

1. **Миграция** `server/prisma/migrations/20260928120000_legacy_body_content_document/migration.sql`
   переводит `article_translations.body` и `article_revisions.body` в документ `content`
   (ADR-0001, ADR-0029) и заменяет тело trigger T-015 так, что legacy-запись в `articles.body`
   тоже даёт документ, а не JSON-строку.
2. **Алгоритм конверсии существует в одном месте** — SQL-функция `t020_legacy_body_to_document`.
   Её вызывают миграция, trigger и скрипт проверки. Второй реализации того же алгоритма на
   TypeScript в проекте нет намеренно: расхождение SQL и TS было главным риском задачи.
3. **`pnpm verify:legacy-bodies`** (`server/scripts/verify-legacy-bodies.ts`) читает все тела из
   трёх источников, прогоняет каждое через ту же SQL-функцию и проверяет результат **настоящим
   валидатором каталога** — `readDocument` из `@altera/content` (`migrateDocument` +
   `validateDocument`). Скрипт только читает. Код выхода: 0 — неконвертируемых нет; 1 — есть
   (печатаются идентификаторы); 2 — нет `DATABASE_URL` либо не применены миграции.
4. **Репетиция миграций** проведена дважды на локальных копиях: весь набор E-03 от состояния до
   E-03 и копия населённой базы. Development Neon и любая внешняя база не читались и не менялись.

### Правила конверсии

| Вход | Результат |
| ---- | --------- |
| уже документ (`doc` с целым `attrs.schemaVersion`) | возвращается без изменений |
| JSON `null`, пустая строка | документ из одного пустого абзаца |
| JSON-строка с legacy-корнем `{"type":"root","children":[…]}` | разбирается как объект |
| JSON-строка обычного текста | каждая непустая строка текста → отдельный абзац |
| JSON-объект legacy-корня | каждый дочерний узел → абзац с его текстом, порядок сохраняется |
| JSON-массив узлов | то же, что `children` |
| число, boolean, объект неизвестной формы | `NULL` — «неконвертируемое тело» |

`NULL` — сознательный отказ, а не ошибка: постпроверка миграции на таком теле останавливает
транзакцию, и данные остаются нетронутыми. Молчаливая потеря текста хуже остановки деплоя.

Функция идемпотентна: на своём же результате возвращает его без изменений, поэтому повторное
применение миграции ничего не переписывает и `attrs.id` абзацев остаются стабильными
(ADR-0001 п. 3).

## Границы

- **Каталог блоков (Q-02) вне объёма.** Конверсия использует единственный блочный узел «абзац»
  `[ДОПУЩЕНИЕ]`. Заголовок и цитата legacy-тела становятся абзацами: текст сохраняется целиком и
  в исходном порядке, семантика блока — отдельная задача после утверждения каталога для конверсии.
  Граница подтверждена handoff оркестратора 2026-09-27 и §3 карточки задачи.
- **Legacy-поля `articles.*` и trigger T-015 не снимаются.** T-015 отнесла их снятие к
  «T-020/API-cutover»; сам cutover — перевод резолверов на языковые версии — в объём T-020 не
  входит: `Article.body` читают `server/src/graphql/article/resolver.ts`, `.../tag/resolver.ts`,
  `.../section/resolver.ts` и GraphQL-поле `Article.body: String!`. Поэтому `articles.body`
  остаётся строковым legacy-полем, а trigger — временным контрактом совместимости, который
  теперь пишет документ.
- Обычный текст разбивается на абзацы по переводам строк, лишние пробелы по краям абзаца
  срезаются: перевод строки внутри абзаца в документе смысла не имеет.

### Отказ на неконвертируемом теле

Проверено, что критерий имеет смысл, а не выполняется тождественно.

| Сценарий | Фактический результат |
| -------- | --------------------- |
| В копии населённой базы одному телу версии присвоено `'42'::jsonb`, затем `migrate deploy` | exit 1, `Database error code: P0001`, `ERROR: T-020: тел материалов, не приводимых к документу content: 1; какие именно — покажет pnpm verify:legacy-bodies`; данные не изменились — `487 string + 67 object + 1 number` |
| То же тело в уже сконвертированной базе, `pnpm verify:legacy-bodies` | exit 1, `неконвертируемых: 1`, напечатан идентификатор `01fd0f7f-2aa9-49e0-b754-2ad117b091df`, `Итого: … 1 неконвертируемых` |

Диагностика в `migrate deploy` видна потому, что в файле миграции нет собственных `BEGIN`/`COMMIT`.
С явной транзакцией Prisma не доходила до `COMMIT` и сообщала `current transaction is aborted`
вместо текста постпроверки; это наблюдалось на промежуточной версии файла и исправлено.
Управление транзакцией нужно там, где в файле есть `ALTER TYPE … ADD VALUE` (как в T-015);
здесь такого оператора нет, а `prisma migrate deploy` и `prisma db execute` дают транзакцию сами.

## Находка за пределами объёма

`createArticle` в `server/src/graphql/article/resolver.ts` создаёт статью вложенным
`translations: { create: … }`. Trigger T-015 к этому моменту уже вставил исходную версию, поэтому
вложенная вставка нарушает уникальность `(articleId, locale)`. Проверено на настоящей базе:
запрос, повторяющий данные резолвера, отказывает с
`Unique constraint failed on the fields: (articleId, locale)`.

Это **дефект, существовавший до T-020** (взаимодействие T-039 и T-015), а не следствие конверсии:
строка `body: []` в резолвере до базы не доходит. Действующие тесты резолвера используют двойник
Prisma и поэтому этого не видят. Конверсия обрабатывает и такую форму (JSON-массив → документ из
одного пустого абзаца), так что через этот путь база не может вернуться к недокументу. Правка
резолвера требует собственных тестов и ревью и в объём T-020 не входит — передаю как отдельный
вопрос владельцу и координатору.

## Ограничения

- Прод-окружения в РФ нет (T-103); репетиция выполнена на локальных копиях, а не на копии
  production. Копия development Neon не снималась: в этом рабочем дереве нет `server/.env`,
  а локальный `pg_dump` отсутствует (в контейнере — PostgreSQL 16, Neon новее). Репетиция на
  клоне development-данных остаётся релизным шагом.
- CI использует PostgreSQL 17, локальная репетиция — 16.15. Использованные средства
  (`jsonb`, `plpgsql`, `gen_random_uuid`, `regexp_split_to_table`) присутствуют в обеих версиях,
  но это не заменяет прогон на 17.
- Данные локальной базы синтетические (`seed/dev-seed.ts` и `seed/seed.ts`), поэтому набор форм
  legacy-тела в репетиции Р2 ограничен теми, что порождает сид; отдельные формы (пустое тело,
  текст, похожий на JSON, многострочный текст, неконвертируемое тело) проверены явно в Р1,
  тестах и сценарии отказа.
- Скрипт `verify:legacy-bodies` требует применённых миграций: без функции конверсии он выходит с
  кодом 2. Проверка конвертируемости до применения T-020 выполняется самой миграцией — её
  постпроверка останавливает транзакцию и не меняет данные.
- Семантика заголовка и цитаты уплощена в абзац по границе Q-02. Возврат семантики потребует
  отдельной конверсии после того, как владелец утвердит каталог для конверсии legacy-данных.
- Скрипт и тест — первое подключение `@altera/content` к `server` (devDependency). Рабочий код
  `server/src/**` пакет по-прежнему не импортирует; интеграция резолверов остаётся за T-049.
- Зелёный локальный набор не означает зелёный aggregate CI: он проверяется на PR.
- Deployment не выполнялся.
