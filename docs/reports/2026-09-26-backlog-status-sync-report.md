## 2. Как сопоставлялись статусы

Словарь `README.md` §2 не знает состояния «влито, ждёт приёмки», поэтому такие задачи получили
`в работе` с пометкой: номер PR, merge и ALTE ожидающей приёмки. Новый статус не вводился.

- `done` в Multica → `завершена (PR #N, merge <sha>; приёмка ALTE-…)`.
- `in_review` → `в работе (влита PR #N, merge <sha>; ждёт приёмки ALTE-…)`.
- Если задача входит в список «Блокирует» открытого Q, к пометке добавлено «реализована при
  открытом Q-NN».
- Невзятые задачи: из `зависит:` убраны уже завершённые зависимости.
- PR — из receipt `docs/reports/tasks/T-NNN.json`, иначе самый ранний слитый PR с номером задачи в
  ветке или заголовке.
- Стадийные подзадачи («T-011 стадия 4») не считаются приёмкой.
- `завершена`, записанная хранителем документации, не понижается (T-087). Ручная пометка при ней
  сохраняется (T-053).

## 7. Как повторить сверку после окончания ревью

```bash
git fetch origin && git switch -c docs/backlog-status-resync origin/app
python3 scripts/backlog/sync_status.py                  # таблица расхождений, ничего не пишет
python3 scripts/backlog/sync_status.py --apply          # шапки и таблицы
python3 scripts/backlog/sync_status.py --check          # должно быть 0 и exit 0
python3 -m unittest discover -s scripts/backlog
git diff --stat
```

Скрипт читает Multica через CLI из `Multica.app` (`MULTICA_BIN` переопределяет путь) и слитые PR
через `gh`. Нужна авторизация обоих; оба только читают. После закрытия `in_review` в Multica
задачи перейдут в `завершена (…; приёмка ALTE-…)`. Невзятые задачи, чьи зависимости все
завершены, станут `кандидат`. Q-пометки останутся, пока вопрос в `owner-blockers.md` открыт.
Если появится новая частично принятая задача, её добавляют в `PREFER_OPEN_REISSUE` с причиной.
