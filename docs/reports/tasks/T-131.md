## T-131 — Уведомление сотрудникам о новом обращении в поддержку

**Task ID:** T-131
**Итоговый head:** `1912ec1f2256ba871fa919f93b069fa2579e370b`
**PR:** #252 → merge `be6675afb677bd97526bb7e00a26afe7d501a15b`

### Проблема

Выборка получателей уведомления требовала `isServiceAccount: false`, тогда как роли
`admin`/`owner` назначаются с `isServiceAccount: true`. Запрос возвращал пустой список —
сотрудники не получали писем. Сбой уведомления поднимался наружу после записи обращения:
пользователь видел ошибку и повторной отправкой создавал дубль.

### Решение

Получатели — все активные `admin` и `owner` из служебных записей; фильтр `isServiceAccount`
убран. Шаг уведомления не поднимает ошибку наружу: сбой пишется как `backend.error`.
Контракт `createSupportRequest`, `requestId` и шаблон `support_request_staff` не менялись.

### Критерии

- **AC-1 passed** — `server/tests/support-requests.test.ts`: уведомляет служебные записи
  admin и owner (2 письма), архивированная не получает.
- **AC-2 passed** — сбой почты не отменяет сохранённое обращение, номер обращения
  возвращается, повтор не создаёт дубль.

### Проверки

Формат, линт, тесты (server 858/44 skipped, web 588, content 99), сборка сервера и веба —
exit 0. CI run 36294944659 зелёный.
