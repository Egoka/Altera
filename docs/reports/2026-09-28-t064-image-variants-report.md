## 1. Объём и границы

Выполнен шаг конвейера после мастер-файла (`upload-pipeline.md` п. 5, `image-variants.md` §2 п. 2)
и вывод его результата в вебе: из мастера создаются размытый заполнитель, thumbnail и адаптивные
варианты в AVIF и WebP по централизованной матрице; веб строит из набора `<picture>` с
`srcset`/`sizes` и единым `alt`; `/_ipx/` не используется (ADR-0030 п. 1–2).

Вне объёма и не затронуто: ручное AI-улучшение (F-04), черновик `alt` моделью (T-048), перевод
карточек и страниц на медиа из базы (T-056, T-066), подписанные ссылки на медиа черновика в
редакторе (`access-and-signed-urls.md` п. 5), кадрирование по фокусной точке и задание
перегенерации (`media.update.meta`, `media.regenerate`) — отдельные задачи эпика.

Загрузка пользователям по-прежнему закрыта признаком `MEDIA_UPLOAD_ENABLED`: числовые параметры
матрицы и сжатия остаются `[ДОПУЩЕНИЕ]` до утверждения владельцем (журнал §33 п. 3).

### 2.1 Матрица одним местом

`image-variants.md` §2 п. 1 и заметка владельца п. 3 требуют централизованной матрицы: один список
ширин и форматов на весь продукт, а не набор чисел по компонентам. Числа лежат в `limits.ts`,
правила — в `variant-matrix.ts`:

- ширины 480/960/1440/2000 — временная матрица журнала §33 п. 2 (ширины ADR-0030);
- форматы AVIF и WebP (журнал §29.4), порядок предпочтения — AVIF первым;
- берутся только ширины не больше мастера: конвейер не увеличивает изображение
  (`image-variants.md` §5 — мастер 1000 px даёт 480 и 960, без 1440 и 2000);
- мастер мельче наименьшей ширины матрицы всё равно получает один вариант в свою ширину: публичен
  только вариант, сам мастер публичным не бывает (`access-and-signed-urls.md` п. 1–2), и без
  варианта у готовой записи нечего показать;
- thumbnail — наименьшая ширина полученного набора. Отдельного числа не вводится: точные точки
  останова остаются за проходом конвейера (журнал §29.12), и набор не пополняется шириной,
  которой владелец не утверждал.

### 2.2 Заполнитель

Заполнитель — WebP шириной 48 px строкой `data:` в самой записи, отдельным объектом хранилища он
не лежит: 48 px названо владельцем в заметке п. 2 («очень маленькая миниатюра / размытый
placeholder, начиная примерно с 48 × 48») — это единственное число набора, которое задал владелец.
Строка в записи не стоит отдельного запроса (`image-variants.md` §2 п. 4). Формат один: WebP
читают все браузеры, которым вообще показывается сайт. Прозрачность мастера сохраняется, иначе
заполнитель PNG-логотипа стал бы чёрным прямоугольником.

### 2.3 Идемпотентность и повтор

`ensureVariants` идёт по плану и не пересоздаёт то, что уже есть: вариант берётся из записи, только
если его объект действительно лежит в хранилище. Проверка по объектам, а не по длине списка —
запись могла пережить потерю файла, и повтор задания такой вариант восстанавливает, а не считает
набор готовым.

Отказ на любом варианте сохраняет уже полученную часть набора и пробрасывается наружу: без этой
записи повтор не знал бы, что пересоздавать не нужно (`image-variants.md` §2 п. 8, заметка
владельца п. 9). В `runMediaProcessing` варианты встали между мастером и снятием карантина; запись
с уже существующим мастером доделывает только недостающее и не перечитывает мастер, если набор
цел — повтор после частичной ошибки не должен стоить как первая обработка.

Варианты прежней матрицы, которых нет в плане, в набор не переносятся. Удаление их объектов — шаг
миграции набора ширин (§2 п. 6), а не обработки одного файла.

### 2.4 Ключи в базе, адреса в API

В колонке остаются ключи хранилища: смена провайдера меняет домен, а не ключи
(`access-and-signed-urls.md` п. 9). Адрес собирается при чтении из `STORAGE_MEDIA_BASE_URL`, и в
ответ попадают только записи с ключом вида `variant` — право на файл проверяет раздача по ключу
(`storage/access.ts`), а не эта сборка. Поле `variants: JSON!` получило описание схемы вместо
прежней отсылки к невыполненной задаче; зеркало схемы в вебе обновлено тем же проходом.

### 2.5 Вывод в вебе

`MediaPicture` — `<picture>` с источником AVIF и запасным WebP. Формат без вариантов источником не
становится: пустой `srcset` заставил бы браузер выбрать несуществующий файл. В `src` у `<img>`
идёт самый широкий WebP — `src` читает браузер, не выбравший ни одного `<source>`, и запасной
формат для него надёжнее (журнал §29.4). Размеры проставлены атрибутами, чтобы место под
изображение резервировалось до загрузки; заполнитель стоит фоном того же `<img>`.

`alt` компонент принимает готовым и ничего к нему не добавляет: описание всегда принадлежит самому
медиафайлу, узел документа его не переопределяет (журнал §29.13). Пустая строка допустима — так
помечается декоративное изображение. Изображения «в меру», «широкое» и «полное»
(`06-design-system.md` §5) различаются только значением `sizes`: отдельных файлов под них нет
(`image-variants.md` §2 п. 5).

`NuxtImg` для пользовательских изображений не используется: варианты уже сделаны при загрузке,
обработки на лету нет. Провайдер `none` в `nuxt.config.ts` остался с T-004, комментарий к нему
уточнён.

## 4. Остаток

- Точные точки останова и параметры сжатия — отдельный проход конвейера медиа (Q-03, журнал §29.12,
  §33 п. 3): числа предлагает архитектор, утверждает владелец. До утверждения матрица остаётся
  временной, а загрузка пользователям закрыта признаком `MEDIA_UPLOAD_ENABLED`.
- Скрипт пересчёта вариантов при смене матрицы (`image-variants.md` §2 п. 6) и удаление объектов
  прежних ширин в задачу не входили.
- Перевод карточек и страниц на `MediaPicture` — T-056 и T-066: компонент готов, но ни одна
  страница пока не берёт изображения из базы.
- Независимое ревью и Done — за координатором; поля `review` в receipt оставлены незаполненными.

Код слит в `app` автослиянием GitHub по зелёному CI (PR #344, merge `4da313d`) прогоном агента,
который завершился отказом `403 Request not allowed` на публикации итогового комментария — его
идентификатор прогона не восстановим, поэтому в receipt указан прогон, выпустивший этот отчёт.
