### Инвариант «хотя бы один владелец» под конкуренцией (AC-1)

`revokeOwner` и `deactivateOwner` первым действием транзакции берут блокировку строк действующих
владельцев: `SELECT "id" FROM "users" WHERE "role" = 'owner'::"Role" AND "archivedAt" IS NULL
ORDER BY "id" FOR UPDATE` (`server/src/admin/staff.ts`, `lockActiveOwners`). Приём тот же, что у
слияния разделов (`server/src/taxonomy/service.ts`).

До этого проверка шла на READ COMMITTED без блокировки: два владельца, снимающие друг друга
одновременно, читали каждый своего соседа, оба видели двух владельцев и оба коммитились — система
оставалась без владельца (write skew, журнал #10). `ORDER BY "id"` задаёт обеим транзакциям один
порядок захвата строк, поэтому встречные действия не блокируют друг друга взаимно.

Serializable не выбран: раздел уже опирается на условные `updateMany` (`replaceRole`, `closeAccess`),
и блокировка строк держит инвариант без повторов транзакции на ошибке сериализации.

### Ошибки мутаций в интерфейсе (AC-2)

`useAdminStaff` получил отдельное состояние `actionFailure` (приём `useAdminJobs`) с полями `code`,
`entity`, `field`, `rule`, `requestId`. После любого исхода мутации список, владельцы и открытая
карточка перечитываются, и только затем ставится состояние отказа — иначе успешное чтение списка
сбрасывало его. Страница `web/app/pages/admin/admins/index.vue` показывает строку `role="alert"` с
`data-staff-failure="<код>"` на самой странице и в диалогах причины, создания и назначения; текст
выбирается по коду, а внутри `VALIDATION_ERROR` — по `rule`/`field`. Конфликт по сущности `owner`
наконец использует заготовленную строку `admin.staff.lastOwner`.

Ограничение: `requestId` публичен только у `INTERNAL_ERROR` и `PROVIDER_UNAVAILABLE`
(`server/src/errors/graphql-error.ts`, словарь ошибок T-086) — у остальных кодов он вырезается из
extensions. Интерфейс печатает код запроса, когда сервер его отдал; расширять словарь на остальные
коды в этой задаче не стал: это изменение общего контракта ошибок, а не раздела.

### Список владельцев без полного e-mail (AC-3)

`listOwners` отдаёт `maskEmail(email)` и `emailMasked: true`; поле добавлено в `AdminOwner` и в
запрос `GetOwners`. Полный адрес остаётся только в карточке служебной записи, чьё открытие пишет
`admin.read.personal`. Это приводит список владельцев к правилу, которое §8 спецификации уже
формулирует: «не аудируется просмотр списка с маскированным e-mail». Отдельной записи чтения ПДн
для списка не нужно, потому что ПДн он больше не раскрывает (§28.7).

Двухшаговое назначение владельца не затронуто: точный адрес для второго шага берётся из карточки.

### Атомарное создание служебной записи (AC-4)

`createUserWithReservedHandle` принимает целевую роль, признак служебной записи и необязательный шаг
`withinTransaction`, который выполняется в той же транзакции. `createStaff` создаёт аккаунт сразу
служебным, с ролью и аудитом `user.create.staff`, одной транзакцией. Цикл повтора при занятом хэндле
остался снаружи: неуникальность отменяет транзакцию PostgreSQL целиком, и новая попытка возможна
только новой транзакцией.

Раньше аккаунт создавался первой транзакцией, а роль и аудит — второй: сбой между ними оставлял
аккаунт читателя с занятым адресом, и повторное создание навсегда падало
`VALIDATION_ERROR/not-an-account` (журнал #46–47). Письмо входа по-прежнему ставится после коммита:
недоступная почта запись не отменяет (`appoint-admin.md` §5).

### Тесты проверены на способность падать

- Со снятыми вызовами `lockActiveOwners` оба встречных сценария дают два успеха вместо
  «успех + `CONFLICT`», и в базе остаётся ноль активных владельцев — исходный write skew
  воспроизводится.
- С возвратом создания к двум транзакциям аккаунт читателя с этим адресом остаётся в базе после
  сбоя второго шага, и проверка AC-4 падает на `findUnique({ where: { email } })`.

  повторную приёмку в своей карточке ALTE-94.
- `requestId` у `VALIDATION_ERROR`, `FORBIDDEN`, `NOT_FOUND` и `CONFLICT` остаётся невидимым по
  словарю ошибок — вопрос к владельцу, расширять ли контракт.
- Производные таблицы бэклога (`docs/backlog/matrix.md` и прочие) держат T-133 в статусе
  «кандидат» вместе с другими слитыми задачами; их пересобирает отдельный проход
  `scripts/backlog/sync_status.py --apply`.
