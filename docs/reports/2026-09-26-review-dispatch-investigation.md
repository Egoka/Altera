- **План**: [docs/plans/2026-09-26-review-dispatch-investigation.md](../plans/2026-09-26-review-dispatch-investigation.md)
- **Базовый `app`**: `753d7cce6f2b1a4a74f110212523da13a9588ab4`. Срез Multica — 2026-09-26: 107 карточек,
  `in_review` 43, `done` 50.
- **Метод**: только чтение Multica (`autopilot list`, `agent tasks`, `issue runs`, `issue comment list`),
  копия ledger контроллера, установленные контракты и config (без секретов), `controller.py verify`
  в отдельном worktree. Автопилоты, статусы и карточки не менялись.

## Коротко

1. **Отдельного правила «запускать ревьюера на задачи в `in_review`» нет ни в одном автопилоте.**
   «Очередь разработки» (`c40fbc10`) и «Восстановление работы» (`e564a6fb`) — два расписания одного
   агента-оркестратора (`d08ef989`) с одинаковым описанием. Ревью в нём — действие перед слиянием:
   «Review запрашивай на финальном head — том, который пойдёт в merge». Порядка шагов для Done нет.
2. **После PR #178 (слит 2026-09-20 20:08 UTC) ревью перестало быть условием слияния, а новое место
   запуска — переход в Done — никому не поручено.** Исполнитель включает автослияние и «не ждёт»,
   GitHub сливает PR за час. С 20:08 20.09 до остановки 21.09 ревьюер не запускался ни разу, хотя
   оркестратор отработал 41 проход с вызовом модели.
3. **Done сломался ещё раньше, 19.09, на пробе выкладки.** Последний успешный `controller.py done` —
   2026-09-19 15:20 UTC (T-029, T-069), их пробу выкладки сделал ревьюер. Релиз-инженер с 15.09 не имеет
   Render MCP и последний раз запускался 18.09. После 19.09 пробы никто не заказывал: оркестратор
   решил, что «нет live deployment verifier» — из-за мёртвого поля config `deployment_probe: null` и
   фразы контракта. 21.09 он принял холодный старт Render за «среда недоступна».
4. **13 запусков ревьюера за сутки — все до #178 и все ради слияния, а не Done.** 9 одобрений, из них
   6 с валидным маркером. Ни одно не было записано в receipt и не привело к `done`.

## Первопричина

Подтверждена запусками, кодом и ответами контроллера:

1. **Нет владельца и триггера фазы Done.** Ни в описаниях автопилотов, ни в инструкции оркестратора,
   ни в контракте нет шагов «ревью слитого head → итог в `app` → проба выкладки → `done`» и указания,
   кто их делает. До #178 ревью вынуждал gate слияния. После #178 его не вынуждает ничто: 27 из 30
   receipt без ревью. Оркестратор сам формулировал разрыв и откладывал его: 20.09 09:00 — «это
   ответственность финализирующего/daily-runtime, а не автопилота очереди разработки».
2. **Проба выкладки не заказывалась с 19.09.** Причины: у релиз-инженера нет Render MCP; поле
   `deployment_probe: null` (контроллер его не читает) выглядело как «проверки нет»; холодный старт
   Render (21.09 12:00 — HTTP 000 за 20 с; 26.09 — 200, `revision` `db6f168`) читался как «среда лежит».
   Проба живёт только час, поэтому её нельзя заказать заранее — нужен тот, кто закажет её и сразу
   вызовет `done`.
3. **Сопутствующие дефекты:**
   - маркер ревьюера не последней строкой (4 из 13);
   - одобрения не переносятся в receipt;
   - `tested_sha`/итог не обновлены после разрешения конфликта;
   - зависший `running` в ledger (T-007);
   - сигнал внимания не различает «нужна реализация» и «нужна финализация».

Конфликта автопилотов и лимитов очереди как причины нет. Два расписания на одном агенте с
`max_concurrent_tasks: 1` лишь сериализуют проходы.

## Решение

Сравнение вариантов, готовые тексты и порядок шагов — [фаза Done после автослияния](../multica/done-finalization.md).
**Рекомендация — вариант (б): отдельный автопилот «Altera — приёмка в Done»** на отдельном агенте,
раз в час в :30. В нём:

- отбор только слитых PR без активных run;
- одно ревью на пару (карточка, SHA) и один повтор из-за формата;
- один docs-PR итогов за проход;
- одна проба выкладки за проход через агента с Render MCP;
- `controller.py done` в течение часа после пробы;
- маркер `ALTERA_FINALIZE_V1` против повторов неизменного состояния.

В оркестратор добавляется строка о том, что слитые задачи он не ведёт. Вариант (а) проще, но
повторяет условия 20–21.09: обязанность конкурирует с пополнением очереди в одном слоте.

## Изменения этого захода

- `scripts/autonomy/controller.py`: запись `running` фазы `done` освобождается (`release_unapplied`),
  если карточка, прочитанная под `dispatch.lock`, не в Done. Повтор идёт в прежний бюджет трёх попыток.
  Для `merge` поведение прежнее. Тесты: `test_stale_done_running_*`, `test_stale_merge_running_is_still_not_replayed`.
  Начнёт действовать после переустановки runtime.
- `docs/multica/done-finalization.md` — порядок фазы Done, варианты (а)/(б) с готовым текстом.
  Намеренно не `*-prompt.md`: `install.py` установил бы его как контракт без решения владельца.
- `docs/multica/autonomy-controller.md` — ссылка на документ фазы Done.

Проверки: `python3 -m unittest discover -p 'test_*.py'` в `scripts/autonomy` — 218 тестов, OK;
хуки коммита (`format`, `lint`, `test`).

## Что нужно от владельца, чтобы снова включить автономию

1. **Выбрать вариант** (рекомендую (б)) и разрешить изменение Multica:
   - создать агента-финализатора (или перепрофилировать `933edc82`) с Render MCP только на чтение;
   - создать автопилот по тексту из документа;
   - добавить строку в описание оркестратора;
   - дополнить инструкцию ревьюера: маркер — последним действием, после уборки.
2. **Переустановить runtime** (`scripts/autonomy/install.py`) после слияния этого PR и убрать из
   установленного config поле `deployment_probe`.
3. **Сверить ledger T-007**: после переустановки контроллер сам освободит ключ при следующем `done`.
   Без переустановки — только ручная правка ledger с вашего разрешения.
4. **Проверочный запуск**: после создания автопилота запустите его один раз вручную (`autopilot trigger`)
   при остальных на паузе. Ожидаемо: для слитой задачи с одобрением на итоговом head (например,
   T-089 после ревью) — один run ревьюера или пробы в карточке, затем `controller.py done` → `{"ok": true}`,
   карточка в Done, файл в `verified/`. Второй запуск без изменений — `no_action`, без новых запусков.
5. Параллельная сессия ручной приёмки 43 задач уже ведёт ревью и Done этих карточек. Новый автопилот
   стоит включать после неё, чтобы не запрашивать ревью дважды.
