## Предложение: дашборд владельца

### Общие правила

1. Переключатель периода остаётся `7d | 30d`. Периодические показатели сравниваются с
   непосредственно предшествующим периодом той же длины.
2. Для периодического показателя выводятся значение, абсолютная разница и процентная разница.
   Если в предыдущем периоде был ноль, процент не показывается: вместо бесконечного роста
   выводятся абсолютная разница и пометка «нет базы для сравнения».
3. Текущие состояния очередей, ошибок и доступов не получают искусственную динамику: рядом с
   ними показываются число и время обновления. Историческая динамика появится только там, где
   хранится сопоставимый снимок или событие.
4. Служебные и тестовые аккаунты исключаются из продуктовых показателей. Сейчас схема явно
   хранит только `isServiceAccount`; до реализации нужен один канонический способ распознавать
   тестовые аккаунты, иначе фильтр нельзя считать выполненным. Платежи учитываются только после
   включения платности и только по правилам валидности из раздела «Статистика».
5. Отсутствующий источник показывается как «появится с этапом …», а не как ноль.

Первые три показателя можно вычислить на этапе 1, но текущие строки `User` и `Article` дают
только число сохранившихся записей: permanent delete способен уменьшить результат прошлого
периода. До появления неизменяемого дневного снимка они показываются как «по текущим данным» без
динамики; после снимков становятся стабильными KPI с предыдущим равным периодом. Прочтения и
сохранения добавляются без изменения структуры блока, когда появятся утверждённые дневные
агрегаты этапа 2. Текущие строки `Bookmark` нельзя считать историей добавлений: удалённая
закладка исчезает из таблицы, поэтому такой расчёт систематически занижал бы показатель.

### Важные изменения и события

Блок «Важные изменения» строится за выбранный период из `AuditLog`, группируется по смыслу и
ведёт в полный аудит:

- владельцы и служебные роли: `role.assign.owner`, `role.revoke.owner`, `owner.deactivate`,
  `user.role.change`, `user.create.staff`;
- индивидуальные права: `permission.exception.grant`, `.revoke`, `.expire`;
- настройки и правила: `settings.change`, `secrets.rotate`, `legal.update`;
- необратимые или структурные изменения: `entity.delete.permanent`, `section.*`, `tag.*`,
  `format.update`.

Дашборд показывает количество по группе и последние три записи без раскрытия ПДн. Это не
определяет признак «критичной» записи: компактный блок критичного аудита остаётся отдельным
местом дашборда и начинает отбор только после утверждения критерия по §37 п. 15.

Краткая картина событий за период использует уже сохранённые факты:

- положительные: первые публикации по сохранившимся материалам, восстановления аккаунтов и
  материалов из `AuditLog`, переходы backend-ошибок в `resolved` из
  `BackendErrorStatusHistory.createdAt`;
- негативные: архивирования аккаунтов и материалов, запросы доработки и финальные отказы из
  `AuditLog`; новые ошибки из `BackendErrorEvent.occurredAt`; неудачные доставки из
  `MailDeliveryEvent.occurredAt`.

`Job.status` и `MailMessage.status` описывают текущее состояние и могут измениться после повтора,
поэтому по ним нельзя строить периодические события. `failed` / `stuck` остаются текущим
операционным числом; периодическая история заданий требует отдельного неизменяемого события или
явно утверждённого правила подсчёта `JobAttempt`.

Значения не сворачиваются в единый «здоровье-балл»: события несопоставимы по смыслу, а веса
стали бы новым продуктовым правилом без фактического основания.

## Предложение: регулярность автора

### Расчёт

Рекомендуемый показатель — доля активных месяцев среди месяцев, в которых уже можно честно
оценивать автора:

```text
regularityPercent = round(100 * activeMonths / eligibleMonths)
```

- окно — шесть последних **полностью завершённых** календарных месяцев в UTC;
- активный месяц — месяц, в котором автор впервые опубликовал хотя бы один материал;
- публикация считается один раз по `Article.firstPublishedAt`: повторная публикация того же
  материала, восстановление или несколько языковых версий не увеличивают регулярность;
- месяц первой публикации автора исключается как неполный; `eligibleMonths` — следующие
  завершённые месяцы, попавшие в шестимесячное окно;
- до трёх `eligibleMonths` числовой процент не показывается, состояние —
  `INSUFFICIENT_HISTORY`; график публикаций и дата последней первой публикации остаются видны;
- три и более публикации в одном месяце всё равно дают один активный месяц: показатель измеряет
  ритм, а не объём;
- результат не участвует в рейтинге, грейде, доступах или сравнении авторов. Рядом выводится
  расшифровка «публикации были в X из Y полных месяцев».

Предлагаемый контракт поля:

```text
regularity {
  status: READY | INSUFFICIENT_HISTORY
  percent: Int
  activeMonths: Int!
  eligibleMonths: Int!
  lastPublishedAt: DateTime
  publishedByMonth: [{ month, publishedCount }!]!
}
```

Для `INSUFFICIENT_HISTORY` поле `percent` равно `null`. `publishedByMonth` содержит шесть
завершённых месяцев, включая нули. `lastPublishedAt` — максимальный `firstPublishedAt`, поэтому
перепубликация старого материала не выглядит как выпуск нового.

### Почему этот вариант

- он использует уже сохранённый `Article.firstPublishedAt` и не требует выдумывать желаемую
  частоту публикаций для каждого автора;
- месячные интервалы совпадают с уже намеченным `publishedByMonth[]` и не штрафуют автора за
  отсутствие еженедельного выпуска;
- исключение неполных месяцев устраняет штраф за регистрацию в конце месяца и за ещё не
  завершившийся текущий месяц;
- отдельное состояние нехватки истории не выдаёт один ранний материал за устойчивые 100 %;
- формула объясняется одной фразой и не раскрывает внутренние коэффициенты рейтинга, потому что
  их не использует.

Ограничение этапа 1: расчёт по существующим материалам может измениться после их необратимого
удаления. Дневные агрегаты вовлечённости сами по себе не сохраняют историю публикаций. Для
стабильной регулярности нужен отдельный месячный снимок первых публикаций или эквивалентный
неизменяемый факт; после его появления закрытые месяцы читаются из него и не пересчитываются
задним числом.

### Контрольные примеры

| Случай                                                | Результат                                                         |
| ----------------------------------------------------- | ----------------------------------------------------------------- |
| публикаций ещё не было                                | `INSUFFICIENT_HISTORY`, `lastPublishedAt = null`                  |
| первая публикация в текущем месяце                    | `INSUFFICIENT_HISTORY`; текущий неполный месяц не входит в расчёт |
| после первого неполного месяца завершились два месяца | `INSUFFICIENT_HISTORY`, даже если оба активны                     |
| за четыре подходящих месяца публикации были в трёх    | `READY`, `75 %`, пояснение «3 из 4»                               |
| пять публикаций в одном из четырёх месяцев            | месяц считается один раз                                          |
| старый материал восстановлен или повторно опубликован | новая активность месяца не создаётся                              |

## Что требуется утвердить владельцу

1. Состав блоков и правило сравнения периодов дашборда владельца.
2. Отложенное появление прочтений, сохранений и финансов вместо показа ложных нулей.
3. Шестимесячное окно, минимум три подходящих месяца и формулу доли активных месяцев для
   регулярности.
4. Нейтральный характер регулярности: только объясняющая личная метрика, без влияния на рейтинг
   и права.

`docs/spec/40-admin/dashboard.md` и `docs/spec/30-account/author/stats-overview.md`, затем завести
отдельную реализацию. До этой записи настоящий документ остаётся предложением.
