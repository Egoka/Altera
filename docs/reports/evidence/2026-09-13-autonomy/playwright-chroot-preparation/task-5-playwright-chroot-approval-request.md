# Запрос конкретного расширения seccomp для Playwright

Статус: подготовка; разрешение владельца ещё не получено, кандидат не применён.

## Предлагаемое изменение

Кандидат `playwright-chroot-preparation/candidate.json`, SHA-256
`e75c64002d22c7893bbc3aef2f8d7c0dde8f673254d0846d9182e89b180024f1`.
От исходного `ff9cc602bfbd54007f4894c121d9f3013e4e7a2a9b9b7a7d3fcd7c2f0f3b7140`
он отличается только удалением условия `includes.caps=[CAP_SYS_CHROOT]`
у единственного правила `names=[chroot]`. Все остальные правила сохраняются.
Фильтр предназначен только для изолированного runtime тестировщика с Playwright;
глобальная конфигурация Docker не меняется.

Разрешение относится к пропуску syscall через seccomp, а не к выдаче capability:
UID/GID 1000, cap-drop ALL, no-new-privileges и read-only rootfs сохраняются.
Ядро по-прежнему проверяет права в user namespace. Seccomp не может ограничить
этот вызов конкретной строкой пути, поэтому процесс с соответствующим правом
в собственной user namespace сможет вызывать chroot для любого видимого ему
пути. Доступные mounts этим изменением не расширяются.

## Последовательность после независимой статической проверки

1. До расширения фильтра: read-only проверка наличия, ELF/архитектуры и хэша
   `/usr/bin/perl` в закреплённом образе. Она использует текущий built-in seccomp,
   network none, без mounts/учётных данных, и входит в уже разрешённую подготовку.
2. После конкретного разрешения владельца: два ограниченных диагностических
   запуска одного неизменённого helper в образе
   `sha256:97bd451e71779dbd6527814023f16dd952e792ba633132fc7da297aed10b1426`:
   исходный фильтр и кандидат. Network none, памяти128MiB, CPU1, PIDs32,
   внешний timeout15секунд на arm, единственный mount — read-only helper.
   Записать actual return/errno, namespaces, metadata и удаление точных контейнеров.
3. Только если контроль вернёт EPERM, а кандидат успех, и отдельные R1/R2
   исправления canary/runtime приняты независимым ревью: разрешить одну
   cause-based recovery той же полной Playwright canary под новым фильтром.
   Сохранить оба прежних отказа и счётчик2 до фактического PASS. Canary использует
   только синтетические локальные web/redirect fixtures, без модели и credentials.
   При неожиданном результате остановиться и сообщить, не выполнять новые повторы.
4. Только после полной canary и независимой приёмки допускается закрепить этот
   точный фильтр для runtime тестировщика. Native приёмка, Multica readback,
   сквозной пилот и включение автопилотов остаются отдельными обязательными gates.

Это не разрешение повторять refresh Claude, читать credentials, отключать sandbox,
добавлять capabilities, включать глобальный профиль или выдавать receipt заранее.

## Почему запрашивается подтверждение

План исполнения, Task4: «конкретные расширения безопасности и недостающие решения
запрашивать на последнем шаге». Навык subagent-driven-development также относит
`a security-sensitive action` к случаям `stop and ask`. Общая задача уже разрешает
подготовку и обратимые исправления; дополнительный вопрос касается только этого
конкретного расширения syscall-фильтра. Предыдущее «Да разрешаю» использовано
для одного refresh/Opus запроса Claude и не переносится на другую операцию.
