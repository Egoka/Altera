# Claude credential refresh preflight (design only)

Primary sources checked 2026-09-14: [official environment variables](https://code.claude.com/docs/en/env-vars), [official authentication](https://code.claude.com/docs/en/authentication). The documented headless operation is fixed `claude auth login` with `CLAUDE_CODE_OAUTH_REFRESH_TOKEN` and `CLAUDE_CODE_OAUTH_SCOPES`; it exchanges a refresh token without opening a browser. The credentials file remains a CLI-managed artifact. An expired/revoked login that cannot refresh requires the user to sign in again. A long-lived setup-token is another mode, not an automatic replacement for the user's existing login.

## Candidate design for separate implementation/review

Keep the checker credential input read-only. A dedicated trusted refresh container has no source checkout, model tools, MCP, gate authority, Multica token, host HOME, Docker socket, or host execution bridge. Its fixed operation validates one mounted credential artifact's bounded structure internally, transfers only the CLI-required refresh token/scopes through the child environment inside the container, and invokes pinned Claude auth login. These opaque values must never appear in tool output, command-line arguments, Docker environment metadata, source manifests, hashes, telemetry, or archives. No root agent reads credential contents. The only writable output is a new private credential generation and minimal allowlisted status.

A coordinator single-writer lock prevents simultaneous refresh or checker generation selection during publication. Retain the previous generation until the new one is structurally valid and independently accepted by a fresh container; publish an atomic private pointer only after success. Because provider rotation can invalidate a previous refresh token, a crash after exchange must retain the unpublished new generation for deterministic recovery instead of discarding it or retrying with the old token. Failed refresh must not overwrite known credentials or start a browser/model/API-billing fallback. Revoked credentials stop with one actionable request for user login.

Required evidence before live exchange: narrow implementation brief and independent review; pinned CLI support (synthetic invalid token must take noninteractive path without printing its value); synthetic success/failure/timeout/concurrency/interrupted-publication tests; secret canaries; no source/network bypass. Then one explicitly recorded real headless exchange may prove refresh without waiting for access-token expiry, followed by fresh-container auth status/model acceptance using the new generation. Actual token values or their digests are never evidence. Changed-generation booleans and file permission/ownership metadata are sufficient. The provider call's rotation side effect must be handled transactionally as above.

Current status: this is a researched supported candidate, not an implemented or accepted refresh operation. Existing user login and standalone model proof remain intact. No auth file was read, changed, refreshed, revoked or copied during this preparation.
