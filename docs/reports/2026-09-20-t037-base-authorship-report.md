# Отчёт: T-037 — базовое авторство при первом «Создать статью»

- **Задача**: T-037, Multica ALTE-84; план — `docs/plans/2026-09-20-t037-base-authorship.md`
- **Baseline**: `4ea27a63d0fac9ccc9eb38cde522d9b17b58799b` (`origin/app`)
- **Ветка**: `server/t037-base-authorship`, рабочее дерево `.worktrees/t037-authorship`
- **Зависимости на момент работы**: T-017 (merge `7a900e02`), T-026, T-039 (merge
  `2f8870505e5e27e128d26a8da0362431b3a98b2a`, PR #117) — все в `app`

## 1. Результат

Первое нажатие «Создать статью» бессрочно открывает базовые авторские возможности без оплаты и
ручного одобрения, тем же вызовом создаётся черновик и открывается редактор. Событие
`author.enabled` (#87) пишется в аудит с `userId`, `grantId` и временем. Служебные роли и
служебные записи авторство не получают.

## 3. Правило «первого нажатия»

Признак того, что нажатие первое, — у аккаунта нет ни одной записи `PlanGrant`. Подписок на
этом этапе нет (модели `Subscription` в схеме нет), поэтому `PlanGrant` — единственный источник
плана (`role-derivation.md` п. 1).

Следствия, заложенные в код:

1. Повторное нажатие у включённого автора не создаёт вторую выдачу и не пишет второе событие.
2. Расхождение кэша (`planTier = free` при действующей бессрочной выдаче) чинится по выдаче как
   источнику истины, без второй выдачи и без второго события (`role-derivation.md` п. 1, 9).
3. Истёкшая срочная выдача и отозванная бессрочная выдача **не** превращаются в новое базовое
   авторство: создание остаётся закрытым `PLAN_LIMIT` до продления (`plan-free.md` п. 3–4).
4. Действующий план со сроком не трогается: `planUntil` не обнуляется.

`[ДОПУЩЕНИЕ]` Пункт 3 — трактовка, сводящая §25.1 («первое нажатие открывает авторство») с
`plan-free.md` п. 3–4 («истёкший план закрывает создание»). На бесплатном первом запуске эти
случаи не возникают; при включении платности судьба базовых выдач — отдельное решение владельца
(`90-business-model/overview.md` §6), и это правило может быть пересмотрено.

`[ДОПУЩЕНИЕ]` Аудит `author.enabled` пишется с `actorId` и `actorRole` включаемого аккаунта
(роль до включения — `reader`), хотя реестр событий называет актором систему: так сохраняется
связь «кто нажал». Поля события (`userId`, `grantId`, время) соответствуют реестру #87.
